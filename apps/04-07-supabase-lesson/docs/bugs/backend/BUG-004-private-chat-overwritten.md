# BUG-004 — Групповой апдейт перенаправляет личный диалог гостя в группу

- **Статус:** open
- **Важность:** high
- **Область:** backend
- **Модуль:** supabase/functions/_shared/repositories/conversationsRepo.ts:21–29; supabase/functions/telegram-webhook/router.ts:73–90
- **Найден:** 2026-11-17, code review
- **Спринт-источник:** ревью текущего приложения, не относится к спринту

## Симптом, воспроизведение и причина

**Условие:** бот добавлен в группу и получает команду от гостя, который уже общался с ним лично. Наличие такой настройки у рабочего бота в рамках ревью не проверялось.

`buildContext` открывает диалог до проверки типа чата. Уникальность диалога задана по ресторану, каналу и пользователю, а `chat_id` каждый раз перезаписывается. Поэтому команда `/start@bot_name` в группе заменяет адрес личного диалога на ID группы. Ответ менеджера через handoff использует этот сохранённый адрес; личные заявки также доступны тому же гостю через «Мои заявки» в группе. Это может раскрыть группе сведения, ранее переданные в личном чате.

**Воспроизведение:** открыть личный диалог, затем от того же пользователя отправить боту команду в группе; после этого отправить ответ менеджера из админки. Ожидается сохранение личного адресата; по коду ответ уйдёт в группу до следующего личного апдейта.

**Доказательство:** вызов настоящего `upsertConversation` дважды с подменённым клиентом подтвердил замену `chat_id: 42` на `-99` при неизменном ключе конфликта. Полный сценарий Telegram/БД не запускался. Telegram допускает адресованные боту команды в группах и при privacy mode: [официальный FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

**Предложение:** отклонять неперсональные чаты до `openConversation` в обоих путях — message и callback. Если группы действительно нужны, разделить диалоги по chat ID и явно определить правила доступа к личным заявкам.

**Регрессия:** private → group command/callback не меняет личный `chat_id`, не открывает личные заявки; ответ менеджера остаётся в private.
