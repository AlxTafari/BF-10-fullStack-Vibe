## Находки и предложения

### BUG-004: Групповой апдейт перенаправляет личный диалог гостя в группу

**Приоритет:** P1 / high. **Место:** `supabase/functions/_shared/repositories/conversationsRepo.ts:21–29; supabase/functions/telegram-webhook/router.ts:73–90`.

**Условие:** бот добавлен в группу и получает команду от гостя, который уже общался с ним лично. Наличие такой настройки у рабочего бота в рамках ревью не проверялось.

`buildContext` открывает диалог до проверки типа чата. Уникальность диалога задана по ресторану, каналу и пользователю, а `chat_id` каждый раз перезаписывается. Поэтому команда `/start@bot_name` в группе заменяет адрес личного диалога на ID группы. Ответ менеджера через handoff использует этот сохранённый адрес; личные заявки также доступны тому же гостю через «Мои заявки» в группе. Это может раскрыть группе сведения, ранее переданные в личном чате.

**Воспроизведение:** открыть личный диалог, затем от того же пользователя отправить боту команду в группе; после этого отправить ответ менеджера из админки. Ожидается сохранение личного адресата; по коду ответ уйдёт в группу до следующего личного апдейта.

**Доказательство:** вызов настоящего `upsertConversation` дважды с подменённым клиентом подтвердил замену `chat_id: 42` на `-99` при неизменном ключе конфликта. Полный сценарий Telegram/БД не запускался. Telegram допускает адресованные боту команды в группах и при privacy mode: [официальный FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

**Предложение:** отклонять неперсональные чаты до `openConversation` в обоих путях — message и callback. Если группы действительно нужны, разделить диалоги по chat ID и явно определить правила доступа к личным заявкам.

**Регрессия:** private → group command/callback не меняет личный `chat_id`, не открывает личные заявки; ответ менеджера остаётся в private.

### BUG-005: Запоздавший AI-ход восстанавливает отменённый сценарий

**Приоритет:** P1 / high. **Место:** `supabase/functions/_shared/services/flow.ts:151–175; supabase/functions/_shared/repositories/conversationsRepo.ts:38–44; supabase/functions/telegram-webhook/handlers/ai.ts:17–20`.

Агент работает со снимком диалога начала запроса. После ожидания LLM инструменты `draftBookingFromAgent` и `draftGuestRequestFromAgent` безусловно сохраняют состояние по ID диалога. Отмена, начало другого сценария или подключение менеджера во время ожидания не делают этот снимок недействительным. Перед отправкой AI-ответа актуальность ручного режима также не проверяется.

**Воспроизведение:** задержать ответ модели; пока она готовит черновик, выполнить `/cancel` либо подключить менеджера; затем разрешить модели вызвать draft tool. Ожидается сохранение отмены/ручного режима; фактически старый ход может записать черновик заново и показать его гостю. При handoff это позволяет боту снова забрать последующий текст в сценарий.

**Доказательство:** последовательность настоящих `cancelFlow` → запоздавший `draftBookingFromAgent(current=null)` на подменённом клиенте восстановила `state.flow = booking`. Это детерминированная модель порядка конкурентных операций; полный параллельный webhook-тест с БД не запускался.

**Предложение:** ввести версию состояния/поколение хода. Отмена, новый сценарий и handoff должны увеличивать её; сохранение AI-черновика — атомарный CAS по ожидаемой версии. Перед показом результата проверять актуальность хода. Очередь `FlowHolder.queue` работает только внутри одного AI-хода и не защищает от другого webhook.

**Регрессия:** отложенный fake LLM + отмена, новый сценарий и handoff; старый ход не меняет state и не публикует устаревшую карточку.

**Связь с принятым ограничением:** `docs/STATE.md` уже описывает last-write-wins для двух обычных действий на шаге. Здесь выделено более широкое последствие: длительный AI-ход нарушает отмену и подключение человека, а не только теряет один из быстрых вводов.

### BUG-006: Отмена исходной брони и её изменения не атомарна

**Приоритет:** P2 / medium. **Место:** `supabase/functions/_shared/services/myRequests.ts:84–87; supabase/functions/_shared/repositories/bookingRequestsRepo.ts:102–131`.

`cancelMyBooking` выполняет два независимых запроса: отмена исходной брони, затем отмена ожидающего изменения. Если второй запрос падает, исходная бронь остаётся cancelled, а изменение — pending. Повторный вызов заканчивается на `not_cancellable` и не пытается завершить каскад.

**Воспроизведение:** создать активную бронь с pending-изменением; после успешного первого UPDATE вернуть ошибку второго; повторить отмену. Ожидается атомарная отмена обеих записей либо восстановление при повторе; фактически остаётся pending-заявка к отменённой брони. Это засоряет очередь менеджера и нарушает инвариант каскадной отмены. Подтверждение такой заявки RPC отдельно запрещает — успешное подтверждение здесь не утверждается.

**Доказательство:** fault injection на подменённом Supabase-клиенте при вызове настоящего `cancelMyBooking`: первый вызов бросил ошибку второго запроса; повтор вернул `not_cancellable`; второй UPDATE вызывался ровно один раз.

**Предложение:** вынести гостевую отмену и каскад в один RPC/транзакцию, с проверкой принадлежности и порядком блокировок «исходная → изменение», согласованным с RPC менеджера. Отдельно предусмотреть восстановление уже возникших несогласованных строк.

**Регрессия:** ошибка каскада откатывает обе записи; повтор безопасен; конкурентное подтверждение изменения и отмена исходной не оставляют неконсистентные статусы.

### BUG-007: CI пропускает изменения общих зависимостей приложения

**Приоритет:** P2 / medium. **Место:** `.github/workflows/guest-bot.yml:20–30`.

Оба фильтра `paths` учитывают только каталог приложения и сам workflow. При этом установка использует корневые `pnpm-lock.yaml`, `pnpm-workspace.yaml` и `package.json`. Изменение только lock-файла, например версии транзитивной зависимости админки, не запустит проверки и публикацию этого приложения.

**Воспроизведение:** PR с изменением только относящихся к админке записей корневого lock-файла. Ожидается запуск Guest bot; ни один заданный путь не совпадёт. Состояние branch protection не проверялось; последствия для возможности merge зависят от него.

**Доказательство:** статическая проверка списка путей и команд установки. Семантика фильтра подтверждается [документацией GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore). Тестовый push/PR не создавался.

**Предложение:** добавить в оба списка `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `package.json`; при появлении общей конфигурации также включать её. Более сложный анализ графа зависимостей для этого проекта пока не нужен.

**Регрессия:** изменение каждого общего файла запускает workflow; изменение изолированного другого приложения без общих файлов не запускает.
