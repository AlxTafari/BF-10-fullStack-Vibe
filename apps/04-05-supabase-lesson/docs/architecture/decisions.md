# Архитектурные решения (ADR)

Единый источник правды. Роадмап и код обязаны соответствовать этим решениям; расхождение — повод
править ADR, а не молча делать иначе.

Исходные документы — `../restaurant-guest-bot-mvp-plan.md`.

## Статусы

- **Принято** — реализуем так.
- **Отложено** — решение верное, но его цена не оправдана сейчас. Отсутствие в коде — **не баг**.
- **Предложено** — требует решения владельца.

Полная сводка расхождений кода с решениями — `../STATE.md` §3.

## ADR-001. Бэкенд бота — Supabase Edge Functions по слоям урока 3

**Статус:** Принято, реализовано S01.

**Контекст.** Курс по Supabase; стек фиксирован уроком `03-supabase-lesson`.

**Решение.** Postgres + Edge Functions (Deno). Слои: `domain/` (чистая логика), `repositories/` (таблицы), `telegram/` (клиент API), `handlers/` (тонкие обработчики). Без DI-контейнеров и абстракций под единственную реализацию. Миграции — `supabase/migrations`.

**Альтернативы.** Отдельный Node-сервер — лишняя инфраструктура для учебного MVP.

**Последствия.** Правила зависимостей между слоями — ADR-008. Доступ к БД из функций через service role; Deno-импорты, `deno.json` в `supabase/functions`.

## ADR-002. Админка — Vite SPA + shadcn/ui + TanStack Router

**Статус:** Принято, реализовано S04 (каркас, вход, справочники) и S05 (заявки, обращения, Realtime) и S06 (чат: список диалогов, лента, непрочитанные), S06b (ручной режим менеджера), S09 (блок «AI-помощник», пометки AI и угроз в чате, голосовые, экран «Статистика AI»). Каталог — `apps/04-05-supabase-lesson/admin/`.

**Контекст.** Админка за логином, SEO не нужно, SSR не нужен. Маршрутизация — TanStack Router (требование владельца), поэтому Next.js 15 с App Router не используем.

**Решение.** Vite + React + TypeScript, shadcn/ui для компонентов, TanStack Router (типобезопасные маршруты, loaders), Redux Toolkit + RTK Query для данных. Каталог `admin/` в корне проекта.

**Альтернативы.** Next.js 15 — свой роутер конфликтует с TanStack Router, SSR не нужен.

**Последствия.** Два пакета в проекте (bot/supabase и admin); общие типы БД генерируются `supabase gen types`.

## ADR-003. Realtime админки — Supabase Realtime (WebSocket)

**Статус:** Принято, реализовано S05 для `booking_requests` и `guest_requests` (канал `requests:<restaurantId>`, `applyRowEvent`, `setAuth` после refresh); `conversations` (на уровне `_authed`) и `messages` (маршрутная подписка) — S06. Уточнения: `DELETE`-события RLS не фильтруются (приходят всем подписчикам, только с `id`); список пересчитывается на каждом `SUBSCRIBED`; переподключение проверено вручную не полностью (`TESTER.md`).

**Контекст.** Менеджер должен видеть новые заявки, обращения и сообщения без перезагрузки.

**Решение.** Подписки `postgres_changes` на `booking_requests`, `guest_requests`, `messages`. Вливаем событие в кэш RTK Query (`updateQueryData`) — подписка не заменяет запрос, а дополняет его. Подписка живёт в хуке на уровне маршрута и закрывается при уходе. Нужны RLS-политики SELECT для роли менеджера и включённая публикация таблиц в `supabase_realtime`.

**Альтернативы.** Polling — задержка и лишняя нагрузка.

**Последствия.** Тестировать переподключение и дубль события + ответ запроса.

## ADR-004. Ядро бота без AI; AI — подключаемый слой (S09)

**Статус:** Принято (ядро), реализовано S01–S03: `getRestaurantInfo` (S01), `listFaq`, `getFaqAnswer`, `listMenuCategories`, `searchMenu` (без `maxPrice`), `getDishDetails` (S02); `createBookingRequest`, `createGuestRequest`, `notifyManager`, `listMyRequests`, `getMyBooking`, `cancelMyBooking` (S03); `notifyGuestOfBookingDecision` (S05, вызывается из Edge Function `notify-guest`, не из webhook). Валидация полей — внутри сервисов, ошибки — значениями. **AI-слой реализован S09** (ADR-010): провайдер — Gemini; сервисы ядра стали tools агента без изменения сигнатур и ничего не знают про AI.

**Контекст.** Сначала нужны рабочее ядро и админка. MVP-план §5 предполагает AI поверх ограниченного набора функций; RAG и векторная база в первой версии не нужны.

**Решение.** Бизнес-логика живёт в сервисах ядра (`_shared/domain` + `repositories`): `getRestaurantInfo`, `searchMenu`, `getDishDetails`, `createBookingRequest`, `createGuestRequest`. Сейчас их вызывают хендлеры команд и inline-кнопок. Пошаговые сценарии (бронь, обращения) — машина состояний, состояние в `conversations`. Сервисы не знают ни про Telegram, ни про AI: на S09 те же функции описываются как tools для LLM. Принцип прежний: AI понимает и формулирует, код достаёт данные, проверяет поля и сохраняет заявки.

**Альтернативы.** AI с первого спринта — усложняет отладку ядра, добавляет стоимость и недетерминизм.

**Последствия.** Сигнатуры сервисов проектируем сразу пригодными под tool-calling (явные входные типы, валидация внутри). Подбор по пожеланиям и свободный диалог появились в S09 (ADR-010). Первоначальное «RAG не планируется» пересмотрено: база знаний ресторана на векторном поиске — S10 ([спека](../roadmap/sprints/S10-rag-knowledge.md)), `searchKnowledge` подключается как ещё один tool.

## ADR-005. Курсорная пагинация сообщений чата

**Статус:** Принято, реализовано S06 (RPC `get_messages_page`, `domain/cursor.ts`, кэш с `merge`/`serializeQueryArgs`). Уточнение: сравнение меток времени — только через `compareTimestamptz` (дробь до 6 знаков, смещение в UTC); Postgres отбрасывает хвостовые нули дроби, строки сравнивать нельзя.

**Решение.** Курсор — пара `(created_at, id)`, порядок `created_at desc, id desc`, страница фиксированного размера, ответ содержит `nextCursor | null`. Не offset: новые сообщения не сдвигают страницы. На клиенте — RTK Query infinite-подход (`merge` + `serializeQueryArgs` без курсора) + `IntersectionObserver` для подгрузки вверх. Новые сообщения по Realtime добавляются в начало кэша.

**Альтернативы.** Offset-пагинация — дубли и пропуски при живом потоке.

**Последствия.** Составной индекс `messages (conversation_id, created_at desc, id desc)` (S01). Тест: на границе страницы с одинаковым `created_at` нет дублей и пропусков.

## ADR-006. Идемпотентность заявок

**Статус:** Принято, реализовано S01 (дедупликация апдейтов по `update_id`) и S03 (ключ идемпотентности заявок `booking:/guest:<conversationId>:<draftId>`, атомарный сброс состояния сценария, отмена одним условным `UPDATE`).

**Решение.** Входящие апдейты дедуплицируются по `update_id` (уникальный ключ); заявка создаётся только после явного подтверждения гостя; повтор обработки сообщения не создаёт дубль (уникальный ключ идемпотентности на заявке).

## ADR-007. CI/CD

**Статус:** Принято, реализовано S08: `.github/workflows/guest-bot.yml` — `checks` (слои, `deno check`/`lint`, typecheck/lint/build админки) и `integration` (`supabase start` в раннере, все тесты бота и админки на чистой БД) на PR и push в `main`; `deploy` (`db push`, `functions deploy --use-api`, smoke) и `deploy-admin` (GitHub Pages через OIDC) только из `main`. Уточнения: отдельного prod-проекта нет, деплой в `myrest-guest-bot-dev`; админка на GitHub Pages, а не Cloudflare (CSP тегом `<meta>`); в Secrets только токен и пароль Supabase, секреты функций и Vault заводятся руками; откат — `git revert` + push.

**Решение.** GitHub Actions: на PR — typecheck, lint, build админки, тесты, `deno check`/тесты функций; на main — `supabase db push`, `supabase functions deploy`, деплой админки. Секреты — в GitHub Secrets.

## ADR-008. Чистая архитектура: правило зависимостей

**Статус:** Принято, действует с S01. Проверка — `pnpm check:layers` (бот), `pnpm check:layers:admin` (админка, S04); слой `_shared/llm` и его проверка — с S09.

**Контекст.** Ядро бота переживёт смену канала (Telegram → другой) и появление AI (S09); админка — смену способа получения данных. Для этого бизнес-логика не должна знать ни про Telegram, ни про Supabase, ни про UI. ADR-001 задаёт слои, этот ADR фиксирует правило зависимостей между ними.

**Решение.** Зависимости направлены только внутрь, нарушать нельзя.

Бот (`supabase/functions`):

| Слой | Каталог | Может импортировать | Не может |
|---|---|---|---|
| Домен | `_shared/domain`, `_shared/types.ts` | только себя и типы | БД, Telegram, сервисы, обработчики |
| Данные | `_shared/repositories` | типы, Supabase-клиент | сервисы, Telegram, обработчики |
| Сценарии ядра | `_shared/services` | домен, репозитории, типы | Telegram, обработчики |
| Клиент канала | `_shared/telegram` | себя | любые слои приложения |
| Клиент LLM (S09) | `_shared/llm` | себя; SDK `@google/genai` — только здесь | любые слои приложения |
| Представление | `telegram-webhook` (router, handlers) | сервисы, домен, клиент Telegram, тексты и клавиатуры | репозитории напрямую |

- `_shared/llm` подключают только сервисы AI (`_shared/services/ai`); `domain` и `telegram-webhook` его не импортируют (исключение — тесты и `testing/`, им нужен фейк). Наружу — только свои типы (`LlmMessage`, `LlmToolCall`, `LlmToolSchema`), типы SDK не выходят. Проверяет `check:layers` (S09).
- Сервис — единственная точка входа в данные для обработчиков (и для будущих tools LLM, ADR-004). Сервис принимает `SupabaseClient` параметром лишь затем, чтобы передать его репозиториям; других обращений к SDK у него нет.
- Тексты и клавиатуры (`content.ts`) — слой представления, в домен не попадают. Форматирование данных в строку для гостя — чистые функции домена без знания о Telegram.
- Без DI-контейнеров и интерфейсов «про запас»: порт/интерфейс вводится, когда появляется вторая реализация (ADR-001).

Админка (`admin/`, с S04):
- `routes` (TanStack Router) → `features/*` (компоненты, хуки) → `api` (RTK Query, единственное место обращения к Supabase) → Supabase-клиент.
- Компоненты не вызывают Supabase напрямую и не знают про Realtime-канал: подписку инкапсулирует хук поверх `api`.
- Чистая логика (курсор, форматирование, валидация) — в `domain/` без React и Supabase.

**Проверка.** Бот: `scripts/check-layers.sh` (`pnpm check:layers`) ищет запрещённые импорты; в CI — на каждом PR (S08). Для админки аналогичная проверка добавлена в S04 (`admin/scripts/check-layers.sh`). Ревью обязано проверять правило и там, где скрипт не достаёт.

**Альтернативы.** Без формального правила — граница размывается при первом «быстром» вызове репозитория из обработчика.

**Последствия.** Новая функциональность = домен/сервис + тонкий обработчик. Обработчик не содержит бизнес-логики: разбор апдейта, вызов сервиса, ответ. Юнит-тесты пишутся на домен и сервисы, без Telegram и сети.

## ADR-009. Размещение текстов бота

**Статус:** Принято, действует с S02. Исключение с S09 (ADR-010): текст ответа AI-агента генерирует модель; системные реплики (приветствие AI-помощника, запасной ответ, отказы по голосу, подписи кнопок под ответом) по-прежнему в `content.ts`.

**Контекст.** Тексты, которые видит гость, оказались в двух местах: `_shared/content.ts` и доменные форматтеры (`formatRestaurantInfo.ts`, `formatDishCard.ts`). Это следствие ADR-008: домен не может импортировать слой представления.

**Решение.**
- Реплики бота, подсказки, пустые состояния и подписи кнопок — только в `_shared/content.ts`. В обработчиках и сервисах строковых литералов для гостя нет.
- Подписи полей данных, которые форматирует чистая функция домена («Адрес», «Состав», «КБЖУ на порцию», `NO_DATA`, предупреждение про аллергию), остаются в домене рядом с форматтером: «отсутствие данных» и предупреждения — часть инварианта «не выдумывать», а не оформление.
- Единый словарь `strings.<язык>`, передаваемый в форматтеры аргументом, вводится при появлении второго языка, не раньше.
- Тексты для логов и ошибок разработчика (`console.error`, `throw new Error`) гостю не показываются и правилу не подчиняются.

**Альтернативы.** Словарь `strings.ru` уже сейчас — единый источник, но усложняет сигнатуры форматтеров без второго языка. Тексты в БД с правкой из админки — избыточно для MVP.

**Последствия.** При смене языка или тона править два места (`content.ts` и форматтеры домена). Новые тексты S03 (сводка брони, уведомление менеджеру) — в `content.ts`; форматирование сводки как данных — в домене.

## ADR-010. AI-слой: Gemini, агент поверх сервисов ядра

**Статус:** Принято, реализовано S09.

**Контекст.** После ядра на кнопках (ADR-004) бот становится AI-first: гость пишет или говорит как привык, бот отвечает про меню и аллергены, оформляет бронь и обращение диалогом. Нужно не сломать инварианты ядра: «не выдумывать», аллергены только детерминированно, запись в БД — через сервисы с валидацией и по кнопке гостя.

**Решение.**
- **Провайдер — Gemini**, SDK `@google/genai`, метод `generateContent` без хранения у Google: историю держим сами (`messages`), каждый вызов передаёт окно (`history_window`). Модель и ключ — секреты `GEMINI_MODEL`, `GEMINI_API_KEY`: смена модели без деплоя. SDK изолирован в `_shared/llm` (ADR-008).
- **Агент поверх сервисов ядра:** `runAgentTurn` (`_shared/services/ai`) — до 5 раундов tools, таймауты 20 с на вызов и 45 с на ход. Tools на чтение — существующие сервисы ядра + детерминированный `filterMenuByAllergens`; tools на запись — только черновики (`draftBooking`, `draftGuestRequest`) в тот же `conversations.state`, что у кнопок, теми же валидаторами. Заявку создаёт кнопка гостя на карточке. Единственная запись по решению модели — `flagThreat` (пометка менеджеру, ничего не делает от имени гостя).
- **Ответ — обязательный tool `reply({ text, actions })`**: кнопки под ответом — до 3 из фиксированного набора существующих callback'ов, подписи из `content.ts`.
- **Маршрутизация без LLM, где можно:** кнопка, команда, проверка шага сценария — код; агенту — только то, что коду не подошло. `restaurant_ai_settings.ai_enabled = false` или нет секретов — поведение до S09.
- **Голос** — отдельный вызов Gemini «только расшифруй» (аудио inline, до 60 с), дальше текст идёт обычным путём.
- **Деградация:** ошибка, таймаут, квота, суточный лимит ходов → вежливый ответ и главное меню; гость не видит текста ошибки. Кнопки работают всегда.
- **Учёт расхода** — токены и время хода в `messages.meta`, деньги считает админка по таблице цен с датами действия.
- **Данные гостей** — только на платном тарифе и модели с «Used to improve our products: No».

**Альтернативы.** Свой отдельный черновик у агента — два источника правды для одной брони. Создание заявки самим агентом — prompt injection превращается в действие от имени гостя. Аудио прямо в ход агента — расшифровка нужна и вне агента (кнопка менеджера). Кэш контекста и семантический кэш — выгода сомнительна при коротких сессиях, риск устаревших данных (стоп-лист).

**Последствия.** Сервисы ядра не изменились; новая возможность агента = новый tool поверх сервиса (так подключится `searchKnowledge` в S10). Качество ответов модели автотестами не ловится — агент в тестах на фейковом LLM, реальная модель проверяется эталонными фразами (`pnpm eval:ai`) вручную. Текст ответа агента — исключение из ADR-009.
