# Гостевой AI-бот ресторана — начальный план MVP

## 1. Цель и границы

Гостевой AI-бот для одного ресторана, который отвечает по меню и информации о заведении, принимает заявки на бронь и передаёт обращения менеджеру.

В рамках курса данные и сценарии реализуются на Supabase. My-Rest не является обязательной зависимостью первой версии. Сначала данные блюд вводятся вручную, затем добавляется импорт гостевых карточек.

Один канал общения — используемый в рамках курса. Подключение нескольких каналов не входит в первую версию.

## 2. Сценарии MVP

| Сценарий | Поведение бота | Ограничение |
| --- | --- | --- |
| Информация о ресторане | Адрес, часы работы, контакты, правила посещения | Только заполненные данные |
| Просмотр меню | Категории, блюда, описания, цены | Без заказа и оплаты |
| Вопрос по блюду | Состав, порция, указанные аллергены и КБЖУ | Не придумывать отсутствующие данные |
| Подбор блюда | Подбор по пожеланиям гостя и бюджету | Только опубликованные характеристики |
| Заявка на бронь | Сбор даты, времени, числа гостей, имени и контакта | Не автоматическое подтверждение столика |
| Обратная связь | Отзыв или жалоба | Передача менеджеру без обещаний решения |
| Связь с менеджером | Вопрос и контакт для ответа | Асинхронная заявка, не live-chat |

## 3. Пользовательские потоки

### 3.1. Вопросы о меню

1. Гость задаёт вопрос.
2. Бот находит блюдо.
3. При неоднозначности уточняет выбор.
4. Получает карточку из Supabase.
5. Отвечает по сохранённым данным.

Если КБЖУ или другие сведения отсутствуют, бот сообщает об этом. Отсутствие аллергена в карточке не является основанием обещать безопасность блюда при аллергии. При неполных данных бот предлагает уточнить у персонала.

### 3.2. Заявка на бронь

1. Собрать дату, время, число гостей, имя, контакт и необязательный комментарий.
2. Показать сводку.
3. Получить подтверждение отправки от гостя.
4. Создать заявку со статусом `pending`.
5. Уведомить менеджера.
6. Менеджер подтверждает или отклоняет заявку.

Сообщение гостю после отправки:

> Заявка передана ресторану. Бронь пока не подтверждена — ожидайте ответа менеджера.

В первой версии менеджер отвечает гостю вне бота: звонком или сообщением по указанному контакту. Автоматическая отправка решения — отдельное последующее улучшение.

### 3.3. Обратная связь и связь с менеджером

1. Определить тип обращения.
2. Собрать текст и контакт, если нужен ответ.
3. Получить подтверждение отправки.
4. Сохранить обращение.
5. Уведомить менеджера.

Единый механизм с типами `feedback`, `complaint`, `manager_request`.

## 4. Данные в Supabase

| Таблица | Назначение |
| --- | --- |
| `restaurants` | Название, описание, адрес, контакты, часовой пояс, часы работы |
| `faq_entries` | Проверенные ответы о парковке, детях, животных, правилах брони и других вопросах |
| `menu_categories` | Категории меню и порядок отображения |
| `menu_items` | Гостевые карточки блюд |
| `conversations` | Диалоги и идентификатор пользователя в выбранном канале |
| `messages` | Сообщения диалога |
| `booking_requests` | Заявки на бронь |
| `guest_requests` | Отзывы, жалобы, запросы менеджеру |

Добавлять `restaurant_id` к данным ресторана с самого начала. Подписки, сети ресторанов и сложное управление организациями пока не разрабатывать.

### 4.1. Карточка блюда: `menu_items`

```text
id
restaurant_id
category_id
external_id             — связь с My-Rest в будущем
name
description
price
currency
photo_url
ingredients             — опубликованный состав
allergens               — указанные аллергены
portion_grams
kcal_per_portion
protein_per_portion
fat_per_portion
carbs_per_portion
is_published
is_available
source                  — manual / my_rest
source_updated_at
updated_at
```

Правила:

- КБЖУ в первой версии указываются на порцию.
- Неизвестные значения хранятся как `null`, не как ноль.
- `is_published` определяет видимость блюда в меню.
- `is_available` определяет текущую доступность блюда.
- Доступность обновляется вручную; интеграция с кассовым стоп-листом не входит в MVP.

### 4.2. Статусы заявок

Бронь:

```text
pending → confirmed / declined / cancelled
```

Обращения:

```text
new → in_progress → resolved
```

Подтверждение гостем отправки заявки и подтверждение брони рестораном — разные события.

## 5. Логика бота

Ограниченный набор функций вместо произвольного доступа модели ко всем таблицам:

```ts
getRestaurantInfo()
searchMenu({ query, category, maxPrice })
getDishDetails({ dishId })
createBookingRequest({ ... })
createGuestRequest({ ... })
```

Разделение ответственности:

- AI понимает вопрос, уточняет недостающие данные и формулирует ответ.
- Код получает данные, проверяет поля и сохраняет заявки.
- Заявки создаются после подтверждения гостя.
- Себестоимость, закупки и внутренние техкарты недоступны гостевому боту.

В первой версии не закладывать отдельную векторную базу и сложный поиск по документам. Начать со структурированного меню и небольшого FAQ.

## 6. Минимальный интерфейс менеджера

1. Редактирование информации о ресторане и FAQ.
2. Добавление и редактирование блюд.
3. Изменение доступности блюда.
4. Просмотр заявок на бронь и изменение их статуса.
5. Просмотр обращений и изменение их статуса.

На первых учебных итерациях данные можно вводить через Supabase Dashboard. Отдельный интерфейс реализуется после работающих сценариев бота.

## 7. Порядок реализации

### Этап 1. Данные и каркас

- [ ] Создать проект Supabase и таблицы.
- [ ] Заполнить ресторан, FAQ и 5–10 блюд.
- [ ] Подключить один выбранный канал общения.
- [ ] Сохранять диалоги и сообщения.
- [ ] Ограничить бота тематикой ресторана.

Результат: гость пишет боту, получает ответ; диалог сохраняется в базе.

### Этап 2. Информация и меню

- [ ] Реализовать получение информации о ресторане.
- [ ] Добавить поиск блюда и просмотр категорий.
- [ ] Добавить ответы по составу, порции и КБЖУ.
- [ ] Обработать отсутствие данных и неоднозначные названия.
- [ ] Добавить простой подбор блюда по пожеланиям.

Результат: работает информационный сценарий без создания заявок.

### Этап 3. Бронь и обращения

- [ ] Реализовать пошаговый сбор данных.
- [ ] Проверять обязательные поля.
- [ ] Показывать сводку перед отправкой.
- [ ] Сохранять заявку после подтверждения гостя.
- [ ] Уведомлять менеджера в одном выбранном канале.
- [ ] Защитить создание заявок от дубликатов при повторной обработке сообщения.

Результат: бот передаёт ресторану конкретные запросы гостей.

### Этап 4. Управление и тесты

- [ ] Сделать минимальный интерфейс менеджера.
- [ ] Проверить работу статусов и доступности блюд.
- [ ] Прогнать тестовые диалоги.
- [ ] Исправить ситуации, где бот обещает больше, чем система умеет.

Результат: ресторан поддерживает данные и обрабатывает заявки без участия разработчика.

### Этап 5. Интеграция с My-Rest

- [ ] Зафиксировать формат гостевой карточки.
- [ ] Сделать экспорт JSON из My-Rest.
- [ ] Добавить импорт в Supabase.
- [ ] Обновлять блюда по `restaurant_id + external_id`.
- [ ] Определить поля, обновляемые импортом, и поля, управляемые локально.

Например, импорт обновляет состав и КБЖУ, но не сбрасывает локальный стоп-лист. Автоматическая синхронизация — после рабочего ручного импорта.

## 8. Граница интеграции с My-Rest

```text
My-Rest
  ↓ экспорт гостевых карточек JSON
  ↓ ручной импорт / обновление меню
Supabase
  ├── меню и информация о ресторане
  ├── заявки на бронь
  ├── обращения
  └── диалоги
  ↓
Гостевой бот
```

My-Rest готовит разрешённые для публикации данные о блюдах. Supabase хранит гостевое представление и данные взаимодействий. Полные внутренние техкарты, закупочные цены и себестоимость не передаются боту.

## 9. Вне первой версии

- Бот для сотрудников.
- Заказы, доставка и оплата.
- Автоматическое распределение столиков.
- Интеграция с кассой и складом.
- Расчёт КБЖУ силами AI.
- Полноценный live-chat.
- Несколько каналов общения.
- Подписки и сложная мультитенантная админка.

## 10. Критерии готовности

- [ ] Бот находит блюдо и сообщает цену.
- [ ] Уточняет выбор, если подходят несколько блюд.
- [ ] Не выдумывает КБЖУ, состав или аллергены.
- [ ] Не рекомендует недоступное блюдо как доступное.
- [ ] Собирает заявку на бронь и сохраняет её после подтверждения гостя.
- [ ] Не называет заявку подтверждённой бронью.
- [ ] Принимает жалобу и запрос менеджеру.
- [ ] Менеджер видит заявки и меняет их статус.
- [ ] Повторная обработка сообщения не создаёт дубликат заявки.
- [ ] В ответах гостю отсутствуют внутренние данные ресторана.

## 11. Первый практический шаг

Создать схему Supabase и тестовое наполнение: один ресторан, несколько FAQ и 5–10 карточек блюд. My-Rest подключать после прохождения основных сценариев на этих данных.
