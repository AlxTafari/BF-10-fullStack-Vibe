# S03 — Бронь и обращения

После спринта гость пошагово оставляет заявку на бронь или обращение (отзыв, жалоба, вопрос менеджеру), видит сводку, подтверждает кнопкой — и заявка сохраняется со статусом `pending` / `new`, а менеджер получает уведомление в Telegram. Повторное нажатие или повторная доставка дубля не создаёт. AI нет (ADR-004).

## 1. Цель и границы

- **Входит:** машина состояний диалога (состояние в `conversations.state`), сценарий брони (дата → период → час → гости → имя → контакт → комментарий → сводка → подтверждение), сценарий обращения (тип → текст → контакт → сводка → подтверждение), отмена в любой момент, истечение брошенного сценария, идемпотентное создание заявок (ADR-006), уведомление менеджера, сервисы ядра `createBookingRequest` и `createGuestRequest` (ADR-004).
- **Не входит:** просмотр и смена статусов заявок (S05), ответ менеджера гостю из бота (роадмап §2), проверка брони по структурированным часам работы и занятости столов (часы — свободный текст, столов в модели нет), отмена гостем уже отправленной заявки, несколько уведомляемых менеджеров, AI-разбор «завтра в восемь на четверых» (S09).

## 2. Что делаем

### 2.А Схема / данные
Таблицы `booking_requests` и `guest_requests` с `idempotency_key unique` есть с S01. Нужна одна миграция:

- Куда слать уведомления: колонка `restaurants.manager_chat_id bigint` (null = уведомления выключены; ресторан-ориентированно, как `restaurant_id` везде; в S04 правится из админки). См. вопрос 1.
- `manager_notified_at timestamptz` в обеих таблицах заявок: null после создания, ставится после успешной отправки уведомления. Сбой уведомления не теряет заявку и виден в БД/админке.
- Seed: `manager_chat_id` не коммитим (личный id) — выставляется вручную в dev-проекте, шаг описать в README проекта.

Форма `conversations.state` (jsonb, `{}` = нет активного сценария):
```jsonc
{
  "flow": "booking" | "guest_request",
  "step": "date" | "time" | "guests" | "name" | "contact" | "comment" | "confirm" | ...,
  "draftId": "<uuid>",          // создаётся при старте сценария, идёт в idempotency_key и в callback_data кнопок
  "data": { "date": "2026-10-20", "time": "19:00", "guests": 4, ... },
  "touchedAt": "<iso>"          // для истечения брошенного сценария
}
```

### 2.Б Сервер

**Домен** (`_shared/domain`, чистые функции + `deno test`; без БД и Telegram):
- `bookingFlow` / `guestRequestFlow` — машина состояний как функция `advance(state, input) → { state, reply }`, где `input` — текст или нажатая кнопка, `reply` — что показать (ключ экрана + данные, не готовая Telegram-разметка). Телеграм-тексты и клавиатуры — `content.ts` (ADR-008).
- Валидация шагов — отдельные функции, их же вызывает сервис создания заявки (защита не только на входе сценария, но и на записи — сервис станет tool'ом для LLM):
  - дата: из кнопок «Сегодня / Завтра / ближайшие 14 дней», в часовом поясе ресторана; прошедшая и дальше чем через 60 дней — отказ;
  - время — два шага кнопками: период «🍽 Обед» (12:00–16:00) / «🌙 Ужин» (17:00–22:00), затем кнопки часов выбранного периода (каждый час). Границы периодов — константы в домене. Для сегодняшней даты часы не раньше «сейчас + 30 мин» (параметр, не магическое число); если в периоде не осталось часов — период не показывается, а если не осталось обоих — «На сегодня запись закрыта, выберите другую дату». Текстовый ввод времени не принимается: на шаге времени свободный текст → подсказка нажать кнопку;
  - гости: целое 1–20; больше 20 → «для больших компаний свяжитесь с менеджером» + кнопка перехода в сценарий обращения;
  - имя: 2–60 символов после trim; контакт: телефон (10–15 цифр после очистки `+ ( ) - пробелов`) или `@username` (5–32 символа); кнопка «Использовать мой @username» показывается, только если он есть в апдейте;
  - комментарий: до 500 символов, кнопка «Пропустить»; текст обращения: 1–2000 символов.
- `zonedDateTimeToUtc(date, time, timeZone)` — перевод локальных даты и времени ресторана в `timestamptz`. Без зависимостей: через `Intl.DateTimeFormat`. Тесты на летний/зимний переход (Europe/Athens, последние воскресенья марта и октября) и на несуществующее/двойное время.
- `buildBookingSummary` / `buildGuestRequestSummary` — текст сводки (чистый форматтер).

**Репозитории:**
- `bookingRequestsRepo.insertIdempotent(row)` → `{ request, created: boolean }`: `insert … on conflict (idempotency_key) do nothing` (в supabase-js — `upsert` с `ignoreDuplicates`), при конфликте — читает существующую строку. `created` отличает «создали» от «уже была».
- `guestRequestsRepo.insertIdempotent(row)` — то же.
- `conversationsRepo.setState(conversationId, state)` и `clearState`.
- `restaurantsRepo` — чтение `manager_chat_id`; наружу гостю не отдаётся (`getRestaurantInfo` уже работает по явному списку полей).

**Сервисы** (`_shared/services`):
- `createBookingRequest(client, input)` — валидирует (доменные функции), считает `booking_at`, ключ `booking:<conversationId>:<draftId>`, `insertIdempotent`. Возвращает `{ request, created }`.
- `createGuestRequest(client, input)` — то же, ключ `guest:<conversationId>:<draftId>`; для `manager_request` контакт обязателен, для `feedback`/`complaint` — нет.
- `notifyManager(client, tg?, request)` — формирует текст и шлёт в `manager_chat_id`; ставит `manager_notified_at`. Вызывается **только если `created === true`**. Ошибка отправки логируется и не пробрасывается (заявка уже сохранена).
- `getFlowState` / `saveFlowState` / `cancelFlow` — тонкая обёртка над `conversationsRepo`; истёкшее состояние (`touchedAt` старше `FLOW_TTL = 30 мин`) возвращается как «нет сценария».
- Сигнатуры: явные входные типы, ошибки валидации — значения (`{ ok: false, errors }`), не исключения.

**Обработчики и роутер** — порядок обработки апдейта:
1. `registerUpdate` (как сейчас).
2. `/start` и `/cancel` → сброс состояния → главное меню.
3. Кнопки главного меню (`menu:*`) → сброс активного сценария; «📅 Забронировать» и «💬 Связаться с менеджером» запускают свой сценарий.
4. Кнопки сценария (`flow:<draftId>:<действие>`): `draftId` не совпал с `state.draftId` → «Эта заявка уже неактуальна» + главное меню (старые сводки в чате остаются кликабельными).
5. Свободный текст: есть живой сценарий → шаг сценария; иначе → поиск блюда (S02).
- Кнопки на каждом шаге: «✖️ Отмена». На сводке: «✅ Отправить», «🔄 Начать заново», «✖️ Отмена».
- После подтверждения: `createXRequest` → очистить состояние → ответ гостю → уведомление менеджера. Порядок важен: если вставка упала, состояние **не** очищено, гость нажимает «Отправить» ещё раз и получает ту же заявку (идемпотентность). Обработчик ловит ошибку и отвечает «Не удалось отправить, нажмите ещё раз».
- Тексты после отправки (не обещаем лишнего, MVP-план §3.2):
  - бронь: «Заявка передана ресторану. Бронь пока не подтверждена — ожидайте ответа менеджера.»
  - обращение: «Обращение передано менеджеру.» — без сроков и обещаний решения.
- Уведомление менеджеру: тип, все поля, ссылка/упоминание контакта гостя, время создания, `id` заявки.

### 2.В Экран
Экрана админки нет (заявки видны менеджеру в Supabase Dashboard и в уведомлении; админка — S05). Диалог в Telegram:

```
📅 Забронировать → [Сегодня][Завтра][…] → [Обед][Ужин] → [19:00]… → гостей «4» → имя → контакт
   → комментарий / «Пропустить» → сводка → [✅ Отправить] → «Заявка передана… не подтверждена»
💬 Связаться с менеджером → [Отзыв][Жалоба][Вопрос менеджеру] → текст → контакт (обязателен для «Вопроса»)
   → сводка → [✅ Отправить]
```

## 3. Инварианты, которые этот спринт обязан удержать

- **Заявка создаётся только после явного подтверждения гостя** (ADR-006): ни один шаг, кроме «✅ Отправить», не вызывает `createXRequest`.
- **Повторная обработка не создаёт дубль.** Двойной тап по «Отправить» — это два *разных* `update_id`, дедупликация по `update_id` его не ловит. Спасает только `idempotency_key` на заявке. Менеджер получает ровно одно уведомление: шлём, только если `created = true`.
- **Заявка на бронь ≠ подтверждённая бронь.** Ни в одном тексте гостю нет слов «забронировано», «столик ваш», «подтверждено». Статус при создании — `pending`.
- Внутренние данные (`manager_chat_id`, `id` заявок других гостей, статусы, чужие диалоги) гостю не показываются; сводка содержит только то, что гость сам ввёл.
- Время брони хранится в UTC, показывается и разбирается в часовом поясе ресторана.
- Неизвестное значение — `null`, не пустая строка (комментарий «Пропустить» → `null`).
- Слои по ADR-008: сценарная логика — домен/сервисы, обработчик только разбирает апдейт, зовёт сервис и отвечает. `pnpm check:layers` зелёный.
- **ADR-006 и расхождение из STATE §3:** апдейт помечается обработанным *до* обработки. Для заявок это не страшно именно из-за ретрая гостем + `idempotency_key`; в спринте это проверяется и фиксируется в STATE при закрытии (оставляем как есть или меняем порядок — решение в LOG).

## 4. Открытые вопросы объёма

Вопрос без ответа блокирует связанную задачу — ответ даётся первой записью `QA.md` сессии.

1. **Куда слать уведомление менеджеру: колонка `restaurants.manager_chat_id` или секрет окружения?** Рекомендация: колонка — правится из админки (S04), ресторан-ориентированно. Секрет проще, но тянет за собой передеплой. Блокирует: миграцию. Оговорка: менеджер должен сам нажать `/start` у бота, иначе Telegram не даст боту написать первым.
2. ~~Выбор времени: текст или кнопки?~~ **Решено:** кнопки — период «Обед / Ужин», затем часы каждый час. Границы периодов (12–16 / 17–22) подогнаны под часы Лавраки; при смене ресторана — константы или данные (S04). Время «не на целый час» (19:30) через бота не заказать — гость уточняет в комментарии.
3. **Проверять бронь по часам работы?** Рекомендация: нет (часы — строка, см. комментарий в схеме). Бронь в 04:00 принимается, менеджер отклонит. Альтернатива — структурные часы, это миграция и правка админки.
4. **Нужен ли шаг «Нужен ли ответ?» в обращениях `feedback`/`complaint`?** Рекомендация: да, контакт опционален; для `manager_request` контакт обязателен.
5. **Тест идемпотентности: как проверять?** Сервисы принимают `SupabaseClient`, фейковый клиент громоздкий. Рекомендация: интеграционный `deno test` против dev-проекта (создаёт заявку, повторяет, проверяет `created`, удаляет свои строки; без `SUPABASE_URL` — пропускается). Альтернатива — только SQL-проверка вручную на приёмке (слабее, DoD требует тест на дедупликацию).

## 5. Что показываем на приёмке

Менеджер должен предварительно написать боту `/start` и иметь выставленный `manager_chat_id` (см. README).

1. «📅 Забронировать стол» → выбрать дату → «Ужин» → `19:00` → `4` → имя → `@username` кнопкой → «Пропустить» комментарий → сводка со всеми полями.
2. «✅ Отправить» → гость видит «Заявка передана ресторану. Бронь пока не подтверждена…». В `booking_requests` одна строка `pending`, `booking_at` в UTC соответствует локальному времени ресторана. Менеджеру пришло уведомление; `manager_notified_at` заполнен.
3. **Дубль:** открыть сводку, быстро нажать «Отправить» дважды; потом нажать «Отправить» в старой сводке уже после отправки → в БД по-прежнему одна заявка, одно уведомление, гость видит «Эта заявка уже неактуальна» / ту же подтверждение, но не вторую запись.
4. Ввод мусора: свободный текст на шаге времени (бот просит нажать кнопку), гостей `0` / `100`, имя из одного символа, контакт «абв» → бот объясняет, что не так, и остаётся на том же шаге. Дата в прошлом недоступна.
5. «✖️ Отмена» на любом шаге и `/cancel` → главное меню, `conversations.state = {}`, заявка не создана. Нажатие кнопки главного меню посреди сценария сбрасывает его.
6. Начать бронь, не дописать, вернуться после 30+ минут и написать «привет» → бот не принимает «привет» за имя, а предлагает меню (проще проверить, подвинув `touchedAt` в БД).
7. «💬 Связаться с менеджером» → «Жалоба» → текст → контакт пропустить → сводка → отправить → строка `guest_requests` со статусом `new`, `kind = complaint`, `contact = null`. Менеджеру пришло уведомление. «Вопрос менеджеру» без контакта не отправить.
8. Отправить заявку при пустом `manager_chat_id` → заявка в БД есть, гость видит успех, `manager_notified_at = null`, в логах функции запись об этом.
9. Свободный текст вне сценария по-прежнему ищет блюдо (S02), а внутри сценария — отвечает на шаг.
10. `deno test` (домен + интеграционный тест идемпотентности), `deno check`, `pnpm check:layers` — чисто.
