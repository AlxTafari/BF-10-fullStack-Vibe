# S06c — Ретеншн сообщений и антиспам бота

После спринта БД не копит шум: нажатия кнопок и поисковые запросы гостей живут 7 дней, остальная переписка — 90 дней, а брони, обращения и диалоги, к которым они привязаны, не удаляются никогда. Бот не принимает от одного гостя больше 3 сообщений за 30 секунд и не принимает сообщения длиннее 500 символов — лишнее не попадает ни в обработку, ни в БД.

Стартует **после приёмки S06** (S06 на финише; `messages.kind`, триггер `messages_after_insert` и `unread_count` из S06 — основа этого спринта).

## 1. Цель и границы

- **Входит:**
  - Миграция: `messages.kind` получает значение `'search'`; таблица `rate_limits`; RPC `check_rate_limit`; функция `purge_old_data()` и расписание `pg_cron`.
  - Бот: проверка лимита частоты и длины на входе (до записи в БД и до маршрутизации); запись `kind = 'search'` для запросов поиска блюда и для ответов бота на них.
  - Админка: сообщения `kind = 'search'` показываются приглушённо (§2.В).
  - Лестница сроков хранения (§2.А) и защита данных, к которым привязаны заявки.
- **Не входит:**
  - Бан/блокировка гостя, капча, ручной список «в чёрный список» — при реальном спаме отдельный спринт (хвост).
  - Ретеншн самих заявок (`booking_requests`, `guest_requests`): они **не удаляются**, это журнал бизнес-событий.
  - Персонализированные сроки по ресторанам (константы в одной функции; настройка из админки — хвост).
  - Rate limit на уровне IP / Telegram `update`-потока: Telegram сам шлёт апдейты только от своих серверов, лимит по `external_user_id` достаточен.
  - Ответы менеджера (S06b): если появятся `sender`/статусы доставки, ретеншн их не учитывает до решения в S06b.

## 2. Что делаем

### 2.А Схема / данные

Одна миграция `…_retention_antispam.sql`.

**Новый тип сообщения.** Поисковый запрос гостя отличается от осмысленного текста, но сейчас это невидимо: `kind in ('text', 'button')`.

```sql
alter table messages drop constraint messages_kind_check;
alter table messages add constraint messages_kind_check check (kind in ('text', 'button', 'search'));
```

(Имя констрейнта сверить с БД.) Тип `search` получают **и входящее** сообщение гостя (запрос блюда), **и исходящий** ответ бота на него (карточки, «ничего не найдено»). Исторические строки не переписываются: старые поиски остаются `text` и живут по 90-дневному правилу — задним числом их не распознать.

Влияние на S06 без правки его кода:
- триггер `messages_after_insert` двигает превью и направление **только для `kind = 'text'`** (S06 §2.А) → поиск превью не подменяет, `last_message_at` двигает;
- непрочитанное = входящее `kind = 'text'` → поиск гостя **не считается непрочитанным** (решено, вопрос 4: ему не нужно привлекать внимание менеджера).

**Лестница хранения.** Сроки — константы в одном месте (`purge_old_data()`), чтобы менять одной правкой:

| Что | Срок | Условие |
|---|---|---|
| `messages` с `kind in ('button', 'search')` | 7 дней | всегда |
| `messages` с `kind = 'text'` | 90 дней | всегда |
| `processed_updates` | 7 дней | всегда |
| `rate_limits` | 1 день | всегда |
| `conversations` | при `last_message_at` старше 90 дней и **без** заявок | диалог без сообщений и без привязанных `booking_requests` / `guest_requests` |

Ключевое правило: **диалог с заявкой не удаляется никогда**, даже когда все его сообщения вычищены. Причина — `booking_requests.conversation_id` и `guest_requests.conversation_id` имеют `on delete set null`; удаление диалога молча оборвало бы связку «заявка → диалог» (S06: кнопка «Открыть диалог» пропала бы, а заявка осталась «сиротой»). Диалог с вычищенной перепиской открывается как «Переписка удалена по сроку хранения» (§2.В). Сообщения диалога с заявкой чистятся по общей лестнице — хранить их вечно мы не обещали, вечны только заявки и связка.

**Функция очистки.**

```
purge_old_data() returns table (purged_messages int, purged_conversations int, ...)
```

- `security definer`, `set search_path = ''`, `revoke all … from public, authenticated, anon`; выполняет только владелец и `pg_cron`.
- **Пачками:** `delete … where ctid in (select ctid … limit 5000)` в цикле до исчерпания; единый огромный `delete` держит блокировки и раздувает WAL. Цикл ограничен (например, 100 пачек за запуск): остаток доберёт следующий запуск.
- Удаление `messages` идёт по `created_at` и использует существующий индекс там, где он применим; если на проде план выбирает полный скан — добавить индекс `messages (created_at)` (вопрос 6).
- Удаление диалогов — после сообщений, в той же функции: `delete from conversations c where c.last_message_at < now() - interval '90 days' and not exists (select 1 from messages m where m.conversation_id = c.id) and not exists (… booking_requests …) and not exists (… guest_requests …)`. Каскад `messages.conversation_id … on delete cascade` не страшен: сообщений к этому моменту нет.
- Возвращает счётчики; их пишет в журнал `cron.job_run_details` (вывод `raise notice`) — **без текста сообщений** (инвариант 7).

**Расписание.** `pg_cron` (расширение включается миграцией, `create extension if not exists pg_cron`): `select cron.schedule('purge-old-data', '17 3 * * *', 'select public.purge_old_data()')` — раз в сутки в 03:17 UTC, не на круглой минуте. Миграция идемпотентна (`cron.unschedule` перед `schedule`, если задание существует). Вопрос 1 — доступность `pg_cron` на тарифе проекта.

**Антиспам-таблица.**

```sql
create table rate_limits (
    external_user_id bigint primary key,
    window_start     timestamptz not null,
    hits             int not null,
    warned           boolean not null default false
);
alter table rate_limits enable row level security;  -- политик нет: только service_role бота
```

Ключ — `external_user_id` (Telegram id гостя), не `conversation_id`: диалога у нового гостя ещё может не быть на момент проверки, а лимит должен работать с первого сообщения.

**RPC `check_rate_limit(p_external_user_id bigint, p_max int, p_window_seconds int)`** — `security definer`, `search_path = ''`, права только `service_role`. Возвращает `allowed` / `warn` / `drop`:

```sql
insert into rate_limits (external_user_id, window_start, hits)
values (p_external_user_id, now(), 1)
on conflict (external_user_id) do update set
    window_start = case when rate_limits.window_start < now() - make_interval(secs => p_window_seconds)
                        then now() else rate_limits.window_start end,
    hits   = case when rate_limits.window_start < now() - make_interval(secs => p_window_seconds)
                  then 1 else rate_limits.hits + 1 end,
    warned = case when rate_limits.window_start < now() - make_interval(secs => p_window_seconds)
                  then false else rate_limits.warned end
returning …
```

- Окно **фиксированное**, не скользящее: проще, один `upsert`, одна строка на гостя. Цена — на стыке окон гость может отправить до 6 сообщений подряд; для защиты от спама достаточно (вопрос 5).
- Решение: `hits <= p_max` → `allowed`; `hits > p_max` и не `warned` → `warn` (и `warned = true` той же операцией); `hits > p_max` и `warned` → `drop`. Всё в одном SQL-операторе → атомарно при параллельных апдейтах (двойной тап).
- Параметры `p_max = 3`, `p_window_seconds = 30` приходят из кода бота — **константы в `domain/`**, а не магические числа в SQL.

### 2.Б Сервер

**Бот** (`pnpm check:layers`, `deno test`, `deno check` зелёные; правило слоёв ADR-008 соблюдается: решение «пропустить / предупредить / отбросить» — чистая функция в `domain/`, вызов RPC — в `repositories/`, оркестрация — в `services/`).

1. **Константы** в `_shared/domain/antispam.ts`: `RATE_LIMIT_MAX = 3`, `RATE_LIMIT_WINDOW_SECONDS = 30`, `MAX_GUEST_TEXT_LENGTH = 500`. Чистые функции:
   - `isTooLong(text)` — по **символам Unicode** (`[...text].length`), не по `.length` (эмодзи — суррогатная пара: «500» не должно превратиться в «250 эмодзи»);
   - `classifyGuestInput(text, flowState)` → `'search' | 'flow' | 'command'` — определяет ветку **до** записи (§2.Б.3).
2. **Порядок проверок в `routeUpdate`:** `registerUpdate` (идемпотентность, ADR-006) → `check_rate_limit` → длина → `buildContext` → маршрутизация. Лимит стоит **до** `buildContext`: отброшенный апдейт не должен создавать диалог и не должен писать ничего в БД, кроме `rate_limits`.
   - `drop` → `return`, ничего не пишем и не отвечаем;
   - `warn` → `tg.sendMessage(chatId, «Слишком много сообщений. Подождите немного.»)` **без** записи в `messages` (ответ-предупреждение — не часть диалога по существу) и без `answerCallbackQuery`-ошибки; для нажатия кнопки `answerCallbackQuery` вызывается всё равно (иначе у кнопки в клиенте крутятся «часики»);
   - `allowed` → продолжаем.
3. **Лимит и нажатия кнопок.** Лимит считает и сообщения, и `callback_query` (иначе спам кнопками обходит ограничение). Но шаги брони — это легитимные быстрые нажатия: 3 нажатия за 30 секунд на проходе «дата → время → гости» — нормальный сценарий. Поэтому **нажатия внутри живого сценария брони не засчитываются** (проверяется по `flow:`-префиксу и `getFlowState`), а нажатия меню и свободный текст — засчитываются (вопрос 3).
4. **Длина.** `isTooLong(text)` → бот отвечает «Сообщение слишком длинное (максимум 500 символов)», текст **не пишется в `messages`** и не передаётся в сценарий/поиск. Это стоит **после** лимита (длинное сообщение тоже расходует попытку). В тексте ответа нет цитаты сообщения гостя (инвариант 7).
5. **Запись `kind = 'search'`.** Сейчас `logIncoming` вызывается в `handleMessage` до маршрутизации. Меняем порядок: маршрут (`/start`, `/cancel`, живой сценарий, иначе поиск) определяется **до** записи, и запись получает правильный `kind`:
   - `/start`, `/cancel`, текст внутри сценария (имя, число гостей) → `'text'`;
   - свободный текст, ушедший в `handleSearch` → `'search'`;
   - нажатия → `'button'` (без изменений).
   Ответы бота на поиск (`reply()` из `handleSearch`) получают `kind = 'search'`: `reply(ctx, text, keyboard, kind)` — необязательный параметр, по умолчанию `'text'`. Перебор «ответ бота после поиска» ограничен веткой `handleSearch`; нажатия по карточке блюда после поиска остаются `button`.
6. **Деградация при сбое RPC.** Если `check_rate_limit` упал (БД недоступна) — **пропускаем** апдейт (`fail open`): антиспам не должен ронять бота; ошибка идёт в `console.error` без текста сообщения. Иначе сбой счётчика остановит бронирование.

Edge Functions не добавляются; миграция раньше деплоя бота (колонка/значение `search` с `check` совместимо со старым ботом: он `search` не пишет).

### 2.В Админка

Малая правка поверх S06:

- **Лента.** `classifyMessage` (`domain/messages.ts`) получает третий вариант `'search'`. Сообщение гостя с поиском — пузырь слева **приглушённого вида** (серый фон/текст ниже контраста, мелкая подпись «Поиск по меню»); ответ бота на поиск — пузырь справа в том же приглушённом стиле. В отличие от нажатий кнопок (строка без пузыря), текст поиска **показывается**: менеджеру интересно, чего ищут (решение пользователя 2026-10-18). Сообщения по-прежнему только текст, `white-space: pre-wrap`, без автоссылок (инвариант 7 S06).
- **Список диалогов.** Превью и непрочитанные не меняются: триггер S06 пишет превью только для `kind = 'text'`, поэтому поиск превью не подменяет и не считается непрочитанным.
- **Диалог с вычищенной перепиской.** Лента пуста, но диалог есть (потому что к нему привязана заявка): показывается «Переписка удалена по сроку хранения (>90 дней)» вместо «Начало переписки»; панель «Заявки гостя» работает как обычно.
- **Диалог без сообщений** удаляется ретеншном, но может остаться открытым во вкладке: запрос возвращает «Диалог не найден» (экран из S06), а не ошибку.
- Realtime: удаление строк `messages` ретеншном порождает события `DELETE`; подписка на `messages` слушает только `INSERT` (S06) — события игнорируются, лента не мигает. Открытая лента может показывать уже удалённое сообщение до перезагрузки — это допустимо (вопрос 7).

## 3. Инварианты, которые этот спринт обязан удержать

1. **Заявки не теряются.** Ретеншн не удаляет `booking_requests`, `guest_requests` и диалог, к которому привязана хотя бы одна заявка; `conversation_id` заявки после очистки остаётся не `null`.
2. **Ретеншн по лестнице, не больше.** Удаляется только то, что старше срока своего типа: сообщение `text` младше 90 дней и `button`/`search` младше 7 дней **не удаляется** (тест на границе: 6 дней 23 ч — остаётся, 7 дней 1 мин — уходит).
3. **Очистка не блокирует работу.** Удаление идёт пачками, ограниченным числом пачек за запуск; одновременная запись бота и чтение админки не ждут долгую блокировку.
4. **Лимит атомарен.** Параллельные апдейты одного гостя (двойной тап) не обходят лимит: счётчик растёт одним SQL-оператором; в окне ровно `p_max` сообщений проходят, дальше — нет.
5. **Предупреждение — один раз за окно.** Гость, продолжающий спамить после превышения, получает ровно одно «слишком часто» за окно; дальнейшие апдейты молча отбрасываются. Новое окно сбрасывает счётчик и флаг.
6. **Отброшенное не попадает в БД.** Превышение лимита и слишком длинный текст ничего не пишут в `messages` и не создают диалог (в `rate_limits` запись есть — это счётчик, не данные гостя).
7. **Личные данные не утекают в логи.** Текст сообщений не пишется в `console`, `cron.job_run_details`, ответ «слишком длинное» и «слишком часто» не цитируют текст гостя.
8. **Длина — в символах Unicode**, не в UTF-16-единицах и не в байтах; сообщение из 500 эмодзи проходит, 501 — нет.
9. **Антиспам не ломает бронь.** Нажатия внутри живого сценария брони не упираются в лимит; сбой `check_rate_limit` не останавливает бота (fail open).
10. **Идемпотентность не ухудшена.** Повторная доставка одного `update_id` по-прежнему отбрасывается до проверки лимита и **не** увеличивает счётчик.
11. **Слои ADR-008** и проверки `check:layers`, `check:layers:admin` зелёные; `deno test`, `deno check`, `typecheck`, `lint`, `build` — чисто.
12. **Поиск виден, но не шумит.** `kind = 'search'` не двигает превью и не увеличивает непрочитанные (инварианты S06 о `unread_count` и превью удержаны).

## 4. Открытые вопросы объёма

Вопрос без ответа блокирует связанную задачу — ответ даётся первой записью `QA.md` сессии.

1. **`pg_cron` на проекте.** Доступно ли расширение на тарифе/в локальной dev-БД? Если нет — запасной путь: Edge Function `purge` по расписанию (Supabase Cron/`pg_net` или внешний планировщик) с тем же SQL. Блокирует: расписание.
2. **Сроки 7 / 90 дней.** Решено 2026-10-18: кнопки и поиск — 7 дней, текст — 90, `processed_updates` — 7, `rate_limits` — 1; заявки — бессрочно. Блокирует: ничего (константы).
3. **Нажатия в сценарии брони вне лимита.** Рекомендация: не засчитывать (§2.Б.3). Альтернатива — считать всё и поднять лимит для нажатий отдельно (`кнопки 10/30 с`). Блокирует: проверку лимита в `router.ts`.
4. **Поиск и непрочитанные.** Решено: поиск гостя непрочитанным не считается (иначе любой поиск блюда будит менеджера). Блокирует: ничего.
5. **Окно: фиксированное или скользящее.** Рекомендация — фиксированное (одна строка на гостя, один `upsert`); скользящее точнее, но требует журнала меток. Блокирует: `check_rate_limit`.
6. **Индекс `messages (created_at)` под очистку.** Нужен ли — решается замером `explain` на демо-объёме (~250 строк слишком мало: проверять на сгенерированных ~100 тыс.). Блокирует: ничего.
7. **Удаление, пока лента открыта.** Принимаем, что открытая лента может показать уже удалённое до перезагрузки; события `DELETE` не слушаем. Блокирует: ничего.
8. **Сообщения диалогов с заявками.** Сейчас чистятся по общей лестнице (хранятся вечно только заявки и сама связка). Если менеджеру нужна переписка вокруг брони дольше 90 дней — вынести как «продлённый срок для диалогов с заявками» (хвост).

## 5. Что показываем на приёмке

Предусловие: миграция S06c применена, бот задеплоен после неё; `pnpm db:seed:chat-demo` создал демо-диалог; dev-seed дополнен сообщениями разного возраста (§2.А: нажатия и поиск старше 7 дней, текст старше 90 дней, диалог с заявкой и диалог без заявки). Живые шаги — с отдельным Telegram-аккаунтом гостя.

**Антиспам**
1. Гость быстро шлёт «а», «б», «в» → все три обработаны. Четвёртое сообщение в течение 30 секунд → бот отвечает «Слишком много сообщений…». Пятое, шестое → тишина.
2. Через 30 секунд гость пишет снова → бот отвечает как обычно; снова превысил → снова ровно одно предупреждение.
3. Гость присылает текст на 501 символ → бот отвечает «слишком длинное», в `messages` этой строки нет. Ровно 500 символов → проходит. 500 эмодзи → проходит.
4. Гость проходит бронь кнопками подряд (дата → время → гости → подтвердить) → лимит не срабатывает, бронь создаётся.
5. Двойной тап по кнопке меню → без дублей в `messages`, лимит не нарушен.
6. После шагов 1–3 в `messages`/`conversations` нет записей от отброшенных сообщений; в логах функции нет текста гостя.

**Поиск**
7. Гость пишет «борщ» → бот отвечает карточкой; в админке оба сообщения показаны **приглушённо** (подпись «Поиск по меню»). Превью диалога в списке — прежнее (не «борщ»), счётчика непрочитанных поиск не добавил.
