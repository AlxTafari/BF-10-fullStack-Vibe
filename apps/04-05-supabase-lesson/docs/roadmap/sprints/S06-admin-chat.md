# S06 — Админка: чат гостей

После спринта менеджер видит список диалогов с гостями, открывает любой и читает всю переписку с ботом: старые сообщения подгружаются по мере прокрутки вверх без дублей и пропусков, новые появляются сами, диалоги с непрочитанными входящими отмечены счётчиком. Чат только для чтения — отвечать гостю из админки пока нельзя: ответы менеджера вынесены в следующий спринт S06b (роадмап §2). Менеджер может перейти от заявки к диалогу этого гостя и обратно.

## 1. Цель и границы

- **Входит:**
  - Миграция: политики `select` на `conversations` и `messages`, тип сообщения (`messages.kind`), «последнее сообщение» и общая отметка прочтения в `conversations`, функции курсорной выборки и `mark_conversation_read`, публикация в `supabase_realtime`.
  - Небольшая правка бота: запись типа сообщения, снятие дублирующего обновления диалога (§2.Б).
  - Экран «Чаты»: список диалогов (курсор), лента сообщений (курсор, ADR-005), живые обновления обоих (ADR-003).
  - **Непрочитанные (общие для всех менеджеров ресторана):** счётчик в строке диалога, число диалогов с непрочитанными в навигации и заголовке вкладки, отметка прочтения при просмотре ленты.
  - Связка с заявками: «Открыть диалог» из карточки заявки (S05) и панель «Заявки гостя» в диалоге.
  - Dev-seed длинного диалога с одинаковыми `created_at` для проверки курсора.
- **Не входит:**
  - Ответ гостю из админки и live-chat — спринт S06b (роадмап §2, §3). Персональные (по менеджеру) отметки прочтения: пока менеджер один на ресторан, общая отметка достаточна; при появлении ролей — отдельная таблица (хвост).
  - Поиск по сообщениям и диалогам, фильтры, архивация и удаление диалогов, экспорт.
  - Редактирование и удаление сообщений: журнал неизменяем.
  - Показ вложений, фото, голосовых: бот их не принимает (S01–S03 пишут только текст).
  - Аудит «кто из менеджеров читал диалог» (хвост).
  - Очистка/ретеншн старых сообщений (политика хранения персональных данных — вне MVP; хвост).

## 2. Что делаем

### 2.А Схема / данные

Одна миграция `…_admin_chat.sql`. Нужные таблицы и индекс уже есть с S01: `conversations`, `messages`, `messages_cursor_idx (conversation_id, created_at desc, id desc)`.

**Тип сообщения вместо магической строки.** Бот пишет нажатия кнопок во `messages` как `[кнопка] <callback_data>` (`router.ts`) — отличить их от текста можно только по префиксу в самом тексте. Админке нужна надёжная классификация, поэтому:

```sql
alter table messages
    add column kind text not null default 'text' check (kind in ('text', 'button'));
update messages set kind = 'button' where direction = 'in' and text like '[кнопка] %';
```

Текст в строках не переписывается (история остаётся дословной); новые нажатия бот пишет с `kind = 'button'`. Вопрос 2.

**Последнее сообщение в диалоге.** Для списка нужны превью и порядок «кто писал последним». Хранить это — денормализация: `conversations.last_message_at` уже есть, добавляем:

```sql
alter table conversations
    add column last_message_preview   text,
    add column last_message_direction text check (last_message_direction in ('in', 'out'));
```

Обновляет их **триггер** `messages_after_insert` (`after insert on messages`): `last_message_at = new.created_at` всегда; превью (`left(new.text, 120)`) и направление — только для `kind = 'text'` (нажатие кнопки двигает диалог вверх списка, но не подменяет превью строкой `[кнопка] menu:booking`). Триггер — потому что вставка сообщения и обновление диалога становятся **одной атомарной операцией**: сейчас бот делает это двумя запросами (`recordMessage`: вставка, затем `touchConversation`), и сбой между ними оставляет диалог со старым `last_message_at`. Миграция заполняет колонки для существующих диалогов (`update … from lateral (последнее сообщение)`). Вопрос 1.

**Непрочитанные — общая отметка.** Одна колонка вместо отдельного счётчика:

```sql
alter table conversations add column manager_last_read_at timestamptz;
update conversations set manager_last_read_at = last_message_at;  -- история на момент миграции считается прочитанной
```

- Непрочитанное = входящее (`direction = 'in'`), текстовое (`kind = 'text'`; нажатия кнопок гость «не писал») сообщение с `created_at > manager_last_read_at`. Исходящие сообщения бота непрочитанными не бывают. `manager_last_read_at is null` (диалог создан после миграции и ещё не открывался) — непрочитано всё входящее.
- Счётчика-колонки (`unread_count`) нет сознательно: число, которое увеличивает триггер и обнуляет RPC, может разойтись с реальными сообщениями (вторая точка правды). Число считает `list_conversations_page` подзапросом по `messages_cursor_idx` с потолком 100 (`99+` в интерфейсе): точное большое число менеджеру не нужно, а запрос остаётся ограниченным.
- Общая отметка значит: один менеджер открыл диалог — для всех он прочитан. Это принятое упрощение (вопрос 3), пока в ресторане один менеджер.
- **Запись отметки — только через RPC** `mark_conversation_read(p_conversation_id uuid, p_up_to timestamptz)` (`security definer`, `search_path = ''`, права только `authenticated`, внутри проверка `is_manager_of`): `manager_last_read_at = greatest(manager_last_read_at, p_up_to)`. Отметка только растёт (запоздалый вызов от старой вкладки её не откатит); `p_up_to` — `created_at` самого нового сообщения, **которое менеджер реально видел**, а не `now()` (иначе прочитанным станет сообщение, пришедшее между отрисовкой и вызовом). Прямой `update` менеджера на `conversations` политикой по-прежнему закрыт. Вызов идемпотентен.

**Индексы:** `conversations (restaurant_id, last_message_at desc, id desc)` под список. Для сообщений достаточно `messages_cursor_idx`.

**Политики** (`to authenticated`, только `select`):
- `conversations`: `is_manager_of(restaurant_id)` (колонка `manager_last_read_at` читается вместе со строкой; менять её можно только через RPC).
- `messages`: `exists (select 1 from conversations c where c.id = messages.conversation_id and is_manager_of(c.restaurant_id))`. У `messages` нет `restaurant_id`, поэтому доступ выводится через диалог. Подзапрос идёт по первичному ключу — дёшево.
- Запись, изменение, удаление — ни для кого из клиентов. `processed_updates` по-прежнему закрыта.

**Realtime:** `alter publication supabase_realtime add table conversations, messages;`.

**Функции выборки.** Обе — `security invoker` (RLS применяется как к прямому запросу), `stable`.

```
get_messages_page(p_conversation_id uuid, p_before_created_at timestamptz,
                  p_before_id uuid, p_limit int) returns setof messages
list_conversations_page(p_before_at timestamptz, p_before_id uuid, p_limit int)
                  returns table (id, display_name, channel, created_at,
                                 last_message_at, last_message_preview, last_message_direction,
                                 manager_last_read_at, unread_count)
count_unread_conversations() returns int   -- число диалогов с непрочитанным, для навигации и вкладки
mark_conversation_read(p_conversation_id uuid, p_up_to timestamptz) returns void
```

- `get_messages_page`: `where conversation_id = p_conversation_id and (p_before_created_at is null or (created_at, id) < (p_before_created_at, p_before_id)) order by created_at desc, id desc limit p_limit`. Сравнение пары (row comparison) с одинаковым направлением сортировки обоих столбцов использует `messages_cursor_idx` напрямую.
- `list_conversations_page`: то же по `(last_message_at, id)`; диалоги без сообщений (`last_message_at is null`) не показываются. Возвращает **узкий набор колонок**: `state`, `chat_id`, `external_user_id` в список не отдаются. `unread_count` — `least(count, 100)` по правилу выше. `count_unread_conversations` — `security invoker`, считает диалоги ресторана менеджера, где есть непрочитанное (`exists`, без подсчёта всех сообщений).
- **Почему RPC, а не PostgREST-фильтр `.or('created_at.lt.X,and(created_at.eq.X,id.lt.Y)')`:** (1) фильтр собирается строкой в URL, где `+` в `+00:00` без экранирования читается как пробел и курсор молча ломается; (2) RPC принимает `timestamptz` в JSON-теле и сохраняет микросекунды без промежуточного разбора. Это не стиль, а профилактика дублей/пропусков (инвариант 1).
- Клиент запрашивает `p_limit = pageSize + 1`; получил `pageSize + 1` строк — значит есть следующая страница: лишняя отбрасывается, курсор берётся из **последней оставшейся** строки. Получил ≤ `pageSize` — `nextCursor = null`. (Иначе при количестве сообщений, кратном размеру страницы, последняя «следующая» страница пустая и обработчик «конец» срабатывает не там.)

**Dev-seed длинного диалога** `supabase/dev-chat-seed.sql` (не входит в основной `seed.sql`, запускается по требованию `pnpm db:seed:chat-demo`; откат — `pnpm db:clean:chat-demo`): диалог с вымышленным `external_user_id` (отрицательный, заведомо не реальный Telegram id), ~250 сообщений с **явными `created_at`**, сгруппированными по 5 с одинаковой меткой (в одной вставке `now()` у всех строк одно и то же, поэтому явные метки нужны, чтобы получить разные ничьи), чередование `in`/`out`, несколько `kind = 'button'`, сообщения с длинным текстом, переводами строк, эмодзи и HTML-подобной строкой. Без этого проверить границу страницы на ничьих `created_at` нечем.

### 2.Б Сервер

**Бот** (малая правка, не новый функционал; `pnpm check:layers` и `deno test` зелёные):
1. `logIncoming(ctx, text, kind)` и `messagesRepo.logMessage({ …, kind })` — нажатие кнопки пишется с `kind = 'button'`, остальное — `'text'`. Тексты по-прежнему `[кнопка] …` (история и формат не меняются).
2. `recordMessage` больше не вызывает `touchConversation` — `last_message_at` ведёт триггер (одна точка правды; иначе значение перезаписывается вторым, чуть более поздним временем из JS и расходится с `messages.created_at`). `touchConversation` удаляется вместе с комментарием.
3. `setConversationState` продолжает обновлять `conversations.state`; это порождает `UPDATE`-события диалога без смены последнего сообщения — админка их игнорирует (§2.В).

Edge Functions не добавляются. Реальный порядок деплоя: сначала миграция (колонка `kind` с `default 'text'` совместима со старым ботом), затем деплой бота; в обратном порядке бот пишет в несуществующую колонку.

### 2.В Админка

Слои — как в S04/S05 (ADR-008). Новое в `domain/`: `cursor.ts`, `messages.ts`, `chatTime.ts`.

#### API (`api/`)

- `getConversationsPage({ cursor })`, `getMessagesPage({ conversationId, cursor })` — вызовы RPC (§2.А); `getConversation(id)` (одна строка для шапки; нужна, если пришли по прямой ссылке и диалога нет в загруженной странице списка); `markConversationRead({ conversationId, upTo })` (RPC) и `getUnreadConversationsCount()` (RPC); `getGuestRequests({ conversationId })` для панели (bookings + guest_requests диалога, последние 10 каждых — политики из S05 уже есть).
- **Кэш RTK Query — плоский список + курсор (ADR-005):** `serializeQueryArgs` без курсора (ключ — `conversationId`), `merge` дописывает страницу в конец и отбрасывает дубли, `forceRefetch` срабатывает при смене курсора. Формат записи кэша: `{ rows: Message[] /* новые → старые */, nextCursor: Cursor | null }`. Плоский список выбран, потому что события Realtime вставляются в произвольное место списка (§Realtime) — с «страницами внутри кэша» это пришлось бы пересчитывать по границам. Если в установленной версии RTK есть встроенный `infiniteQuery`, а плоский `merge` оказывается хуже, ADR-005 обновляется при закрытии спринта (вопрос 5).

#### Курсор и порядок (`domain/cursor.ts`) — сердце спринта

- Курсор — **пара строк** `{ at: string, id: string }`, взятая **дословно** из последней строки ответа. `at` никогда не проходит через `Date` и обратно: JS-`Date` режет микросекунды до миллисекунд, Postgres хранит микросекунды, и «скруглённый» курсор даёт пропуск или повтор сообщений на границе страницы.
- Сравнение двух меток времени (`compareTimestamptz(a, b)`) нужно кэшу (вставка события в нужное место, слияние страниц) и не имеет права разваливаться на форматах: PostgREST отдаёт `2026-10-13T10:00:00.123456+00:00`, Realtime может отдать другое число знаков дробной части или `Z`. Функция разбирает строку на целые секунды (через `Date.parse` без дроби), дробную часть дополняет нулями до 6 знаков и сравнивает числами; с учётом смещения. **Первая запись LOG спринта** — сверка форматов на живых данных (вопрос 6): реальные payload'ы Realtime и ответ RPC для одной и той же строки.
- Порядок везде один: `created_at desc, id desc` (диалоги: `last_message_at desc, id desc`); `id` — только арбитр при равных метках, смысла в нём нет.
- `mergePage(existing, page)`: дедуп по `id`, итог отсортирован по общему порядку, `nextCursor` = курсор **более глубокой** из двух границ (после слияния страницы курсор остаётся у самого старого сообщения; повторный запрос той же страницы курсор не откатывает).

#### Экран «Чаты» (`/chats`, `/chats/$conversationId`)

- **Раскладка.** Десктоп: список слева (≈ 320px), лента справа. Узкий экран (< 768px): `/chats` — список, `/chats/$conversationId` — только лента с кнопкой «← Диалоги». Выбор диалога — это навигация по URL (ссылка, «назад», перезагрузка работают); `$conversationId` проходит проверку на UUID, иначе экран «Диалог не найден».
- **Список.** Строка: имя гостя (`display_name`, иначе «Гость» + 4 символа id), превью с префиксом «Гость:» / «Бот:» по `last_message_direction`, время последнего сообщения (сегодня — часы:минуты, иначе дата; **в поясе ресторана**). При `unread_count > 0` — бейдж с числом (`99+`) и полужирное имя; у активного диалога бейдж не показывается, пока лента внизу. Порядок — по `last_message_at ↓`. Страница — 30, догрузка по `IntersectionObserver` у конца списка («Загрузить ещё» как запасная кнопка, если наблюдатель недоступен). Активный диалог подсвечен. Пустое состояние: «Пока никто не писал боту».
- **Лента.** Сообщения в хронологическом порядке сверху вниз; данные в кэше — «новые → старые», на экран выводятся развёрнутыми. Первая загрузка — последние 30, лента прокручена вниз. При прокрутке к верхнему краю подгружается следующая страница (30); индикатор загрузки сверху; конец — «Начало переписки». Требования к поведению (способ — на усмотрение реализации, например `flex-direction: column-reverse` или ручная коррекция `scrollTop`):
  - при подгрузке старых сообщений содержимое **не прыгает**: то, что гость читал, остаётся на месте;
  - при приходе нового сообщения лента прилипает к низу, **только если** пользователь уже внизу; иначе остаётся на месте и показывается кнопка «↓ Новые сообщения (N)», по клику — прокрутка вниз и сброс счётчика;
  - смена диалога сбрасывает прокрутку (вниз) и счётчик новых.
- **Сообщение.** Входящее (гость) — слева, исходящее (бот) — справа; время `HH:MM` в поясе ресторана; разделители по дням («Сегодня», «Вчера», «13 октября») — день вычисляется в поясе ресторана (сообщение в 23:50 и в 00:10 — разные дни, и граница дня на DST-переходе не должна давать «25 часов»). Текст — `white-space: pre-wrap` (боты пишут многострочно), перенос длинных слов. **Только текст, без разметки и без превращения в ссылки.**
- **Нажатия кнопок** (`kind = 'button'`): не пузырь, а приглушённая строка «Нажата кнопка» с сырым `callback_data` в подсказке (`title`) — менеджеру интересно «что гость нажимал», но не интересно читать `flow:3f2a…:date:2026-10-20`. Подряд идущие нажатия не склеиваются (вопрос 7).
- **Шапка ленты:** имя гостя, канал («Telegram»), «диалог начат <дата>». Кнопок ответа и поля ввода **нет**; под лентой подпись «Менеджер отвечает гостю вне бота» (роадмап §2), чтобы отсутствие поля ввода не выглядело поломкой.
- **Панель «Заявки гостя»** (справа на широком экране, сворачиваемая секция на узком): брони и обращения диалога — тип, время, статус бейджем, ссылка на карточку (`/bookings/$id`, `/requests/$id`); пусто — «Заявок нет». Источник — запросы по `conversation_id`.
- **Когда диалог считается прочитанным.** Вызов `markConversationRead` с `upTo` = `created_at` самого нового *входящего* сообщения в кэше ленты — только если одновременно: диалог открыт, лента прокручена до низа, вкладка видима (`document.visibilityState`). Моменты вызова: открытие диалога (после первой загрузки), приход нового сообщения при ленте внизу, возврат в низ (в том числе кнопкой «↓ Новые сообщения»), возврат на вкладку. Прокрутка вверх и скрытая вкладка диалог не «прочитывают». Вызовы схлопываются (debounce ≈ 300 мс; повтор с тем же `upTo` не отправляется). Сбой вызова не показывается ошибкой: отметка повторится при следующем моменте, пока что бейдж остаётся.
- **Навигация и вкладка.** Пункт «Чаты» — бейдж с числом диалогов с непрочитанным (`count_unread_conversations`), в заголовке вкладки `(N)` — суммируется с заявками из S05 по тому же механизму.
- **Из заявки в диалог.** В карточках броней и обращений (S05) кнопка «Открыть диалог» → `/chats/$conversationId`, если `conversation_id` не `null` (после удаления диалога он `null` — кнопки нет).

#### Realtime (ADR-003)

Два раздельных источника. Бейдж непрочитанных, как и бейджи заявок в S05, должен работать на любой странице, поэтому подписка на **диалоги** живёт на уровне `_authed`-раскладки, пока менеджер вошёл (одна на ресторан). Подписка на **сообщения** остаётся маршрутной — только пока открыта лента:

1. **Диалоги** — `conversations`, события `*`, фильтр `restaurant_id=eq.<id>`: `INSERT` — новый диалог попадает в начало списка; `UPDATE` — если изменился `last_message_at` (смена превью/порядка), строка обновляется и всплывает вверх; число непрочитанных по событию **не угадывается** (+1 дало бы ложные «непрочитанные» от нажатий кнопок: они двигают `last_message_at`, но не счётчик): `applyConversationEvent` возвращает `needsRefresh`, и api-слой перечитывает первую страницу списка (с debounce ≈ 500 мс). Если изменился `manager_last_read_at` и он ≥ `last_message_at` (другая вкладка или другой менеджер прочитал) — `unread_count = 0`. Источник правды для числа — всегда RPC; по событию локально меняется только то, что событие знает точно (порядок, превью, обнуление при отметке ≥ `last_message_at`). `UPDATE`, в котором не изменились ни `last_message_at`, ни превью, ни `manager_last_read_at` (это `setConversationState` бота при шагах сценария), **игнорируется** — иначе список перерисовывается на каждый шаг брони.
2. **Сообщения открытого диалога** — `messages`, `INSERT`, фильтр `conversation_id=eq.<открытый id>`. Подписка создаётся при открытии диалога и закрывается при смене/закрытии (cleanup эффекта по `conversationId`: одновременно живёт не больше одной подписки на сообщения). Почему не «все сообщения ресторана»: у `messages` нет `restaurant_id`, значит фильтр на уровне Realtime единственный — по диалогу; а подписка на всё заставляла бы Realtime проверять RLS-подзапрос для каждого сообщения каждого гостя.

**Вставка нового сообщения — по порядку, не «в голову» (`applyMessageEvent`, чистая функция в `domain/messages.ts`).** `created_at` по умолчанию — `now()` = время *начала транзакции*; два запроса гостя (двойной тап) могут завершиться в порядке, обратном `created_at`, и более позднее по метке сообщение придёт в Realtime раньше. Поэтому:
- сообщения уже есть в кэше (дубль события, или оно уже попало в ответ запроса) → игнорировать;
- метка попадает в диапазон загруженного (между самым новым и самым старым в кэше) → вставить на своё место по общему порядку;
- метка новее самого нового → в начало списка (обычный случай);
- метка старше самого старого загруженного → **игнорировать** (при прокрутке придёт со страницей и не будет потеряно);
- событие чужого диалога (на случай гонки при переключении) → игнорировать.

**Соединение и пропуски.** Статус каналов выводится индикатором в шапке (общий компонент из S05). При возврате в `SUBSCRIBED` после обрыва:
- список диалогов — перечитывается первая страница и сливается через `mergePage` (серверные `unread_count` заменяют локальные), счётчик диалогов с непрочитанным запрашивается заново;
- открытый диалог — запрашивается свежая первая страница и сливается; **если свежая страница не пересекается с кэшем ни одним `id`** (за время обрыва пришло больше сообщений, чем размер страницы — между свежими и старыми образовалась дыра), кэш диалога заменяется свежей страницей, а более старые сообщения подгрузятся прокруткой снова. Дыры в ленте быть не должно (инвариант 3).
- `TOKEN_REFRESHED` → `realtime.setAuth` (как в S05).

#### Домен (`domain/`, всё с тестами)

`cursor.ts` — `compareTimestamptz`, `nextCursor` (правило «pageSize + 1»), `mergePage`; `messages.ts` — `applyMessageEvent`, `classifyMessage` (по `kind`), `groupByDay(messages, timeZone)`; `chatTime.ts` — подписи времени и дней в поясе ресторана (общий код с `time.ts` из S05, не копия). `applyConversationEvent` — для списка диалогов (включая правило «игнорировать UPDATE без смены превью/порядка/отметки прочтения» и пересчёт `unread_count` по событию); `shouldMarkRead` — чистая функция «пора ли отмечать прочитанным» (открыт, внизу, видима → `upTo` или `null`).

## 3. Инварианты, которые этот спринт обязан удержать

1. **Курсор не теряет и не дублирует.** Обход всех страниц диалога даёт каждое сообщение ровно один раз, в порядке `created_at desc, id desc`, в том числе при одинаковых `created_at` на границе страницы и при микросекундных метках (ADR-005). Курсор — строки из ответа БД, без `Date` в пути.
2. **Страницы не накладываются и не пустеют лишний раз.** Правило `pageSize + 1`: `nextCursor = null` на последней странице даже когда число сообщений кратно размеру страницы.
3. **В ленте нет дыр и дублей** после обрыва связи, двойного события, события раньше/позже ответа запроса и сообщений, пришедших не в порядке `created_at`.
4. **Чат только для чтения.** У `authenticated` нет `insert`/`update`/`delete` на `messages` и `conversations`; поля ввода в интерфейсе нет. Сообщения — журнал. Единственное изменение клиентом — `manager_last_read_at` через RPC `mark_conversation_read`.
5. **Чужие диалоги недоступны.** Менеджер другого ресторана, пользователь без строки `restaurant_managers` и аноним не читают ни `conversations`, ни `messages`, не получают их события Realtime и не могут запросить страницу чужого диалога по подставленному `conversationId` (тест).
6. **Личные данные не утекают в логи и URL.** Текст сообщений не пишется в `console`, не попадает в адрес, `title` вкладки и сообщения об ошибках; в URL только `conversationId`.
7. **Недоверенный текст.** Сообщения гостей — только текст (React-экранирование), без `dangerouslySetInnerHTML` и без автоссылок; HTML-подобные строки показываются буквально.
8. **Время и день — в поясе ресторана**, границы дней не зависят от пояса браузера и корректны на переходе на летнее/зимнее время.
9. **Список не дёргается от служебных событий:** `UPDATE` диалога без смены `last_message_at`/превью не перерисовывает список и не двигает порядок.
10. **Подписки не текут:** одновременно не больше одной подписки на `messages` (открытый диалог) и одной на `conversations` (на время сессии); уход из раздела «Чаты» закрывает подписку на `messages`, выход из системы — обе.
11. **Бот не ухудшен:** запись сообщения и обновление «последнего сообщения» — одна операция (триггер); `deno test`, `check:layers`, ручной прогон главного сценария бота зелёные.
12. **Слои ADR-008** и проверки `check:layers`, `check:layers:admin` зелёные.
13. **Непрочитанные не врут.** Диалог не становится прочитанным, пока менеджер не увидел сообщение (лента не внизу или вкладка скрыта — не отмечается); отметка только растёт; сообщение, пришедшее между отрисовкой и вызовом, остаётся непрочитанным (`upTo` = последнее *виденное*); бот, исходящие и нажатия кнопок счётчик не увеличивают; чужой менеджер не может отметить чужой диалог.

## 4. Открытые вопросы объёма

Вопрос без ответа блокирует связанную задачу — ответ даётся первой записью `QA.md` сессии.

1. **Превью и порядок диалогов: триггер + денормализованные колонки (рекомендация) или RPC с `lateral`-подзапросом «последнее сообщение»?** Триггер требует правки бота (убрать `touchConversation`) и миграции, зато список — один дешёвый запрос по индексу, а `UPDATE` диалога несёт всё нужное Realtime'у. RPC без денормализации бота не трогает, но событие Realtime по `conversations` не содержало бы превью — пришлось бы перечитывать строку при каждом сообщении. Блокирует: миграцию и правку бота.
2. **Колонка `messages.kind` (рекомендация) или разбор префикса `[кнопка]` в админке?** Префикс — договорённость внутри текста: любой будущий текст, начинающийся так, превратится в «нажатие». Цена `kind` — миграция и однострочная правка бота. Блокирует: миграцию.
3. **Непрочитанные диалоги. Решено 2026-10-17: делаем, отметка общая** (`conversations.manager_last_read_at`, запись только через RPC; счётчик считается запросом, не хранится). Персональная отметка (таблица по менеджерам) — когда появятся роли. Ответы менеджера гостю вынесены в S06b (роадмап §2). Блокирует: ничего.
4. **Что видит менеджер в `conversations`.** Политика `select` отдаёт строку целиком, включая `state` (черновик заявки гостя), `chat_id`, `external_user_id`; список этого не использует (узкий RPC), но прямой `select` из консоли вернёт всё. Рекомендация: принять — это данные гостей этого же ресторана, менеджер и так видит имя и контакт в заявках; ограничение колонками (`grant select (…)`) ломает `select *` и неочевидно работает с Realtime. Блокирует: ничего, фиксирует граничное решение.
5. **Кэш ленты: плоский `merge` (по ADR-005, рекомендация) или встроенный `infiniteQuery` RTK?** Перед реализацией — свериться с документацией установленной версии (Context7). Плоский список проще для вставки событий «в нужное место»; `infiniteQuery` хранит страницы с параметрами и требует патчить нужную страницу. Если выберем встроенный — обновить ADR-005 при закрытии. Блокирует: слой `api/` ленты.
6. **Формат `created_at` в Realtime против PostgREST.** Проверяется на живых данных первой записью LOG (см. «Курсор и порядок»). Если форматы расходятся — нормализация живёт в `compareTimestamptz`, а не в вызывающих местах. Блокирует: `domain/cursor.ts`.
7. **Нажатия кнопок: «Нажата кнопка» с сырым `callback_data` в подсказке (рекомендация) или человекочитаемая подпись («Меню → Забронировать»)?** Подписи — словарь соответствия `callback_data` → текст, который придётся поддерживать вместе с ботом; пока он не нужен. Блокирует: ничего.
8. **Размер страницы.** 30 для сообщений и диалогов. Меньше — больше запросов при прокрутке, больше — дольше первая отрисовка и тяжелее `merge`. Блокирует: ничего (константа в `domain/`).
