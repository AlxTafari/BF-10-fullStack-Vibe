# S05 — Админка: заявки и обращения + Realtime

После спринта менеджер видит заявки на бронь и обращения гостей, подтверждает и отклоняет их, и новые заявки появляются на экране сами — без перезагрузки, пока вкладка открыта. Подтверждение «запроса на изменение» атомарно подменяет исходную бронь. Гость и менеджер, одновременно меняющие одну заявку, не затирают друг друга.

## 1. Цель и границы

- **Входит:**
  - Миграция: политики `select` на `booking_requests` и `guest_requests`, функции смены статуса (RPC), публикация таблиц в `supabase_realtime`, колонка `guest_notified_at`, триггер уведомления гостя.
  - Уведомление гостя в Telegram о решении менеджера **по брони** (триггер + `pg_net` → Edge Function `notify-guest`, вопрос 1).
  - Экраны «Брони» и «Обращения»: списки с фильтрами, карточка заявки, смена статуса по матрице переходов.
  - Realtime (ADR-003): подписка на `postgres_changes`, вливание событий в кэш RTK Query, бейджи «ожидают» в навигации, индикатор соединения, догрузка пропущенного после обрыва.
  - Закрытие хвоста STATE §4: «подтверждение изменения и перевод исходной брони в `cancelled` — только вручную в БД».
- **Не входит:**
  - Текстовый ответ менеджера гостю из бота (это чат, S06). Уведомление гостя о смене статуса **обращений** — не делаем (гость видит статус в «📋 Мои заявки»). Вопрос 1.
  - Чат с гостем и переход «заявка → диалог» (S06; поле `conversation_id` уже есть).
  - Создание и редактирование заявок менеджером, удаление заявок (заявки — журнал, `delete` не выдаётся никому).
  - Учёт столов и занятости слотов: менеджер решает вручную (роадмап §2).
  - Курсорная пагинация списков (запрос — `limit 100`, размер страницы в UI 20/50/100, вопрос 4), экспорт, поиск по тексту, системные (push) уведомления браузера. Звук — входит (вопрос 5).
  - Автоматическая отмена просроченных заявок (вопрос 6).
  - Правка бота. Единственное, что бот должен делать корректно «из коробки», — показывать гостю новые статусы; это проверяется на приёмке, не кодом. Сообщение гостю шлёт Edge Function `notify-guest`, не обработчик бота.

## 2. Что делаем

### 2.А Схема / данные

Одна миграция `…_admin_requests.sql`.

**Чтение.** Политики `select` для `authenticated`: `is_manager_of(restaurant_id)` (хелпер из S04) на обеих таблицах. Их же использует Realtime: `postgres_changes` доставляет подписчику только строки, которые он вправе читать по `select`-политике.

**Запись статусов — только через функции, прямого `update` у клиента нет.** Политик `update`/`insert`/`delete` для `authenticated` на заявках **не создаём**. Статус меняется двумя RPC:

```
set_booking_status(p_id uuid, p_from text, p_to text) returns booking_requests
set_guest_request_status(p_id uuid, p_from text, p_to text) returns guest_requests
```

Обе: `security definer`, `set search_path = ''`, вызывающий проверяется внутри (`is_manager_of(restaurant_id)` строки), `execute` выдан только `authenticated`. Почему не прямой `update` с политикой и колоночными грантами: три правила (матрица переходов, условие «статус сейчас = p_from», каскад на изменение) нельзя выразить политикой, а держать их в клиентском коде — значит, что любой клиент с токеном (в том числе консоль браузера) обойдёт их. Функция — единственная дверь. Альтернатива — вопрос 2.

Общий контракт RPC:
- `p_from` — статус, который менеджер видел на экране; `update … where id = p_id and status = p_from`. Если у заявки уже другой статус (гость отменил, второй менеджер нажал раньше) — исключение `status_conflict`, ничего не меняется. Это **оптимистичная блокировка**: решение менеджера принимается только по тому состоянию, на которое он смотрел.
- Строка читается с `for update` (блокировка на время транзакции), чтобы две одновременные смены не разъехались.
- Ошибки — исключения с фиксированным текстом сообщения: `not_manager`, `not_found`, `status_conflict`, `transition_not_allowed`, `booking_in_past`, `original_not_active`. Клиент по тексту выбирает сообщение для менеджера. Значения общие для двух функций; список — константы в `domain/`.

**Матрица переходов брони** (`transition_not_allowed` вне неё):

| Из | В | Примечание |
|---|---|---|
| `pending` | `confirmed` | запрещено, если `booking_at` в прошлом (`booking_in_past`): подтверждать то, что уже прошло, бессмысленно |
| `pending` | `declined` | менеджер отказывает |
| `pending` | `cancelled` | менеджер закрывает без ответа (гость пропал, дубль) |
| `confirmed` | `cancelled` | ресторан не может принять подтверждённую бронь |
| `declined`, `cancelled` | — | финальные |

`confirmed → declined` нет: «отклонить» значит «не принять заявку», у принятой бронь отменяется.

**Каскады внутри `set_booking_status` (одна транзакция):**
1. **Подтверждение запроса на изменение** (`p_to = 'confirmed'`, у строки `replaces_id is not null`): блокируется исходная бронь; если она не в `pending`/`confirmed` — `original_not_active`; иначе исходная становится `cancelled`, а изменение — `confirmed`. Обе записи или ни одной. Новая бронь — полноценная замена: исходная в «Мои заявки» у гостя показывается отменённой, новая — подтверждённой.
2. **Закрытие брони, у которой есть ожидающее изменение** (`p_to` — `declined` или `cancelled`, и существует строка `replaces_id = p_id and status = 'pending'`): изменение тоже становится `cancelled`. Зеркалит то, что бот делает при отмене гостем (S03 §2.Г): у закрытой брони не остаётся «висящего» запроса.
3. Отклонение или отмена **самого запроса на изменение** не трогает исходную бронь — она остаётся в силе (как и в S03).

**Обращения.** Статусы `new → in_progress → resolved`. Матрица свободная: любой переход между разными статусами, включая возврат `resolved → in_progress` («переоткрыть») и `in_progress → new`; переход в тот же статус — `transition_not_allowed`. Условие `status = p_from` и блокировка те же.

**Realtime.** `alter publication supabase_realtime add table booking_requests, guest_requests;`. В payload `UPDATE` приходит `new` целиком — этого достаточно, `replica identity full` не нужен (старое значение мы не используем). `DELETE`-событий нет: удалять заявки нельзя.

**Индексы.** Существующий `(restaurant_id, status, created_at desc)` обслуживает фильтр по статусу. Для списка бронь «предстоящие по времени» — `booking_requests (restaurant_id, booking_at)`. Для обращений достаточно имеющегося.

**Форма данных для клиента** (из `database.types.ts`, перегенерировать `pnpm types:gen`): типы функций `set_booking_status` / `set_guest_request_status` появятся в `Database['public']['Functions']`.

### 2.Б Сервер

Обработчики бота не меняются. Смена статуса — по-прежнему две SQL-функции из §2.А: `supabase.rpc(...)` держит её в одной транзакции БД с блокировкой строки и каскадом. Единственная новая Edge Function — `notify-guest`, и она **не участвует в смене статуса**, только сообщает о ней.

**Уведомление гостя (вопрос 1, вариант A).**
- Триггер `after update of status` на `booking_requests` через `pg_net` вызывает `notify-guest` (секрет в заголовке, как у `telegram-webhook`). Шлёт только при переходах **по решению ресторана**: `pending → confirmed`, `pending → declined`, `pending|confirmed → cancelled`. Подтверждение изменения шлёт одно сообщение (по новой брони), а не два: каскадная отмена исходной брони уведомление не создаёт.
- Отличить решение менеджера от отмены самим гостем: `set_booking_status` перед `update` ставит флаг транзакции `set_config('app.notify_guest', '1', true)`; триггер читает его и без флага молчит. Бот статусы меняет прямым `update` без флага, поэтому отмена гостем уведомления не вызывает.
- `notify-guest` берёт чат гостя через `conversation_id` заявки, шлёт текст с датой/временем и статусом, пишет исходящее в `messages` и ставит `guest_notified_at`. Сбой отправки не откатывает статус; в админке заявка с `guest_notified_at is null` (старше минуты, статус из решённых) получает метку «гость не уведомлён».
- Тексты гостю не обещают лишнего: «Бронь на 20.10 19:00 подтверждена» / «К сожалению, ресторан не может принять заявку…». Они в `content.ts` бота (ADR-009) или в функции — решить в начале сессии кода.

Что не должно сломаться в боте: «Мои заявки» читает статус из БД каждый раз; отмена гостем — условный `UPDATE … WHERE status in (pending, confirmed)`. Гость отменяет, пока менеджер подтверждает, — проигрывает тот, кто пришёл вторым (у менеджера — `status_conflict`, у гостя — «уже неактуально»). Обе стороны идемпотентны.

### 2.В Админка

Слои и правила — как в S04 (ADR-008): `routes → features → api → supabase`, чистая логика в `domain/`.

#### API (`api/`)

- Запросы списков: `getBookings({ tab, when })`, `getGuestRequests({ tab, kind })`, `getBooking(id)`, `getGuestRequest(id)`, `getOpenCounts` (число `pending` броней и `new` обращений — `select count`, `head: true`). Мутации: `setBookingStatus({ id, from, to })`, `setGuestRequestStatus(...)` — через `supabase.rpc`.
- Теги: `BookingList`, `GuestRequestList`, `OpenCounts`, `Booking`/`GuestRequest` по `id`. Мутация статуса **пессимистичная** (ждёт ответа сервера — состязание с гостем возможно, откатывать «успех» хуже, чем подождать полсекунды): по успеху кладёт возвращённую строку в кэш карточки и списков, инвалидирует `OpenCounts`; по `status_conflict` — перечитывает строку и показывает, каким статус стал на самом деле.
- Ошибки RPC приводятся к кодам из §2.А (`error.message`); неизвестный текст — общее «Не удалось сохранить».

#### Экран «Брони» (`/bookings`, карточка — `/bookings/$bookingId`)

Фильтры живут в URL (`?tab=pending&when=upcoming`, схема `validateSearch` на zod, неверное значение → значения по умолчанию).

| Вкладка | Что показывает | Порядок |
|---|---|---|
| **Ожидают** (по умолчанию) | `status = pending`, любая дата | по времени брони ↑; просроченные (время прошло) помечены «время прошло» |
| **Подтверждённые** | `status = confirmed`; переключатель «Предстоящие / Прошедшие» | предстоящие ↑, прошедшие ↓ |
| **Закрытые** | `declined`, `cancelled` | по `updated_at` ↓ |
| **Все** | без фильтра | по времени брони ↓ |

Запрос всегда с `limit 100`. В UI переключатель «Показывать: 20 / 50 / 100», по умолчанию 20; размер в URL (`?size=20`, неверное значение → 20). Это срез на клиенте из загруженных 100 — смена размера нового запроса не делает; Realtime-слияние обрезает кэш до 100, а не до выбранного размера (новая заявка не теряется). Если запрос вернул ровно 100, под списком «Показаны последние 100» (курсорная пагинация — вопрос 4). То же для «Обращений». Время показывается в **часовом поясе ресторана** (`restaurants.timezone` из кэша S04), не браузера: менеджер в другой стране видит ту же «19:00», что и гость.

Строка списка: дата и время брони, имя, число гостей, контакт, статус бейджем, «создана N мин назад», метки: **«изменение»** (`replaces_id`), **«уведомление не доставлено»** (`manager_notified_at is null` и заявке больше минуты — меньше минуты это нормальная задержка отправки; подсказка «менеджер мог не получить сообщение в Telegram — проверьте `manager_chat_id`»).

Карточка (боковая панель `sheet`, адрес в URL — работает «назад» и ссылка из уведомления): все поля заявки, комментарий, контакт как ссылка, статус, история времени (создана / обновлена), кнопки действий. Какие кнопки — **считает функция домена** `allowedBookingActions(booking, now)` по той же матрице (§2.А), чтобы интерфейс не предлагал невозможного; последнее слово всё равно за RPC.
- `pending` → «Подтвердить» (недоступна, если время прошло — подсказка почему), «Отклонить».
- `confirmed` → «Отменить бронь».
- Деструктивные действия («Отклонить», «Отменить») — через `alert-dialog` с названием последствия. «Подтвердить изменение» — тоже с пояснением: «Исходная бронь на 20.10 19:00 будет отменена, её заменит эта».
- **Запрос на изменение** в карточке показывает сравнение «Было → Стало» (дата/время, гости) по исходной брони (`replaces_id`, подгружается отдельным запросом). Карточка исходной брони показывает «Есть ожидающий запрос на изменение» со ссылкой на него.
- Контакт: `@username` → ссылка `https://t.me/username`, телефон → `tel:`. Ссылки строит `contactLink(contact)` в `domain/` по строгим шаблонам (тот же формат, что валидирует бот); всё остальное — простой текст.

**Тексты гостей — недоверенные данные.** Имя, комментарий, текст обращения выводятся только как текст React (экранируется); `dangerouslySetInnerHTML` в админке запрещён. Длинные строки без пробелов не должны ломать вёрстку (`overflow-wrap`).

#### Экран «Обращения» (`/requests`, карточка — `/requests/$requestId`)

Вкладки: **Новые** (по умолчанию, `status = new`), **В работе**, **Решённые**, **Все**; фильтр по типу (Отзыв / Жалоба / Вопрос менеджеру; в URL). Порядок — `created_at ↓`. Строка: тип бейджем, начало текста (до ~120 символов), контакт («контакт не указан» серым), статус, время. Карточка: полный текст, контакт-ссылка, статус, кнопки: «Взять в работу» (`new → in_progress`), «Решено», «Вернуть в работу» (`resolved → in_progress`). Деструктивных переходов здесь нет — без подтверждающих диалогов. Для «Вопроса менеджеру» без контакта ответить нельзя — но бот такого не создаёт (контакт обязателен), поэтому отдельного состояния не заводим.

#### Realtime (ADR-003)

Один канал на сессию менеджера: `requests:<restaurantId>`, две подписки `postgres_changes` (`booking_requests`, `guest_requests`, события `*`, фильтр `restaurant_id=eq.<id>`). Фильтр — вторая линия: основную границу доступа задаёт RLS, фильтр уменьшает трафик.

**Где живёт подписка.** В защищённом layout'е (`/_authed`), а не на странице: бейджи в навигации нужны на любой странице, а подписку на странице пришлось бы пересоздавать при каждом переходе. Хук `useRequestsRealtime(restaurantId)` создаёт канал в эффекте и закрывает в cleanup (выход, смена ресторана, размонтирование — никаких висящих каналов; проверяется на приёмке по числу каналов в `supabase.getChannels()`). Компоненты экранов канал не видят — только читают кэш (ADR-008).

**Вливание события в кэш — чистая функция** `applyRowEvent(rows, event, filter, order)` в `domain/` (юнит-тесты, без React и сети), вызывается из `onChange` внутри `updateQueryData` для каждого закэшированного списка (`api.util.selectCachedArgsForQuery` → список ключей кэша). Правила:
- `INSERT`: строка уже есть (событие и ответ запроса пришли в любом порядке) → оставить более свежую; нет, и строка подходит под фильтр этого списка → вставить на своё место по порядку списка; не подходит → игнорировать.
- `UPDATE`: строка есть и подходит → заменить, **если `updated_at` события не старее имеющейся** (опоздавшее событие не откатывает свежие данные); есть, но больше не подходит под фильтр (статус изменился) → убрать из этого списка; нет в списке, но подходит (например, пришла из «Ожидают» в «Подтверждённые») → вставить.
- Строка вне загруженных 100 → список остаётся корректным по правилу «вставить на своё место, затем обрезать до лимита».
- Любое событие инвалидирует `OpenCounts` (счётчик дешевле перечитать, чем выводить из событий) и карточку `Booking`/`GuestRequest` с тем же `id`, если она открыта.

**Новая заявка заметна.** По `INSERT` (не по `UPDATE`, и не для событий, вызванных собственным действием менеджера — они приходят как `UPDATE`) показывается toast «Новая бронь: Анна, 4 гостя, 20.10 19:00» с кнопкой «Открыть»; бейдж в навигации обновляется; к `document.title` добавляется `(N)` по сумме открытых. Строка, появившаяся по событию, подсвечивается на несколько секунд. Первичная загрузка списка toast'ов не создаёт.

**Звук (вопрос 5).** Кнопка «🔔 Звук» в шапке, по умолчанию выключена; выбор — в `localStorage` (обёрнут в try/catch, без него страница работает). Браузер не разрешает звук до действия пользователя, поэтому клик по кнопке создаёт/возобновляет `AudioContext`, после перезагрузки страницы звук надо включить заново кликом (состояние «включён, но не разблокирован» показывается приглушённой кнопкой). Играет только по `INSERT` новой заявки (бронь или обращение), не по `UPDATE` и не при догрузке после обрыва. Звук — короткий сигнал, синтезируемый `AudioContext` (без файла и зависимости). Системные уведомления браузера не делаем.

**Соединение.** Статус канала (`SUBSCRIBED` / `CHANNEL_ERROR` / `TIMED_OUT` / `CLOSED`) отражается индикатором в шапке: «● онлайн» / «● нет связи, переподключаем…». Во время обрыва события теряются безвозвратно, поэтому **при каждом возврате в `SUBSCRIBED` после обрыва** (не при первом подключении) все списки и счётчики перечитываются (`invalidateTags`). Токен: при обновлении сессии (`TOKEN_REFRESHED`) токен передаётся Realtime (`supabase.realtime.setAuth`) — иначе после часа работы подписка тихо перестанет получать события.

#### Домен (`domain/`, всё с тестами)

`bookingStatus.ts` — матрица переходов, `allowedBookingActions`, `isPastDue`; `guestRequestStatus.ts`; `rpcErrors.ts` — коды ошибок и тексты менеджеру; `realtimeMerge.ts` — `applyRowEvent`; `contactLink.ts`; `time.ts` — форматирование момента в часовом поясе ресторана и «N мин назад» (через `Intl`, без зависимостей). Матрица переходов в `domain/` дублирует SQL осознанно (два рантайма); согласованность держит тест интеграционный (§5).

## 3. Инварианты, которые этот спринт обязан удержать

1. **Статус заявки меняется только через RPC.** У `authenticated` нет `update` на заявки ни политикой, ни грантом; обход через консоль невозможен (тест).
2. **Решение принимается по тому состоянию, которое менеджер видел.** `status = p_from` в `update`; расхождение — `status_conflict`, не молчаливая перезапись. Гость и менеджер не затирают друг друга.
3. **Подтверждение изменения атомарно:** либо исходная отменена *и* изменение подтверждено, либо ничего. Нет состояния «две подтверждённые брони вместо одной».
4. **Закрытая бронь не оставляет висящего изменения** (каскад 2 в §2.А) — зеркало поведения бота (S03).
5. **Подтвердить прошедшее нельзя**; отклонить/отменить можно всегда.
6. **События Realtime не портят кэш:** дубль события, событие раньше/позже ответа запроса, устаревшее событие поверх свежих данных, событие по строке вне списка — каждый случай покрыт тестом `applyRowEvent`.
7. **Потерянное во время обрыва догружается** при возврате соединения.
8. **Границы доступа — RLS.** Менеджер другого ресторана и аноним не читают заявки и не получают события Realtime (тест); `select` на заявки не открывает `conversations`/`messages` — они закрыты до S06.
9. **Время — в поясе ресторана.** Хранение в UTC не менялось; ни одно время не форматируется в поясе браузера.
10. **Данные гостей — недоверенный ввод:** вывод только как текст, ссылки — по строгим шаблонам.
11. **Слои ADR-008** и проверки `check:layers`, `check:layers:admin` зелёные; бот не изменён, его тесты зелёные.
12. **Подписка не течёт:** выход и смена пользователя закрывают канал; повторный вход не создаёт второй канал.
13. **Гость уведомляется только о решении ресторана по брони**, ровно один раз на решение: не при отмене самим гостем, не при каскадной отмене исходной брони, не по обращениям. Сбой Telegram не откатывает статус и виден в `guest_notified_at`.

## 4. Открытые вопросы объёма

Вопрос без ответа блокирует связанную задачу — ответ даётся первой записью `QA.md` сессии.

**Решено 2026-10-14 (старт S05):** 1 — **уведомлять**, вариант A (триггер + `pg_net` → `notify-guest`), только по броням; 2 — RPC; 3 — запрет; 4 — `limit 100` в запросе, 20/50/100 в UI, по умолчанию 20; 5 — **звук делаем** (push браузера — нет); 6 — не закрывать, помечать; 7 — открыт, проверка на dev перед `realtimeMerge`. Рекомендации ниже — исходный текст вопросов, где решение отличается (1, 4, 5), оно главнее.

1. **Уведомлять ли гостя в Telegram о подтверждении/отклонении?** Рекомендация: нет в S05 — роадмап §2 откладывает ответ из бота, а гость видит статус в «📋 Мои заявки». Но это самый частый следующий запрос; цена — архитектурная: RPC живёт в БД и не может писать в Telegram, потребуется Edge Function или триггер + `pg_net`. Решение сейчас определяет, остаётся ли смена статуса чистым RPC. Блокирует: форму RPC.
2. **RPC `security definer` (рекомендация) или политики `update` + колоночный грант на `status`?** Грант проще на вид, но не выражает матрицу, условие `p_from` и каскады; клиент сможет делать «подтверждение» без атомарной замены брони. Блокирует: миграцию.
3. **Запрет подтверждения брони в прошлом.** Рекомендация: да (`booking_in_past`). Альтернатива — разрешить и положиться на менеджера; тогда в «Мои заявки» гость увидит «подтверждена» для уже прошедшей даты. Блокирует: матрицу и текст ошибки.
4. **Пагинация списков.** Рекомендация: лимит 100 с пометкой и фильтрами вкладок (для одного ресторана заявок на вкладке «Ожидают» немного). Курсорная пагинация приходит в S06 (ADR-005) — если окажется нужна здесь, переиспользуем её, а не пишем вторую. Блокирует: ничего, фиксирует границу.
5. **Звук и системные уведомления браузера.** Рекомендация: нет; toast + бейдж + счётчик в заголовке вкладки. Звук требует разрешений и взаимодействия пользователя с страницей; добавим, если менеджеры будут пропускать заявки. Блокирует: ничего.
6. **Просроченные `pending` (время брони прошло, менеджер молчал).** Рекомендация: не закрывать автоматически; во вкладке «Ожидают» они помечены «время прошло», менеджер закрывает вручную («Отменить»/«Отклонить»). Автоотмена — cron/Edge Function, лишняя движущаяся часть. Блокирует: ничего.
7. **Realtime: `postgres_changes` с RLS (ADR-003) — подтвердить на dev-проекте до написания UI.** Первой записью LOG сессии: подписка менеджера получает события своего ресторана и не получает события посторонних; формат полей (`updated_at`, `booking_at`) в payload совпадает с ответом PostgREST. Если формат расходится — `time.ts` и `applyRowEvent` нормализуют его. Блокирует: `realtimeMerge`.

**Состязание с гостем**
9. Открыть карточку брони `pending` в админке (не нажимая). Гость в боте отменяет эту бронь. Менеджер нажимает «Подтвердить» → сообщение «Статус уже изменён: отменена», карточка обновилась, бронь **не** стала `confirmed`.
10. Обратное: менеджер подтвердил, гость нажимает «Отменить» в уже открытой карточке → отмена проходит (подтверждённую гость вправе отменить), в админке статус сам стал `cancelled`.

**Изменение брони**
11. Гость запрашивает изменение (дата/час/гости) → в админке появилась строка с меткой «изменение»; карточка показывает «Было → Стало»; у исходной брони — «Есть ожидающий запрос на изменение».

13. Другая пара: гость запрашивает изменение, менеджер **отклоняет** изменение → исходная бронь остаётся в силе. Третья пара: гость запрашивает изменение, менеджер **отменяет исходную** → изменение автоматически `cancelled`.
