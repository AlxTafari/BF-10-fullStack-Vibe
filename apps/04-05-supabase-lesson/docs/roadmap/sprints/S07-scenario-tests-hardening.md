# S07 — Тесты сценариев и hardening

После спринта каждый критерий готовности MVP (план §10, кроме AI-пунктов) подтверждён автотестом, который гонит
настоящий апдейт Telegram через роутер бота до dev-БД и проверяет, что увидел гость. Бот не обещает того, чего
система не делает. Нажатия кнопок получают широкий лимит частоты. Интеграционные тесты админки не мешают друг
другу. Ручная приёмка S05, отложенная в `TESTER.md`, пройдена.

Стартует после закрытия S06d. S06b (ответы менеджера) остаётся по сигналу и в этот спринт не входит.

## 1. Цель и границы

- **Входит:**
  - Сценарные интеграционные тесты бота: `routeUpdate` + подменный Telegram-клиент + dev-БД (§2.Б.1). Матрица
    «критерий §10 → тест» (§2.Б.2). Они же закрывают хвост «тесты сервисов S02».
  - Проверка «внутренних данных» в ответах гостю: общий набор запретных шаблонов на все исходящие тексты всех
    сценариев (§2.Б.3).
  - Аудит обещаний бота: тексты `content.ts` и `domain/guestNotification.ts` (§2.Б.4).
  - Лимит частоты на нажатия кнопок (миграция + бот, §2.А, §2.Б.5).
  - Админка: интеграционные тесты идут последовательно (§2.В.1); тесты вливания Realtime-событий в кэш, если
    логику удаётся вынести в чистые функции (§2.В.2, вопрос 6).
  - Ручная приёмка отложенных шагов S05 по `TESTER.md` (8а, 11–17) — часть приёмки этого спринта (§5).
- **Не входит:**
  - CI, секреты в CI, отдельная БД или `supabase start` для тестов — S08.
  - AI-пункты §10 и всё про свободный текст как диалог — S09.
  - Ответы менеджера из админки — S06b.
  - Тесты UI-компонентов админки (React Testing Library) — не планируются в ядре; приёмка ручная.
  - `editMessageText` по сообщению старше суток — остаётся наблюдением (fallback на новое сообщение есть, STATE §4).
  - Страховка удаления предупреждения антиспама через `pg_cron` — хвост, пока не было случаев.
  - Ретраи `notify-guest` и кнопка «отправить гостю ещё раз» — хвост.

## 2. Что делаем

### 2.А Схема / данные

Одна миграция `…_button_rate_limit.sql`.

Сейчас у `rate_limits` первичный ключ — `external_user_id`, одно окно на гостя. Лимит кнопок должен считаться
отдельно от лимита текста: иначе листание меню съест лимит на сообщения, и наоборот.

```sql
alter table rate_limits add column bucket text not null default 'text';
alter table rate_limits drop constraint rate_limits_pkey;
alter table rate_limits add primary key (external_user_id, bucket);
alter table rate_limits add constraint rate_limits_bucket_check check (bucket in ('text', 'button'));
```

(Имя PK сверить с БД.) `check_rate_limit` получает параметр `p_bucket text default 'text'`, так что старый вызов
бота продолжает работать до деплоя новой функции. Сигнатура меняется, поэтому `drop function` старой версии
и `create` новой — в одной миграции. `purge_old_data()` чистит `rate_limits` по `window_start` и бакетов не
касается, правка не нужна (сверить).

### 2.Б Сервер (бот)

#### 2.Б.1 Каркас сценарных тестов

Точка входа уже подходит для тестов: `routeUpdate({ client, tg }, update)` получает зависимости параметром
(ADR-008), так что Telegram подменяется без `fetch`-моков и без правки боевого кода.

- `telegram-webhook/testing/fakeTelegram.ts` — `createFakeTelegram(): TelegramClient & { calls, sent(), last() }`:
  - реализует все методы `TelegramClient` (`sendMessage`, `editMessageText`, `clearKeyboard`, `deleteMessage`,
    `answerCallbackQuery`) и пишет каждый вызов в `calls` (метод, chatId, текст, клавиатура);
  - `sendMessage` возвращает возрастающий `message_id`, как Telegram;
  - сбой задаётся сценарием: `failNext(method, new TelegramApiError(...))`. Нужно для «гость заблокировал бота»
    (403) и «message to edit not found».
  - Тип берётся из `TelegramClient`. Если в клиенте появится метод, подмена перестанет компилироваться, и это
    хорошо.
- `telegram-webhook/testing/guest.ts` — `createTestGuest(client)`: гость с отрицательным `external_user_id`
  (как в `navigation.integration.test.ts`), построители апдейтов `text("…")`, `tap(callbackData, messageId)`,
  `command("/start")` с уникальным `update_id`. `cleanup()` удаляет заявки по `conversation_id`, затем диалог,
  `rate_limits` и `processed_updates` гостя.
- `telegram-webhook/scenarios.integration.test.ts` — сами сценарии. Запуск как у остальных интеграционных:
  `deno test --allow-env --allow-net --allow-read --env-file=../../.env`, без `SUPABASE_URL` тест пропускается.
  Каждый тест работает со своим гостем, иначе текстовый лимит 3/30 с срабатывает между тестами.
- Ресторан — тот, что в seed. Тест не меняет его настройки: часы и `manager_chat_id` только читает. Уведомление
  менеджеру уходит в подменный клиент, в настоящий Telegram ничего не отправляется.
- Время: бронь зависит от «сейчас» (сегодня не раньше +30 мин, выходные скрыты). Тест берёт первую предложенную
  дату и первый предложенный час из кнопок ответа, а не вычисляет их сам. Так он не ломается в зависимости от дня
  недели и часа запуска.

#### 2.Б.2 Матрица критериев §10

| # | Критерий (план §10) | Сценарий теста | Что проверяем |
|---|---|---|---|
| 1 | Находит блюдо и сообщает цену | текст с точным названием блюда из seed | одно сообщение-карточка, цена в формате `formatPrice` |
| 2 | Уточняет, если подходит несколько | текст с общим словом (2+ совпадения) | `SEARCH_CHOOSE`, кнопки блюд; тап по кнопке открывает карточку |
| 3 | Не выдумывает КБЖУ, состав, аллергены | карточка блюда без КБЖУ из seed | «нет данных» в полях, в тексте нет `0 ккал`; предупреждение про аллергию есть |
| 4 | Не выдаёт недоступное за доступное | поиск блюда из стоп-листа; поиск и подделанный `dish:<id>` неопубликованного | стоп-лист: пометка «недоступно» и в кнопке, и в карточке; неопубликованное: не найдено, `DISH_NOT_FOUND` |
| 5 | Собирает бронь и сохраняет после подтверждения | полный проход: «Забронировать» → дата → период → час → гости → имя → контакт → пропуск комментария → «Отправить» | до «Отправить» в `booking_requests` 0 строк, после — 1, `status = 'pending'`; менеджеру ушло одно сообщение |
| 6 | Не называет заявку подтверждённой бронью | тот же проход | ни одно исходящее гостю сообщение до решения менеджера не содержит «подтвержден» без «не»; итог = `BOOKING_SENT` |
| 7 | Принимает жалобу и запрос менеджеру | «Связаться с менеджером» → «Жалоба» → текст → «Отправить»; то же для `manager_request` с контактом | одна строка `guest_requests` нужного `kind`, `status = 'new'`; без контакта `manager_request` не проходит дальше (`contact_required`) |
| 8 | Менеджер видит заявки и меняет статус | — | уже закрыт: `admin/tests/status-rpc.integration.test.ts`, `rls.integration.test.ts`; в матрице ссылка, новый тест не пишем |
| 9 | Повтор не создаёт дубликат | (а) тот же `update_id` дважды; (б) два разных апдейта «Отправить» по одному `draftId` параллельно (`Promise.all`) | (а) второй апдейт ничего не отправляет и не пишет; (б) одна заявка, одно уведомление менеджеру, гостю один итог |
| 10 | Нет внутренних данных в ответах | все сценарии выше | общая проверка §2.Б.3 на каждом исходящем тексте и подписи кнопки |

Дополнительно, не из §10, но тоже дешёвые и ловят тихие ошибки:

- «Мои заявки»: созданная в сценарии 5 бронь видна в списке; отмена → `cancelled`, менеджеру одно сообщение.
- Сбой Telegram при уведомлении менеджера (`failNext("sendMessage", 403)` на чат менеджера): заявка создана,
  `manager_notified_at is null`, гость получил итог.
- `/cancel` посреди брони: состояние сброшено, заявки нет.

#### 2.Б.3 Проверка «внутренних данных»

`assertNoInternals(text)` в `testing/` прогоняется по каждому вызову подменного клиента (текст и подписи кнопок)
во всех сценариях. Запрещено:

- UUID (`/[0-9a-f]{8}-[0-9a-f]{4}-/i`) — id блюд, заявок и диалогов живут только в `callback_data`;
- `undefined`, `null`, `NaN`, `[object Object]` — признак пропущенного поля;
- `manager_chat_id` ресторана как число и имена полей БД (`external_user_id`, `restaurant_id` и т.п.);
- названия неопубликованных блюд из seed (они вообще не должны покидать БД).

`callback_data` эта проверка не трогает: Telegram гостю его не показывает.

#### 2.Б.4 Аудит обещаний

Правило (MVP-план §3.2, §194): бот обещает только то, что система делает всегда, а не «обычно». Кандидаты,
найденные при чтении текстов:

| Где | Сейчас | Проблема | Предложение |
|---|---|---|---|
| `CANCEL_DONE` | «Бронь отменена. Менеджер уведомлён.» | уведомление может не дойти (`manager_notified_at`), а текст утверждает факт | «Бронь отменена.» или «…Менеджер получит уведомление.» (вопрос 3) |
| `CANCEL_CONFIRM_TEXT` | «…Менеджер получит уведомление.» | то же, но про будущее; допустимо, если уведомление отправляется всегда | оставить, если в вопросе 3 выбран второй вариант |
| `guestNotification`, `cancelled` | «Можно отправить новую заявку или написать нам.» | «написать» = свободный текст = поиск блюда; ответа менеджера в чате нет (S06b) | «…или связаться с менеджером через меню бота.» |
| `too_many_guests` | «…свяжитесь с менеджером — он всё обсудит.» | обещание результата | «Для компании больше N человек оставьте запрос менеджеру.» |
| `welcomeText` | «…оставить заявку.» | ок | — |
| `BOOKING_SENT`, `confirm` | «Бронь пока не подтверждена…», «Это заявка, а не подтверждённая бронь» | ок, закреплено тестом 6 | — |

Список не окончательный. В сессии кода пройти все строки `content.ts` и `guestNotification.ts` ещё раз; каждая
правка текста — одна строка в таблице LOG «было → стало».

#### 2.Б.5 Лимит частоты кнопок

- `domain/antispam.ts`: `BUTTON_RATE_MAX = 30`, `BUTTON_RATE_WINDOW_SECONDS = 60` (вопрос 5).
- `services/antispam.ts`: `checkGuestRate(client, externalUserId, bucket)`. Fail open сохраняется: сбой счётчика
  пропускает апдейт.
- Роутер, ветка `callback_query`: проверка до записи нажатия в `messages`.
  - `warn` → `answerCallbackQuery(id, RATE_LIMIT_WARNING)`, то есть всплывашка, а не сообщение в чат: в чате не
    остаётся мусора, удалять нечего;
  - `drop` → только `answerCallbackQuery(id)` без текста (кнопка перестаёт «крутиться»), без записи в БД;
  - нажатие всегда получает `answerCallbackQuery`: иначе у гостя часы на кнопке до таймаута Telegram.
- Тест: 31 нажатие подряд одним гостем → 30 обработаны, 31-е получает всплывашку, `messages` не растёт.

### 2.В Экран (админка)

#### 2.В.1 Интеграционные тесты последовательно

В `vite.config.ts` → `test`: интеграционные файлы `tests/**` идут без параллелизма между файлами
(`fileParallelism: false` или отдельный `projects`-проект для `tests/`, если юнит-тесты `src/**` станут
заметно медленнее). Приёмка: полный `pnpm test` три раза подряд зелёный.

#### 2.В.2 Вливание Realtime в кэш

Хвост S05: `mergeBookingEvent` / `mergeGuestRequestEvent` проверены только через чистую `applyRowEvent`. Если
слияние можно вынести в чистую функцию (вход: черновик кэша + событие + текущие фильтры, выход: новый черновик),
выносим и покрываем случаями: событие пришло раньше ответа запроса, позже, дубль, `DELETE` чужой строки, строка
перестала подходить под фильтр. Если вынос тянет переписывание `requestsApi`, не делаем и оставляем ручной
приёмкой (вопрос 6).

## 3. Инварианты, которые этот спринт обязан удержать

- **Боевой код не меняется ради тестов.** Подмена идёт через уже существующий параметр `deps.tg`. Если тесту
  чего-то не хватает, сначала вопрос, потом правка. Флаги `if (TEST)` в коде бота запрещены.
- **ADR-008:** `testing/` импортирует только `router.ts`, `TelegramClient`/`TelegramApiError` и
  `supabaseClient.ts`. `pnpm check:layers` проходит; если скрипт смотрит на `testing/`, исключение
  прописывается явно.
- **ADR-006, идемпотентность (S03):** тест 9 проверяет и повтор `update_id`, и гонку двух разных апдейтов по
  одному `draftId`. Это разные защиты (`processed_updates` и ключ `booking:<conversationId>:<draftId>`).
- **ADR-009:** все правленые тексты остаются в `content.ts` / доменных форматтерах; тесты сравнивают с
  константами, а не с копией строки.
- **Заявки бессрочны (S06c).** Это правило не нарушаем: тест удаляет только свои заявки, у гостя с
  отрицательным `external_user_id`. Реальные id Telegram положительные, так что на настоящих гостей удаление
  не попадает.
- **Антиспам fail open (S06c)** — для нового бакета тоже. На кнопке брони «Отправить» лимит не должен отнимать
  возможность отправить заявку: 30 в минуту при живом использовании недостижимо (вопрос 5).
- **Тесты не шлют ничего в настоящий Telegram** и не меняют настройки ресторана в dev-БД.

## 4. Открытые вопросы объёма

1. **Удаление тестовых заявок в dev-БД.** Предлагаю удалять по `conversation_id` тестового гостя в `cleanup()`.
   Альтернатива — оставлять и чистить отдельным скриптом. Не предлагаю: копятся в админке у менеджера.
2. **Где лежат хелперы:** `telegram-webhook/testing/` (рядом с роутером) или `_shared/testing/`. Предлагаю
   первое: подменный клиент нужен только тестам роутера.
3. **«Менеджер уведомлён» при отмене.** (а) нейтрально «Бронь отменена.»; (б) «Менеджер получит уведомление»
   (обещание про попытку, а не результат). Предлагаю (а): гостю важен факт отмены, а не внутренняя доставка.
4. **Порог «подтвержден» в тесте 6.** Проверка «нет слова „подтвержден“ без отрицания» грубая. Предлагаю
   сравнивать итог с константой `BOOKING_SENT` и дополнительно проверять, что в сообщениях до решения нет
   `✅ Ваша бронь подтверждена`. Регулярное выражение по всем текстам не нужно.
5. **Лимит кнопок: 30 в минуту, всплывашка.** Стартовое значение, правится константой. Ок?
6. **Тесты вливания Realtime (§2.В.2)** — делать, только если вынос дешёвый. Решить в начале сессии кода по
   факту чтения `requestsApi`.
7. **Ручная приёмка S05 из `TESTER.md`** — проходить в этом спринте целиком (11–17, 8а, «не покрыто») или только
   то, что не закрыли автотесты S07? Предлагаю целиком: это последний спринт до CI, дальше их никто не пройдёт.

## 5. Что показываем на приёмке

Проверяет пользователь.

1. `deno test … telegram-webhook/scenarios.integration.test.ts` — все сценарии зелёные. Вывод теста показывает
   номера критериев §10 в именах тестов.
2. Поломка нарочно: в `content.ts` временно заменить `BOOKING_SENT` на «Бронь подтверждена» → тест 6 падает.
   Вернуть.
3. После прогона в админке нет тестовых заявок и диалогов (`cleanup()` отработал).
4. `pnpm check:layers`, `deno check`, `deno test` по домену — чисто.
5. Админка: `pnpm test` три раза подряд — зелёный, интеграционные файлы идут последовательно.
6. Живой бот, тексты: отменить свою бронь → новый текст (вопрос 3). Менеджер отменяет бронь → у гостя нет
   «написать нам». Бронь на 13+ гостей → новый текст.
7. Живой бот, лимит кнопок: быстро жать кнопку 30+ раз за минуту → всплывашка «Слишком много…», в чате новых
   сообщений нет, в админке в диалоге лишних нажатий нет.
8. Отложенные шаги S05 по `TESTER.md` (объём — вопрос 7). Пройденное вычёркивается в `TESTER.md` с датой.
