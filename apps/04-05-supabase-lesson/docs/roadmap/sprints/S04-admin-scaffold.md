# S04 — Админка: каркас и справочники

После спринта менеджер входит в админку по email и паролю и сам правит всё, что видит гость: данные ресторана и часы работы, FAQ, категории и блюда, доступность блюда (стоп-лист). Изменения сразу видны в Telegram-боте. Постороннему без аккаунта менеджера база не отдаёт ничего — это проверяет тест, а не вера в интерфейс.

## 1. Цель и границы

- **Входит:**
  - Каталог `admin/` — Vite + React + TypeScript, shadcn/ui, TanStack Router, Redux Toolkit + RTK Query (ADR-002).
  - Вход менеджера (Supabase Auth, email + пароль), защита маршрутов, выход.
  - Первые RLS-политики проекта: таблица `restaurant_managers` и политики на справочные таблицы (§2.А).
  - Экраны: «Ресторан» (включая структурные часы работы `opening_hours` и `manager_chat_id`), «FAQ», «Меню» (категории + блюда, переключатели «опубликовано» и «в наличии»).
  - Типы БД из схемы (`supabase gen types`), проверка слоёв админки (ADR-008), тесты (§5).
- **Не входит:**
  - Заявки, обращения, смена статусов, Realtime — S05. Чат — S06.
  - Загрузка фото блюд (Supabase Storage): поле `photo_url` — обычный текст-ссылка. Фото в боте не показываются (STATE §4), загрузка без потребителя не нужна.
  - Периоды брони «Обед / Ужин» (константы в `bookingRules.ts`): правка из админки потребует перевода бота на данные — отдельная задача, см. вопрос 6.
  - Несколько ресторанов и роли менеджеров (владелец/сотрудник): один менеджер = полный доступ к своему ресторану. Таблица `restaurant_managers` сделана ресторан-ориентированной, чтобы позже не переделывать.
  - Самостоятельная регистрация, сброс пароля письмом, приглашения: менеджера заводит владелец проекта (§2.А, вопрос 1).
  - Realtime для справочников (роадмап §2: совместной правки меню нет), перетаскивание порядка мышью, массовые операции, импорт меню (S10).
  - CI для админки (S08). Деплой админки — S08; в этом спринте она запускается локально.

## 2. Что делаем

### 2.А Схема / данные

Одна миграция `…_admin_auth.sql`. До неё RLS включён, политик нет: доступ только у service role (бот). После неё у роли `authenticated` появляется доступ **минимально необходимый этому спринту** — политики на заявки и чат добавляют S05 и S06, не раньше (принцип наименьших прав).

**Кто такой менеджер.** Пользователь `auth.users` ≠ менеджер ресторана: аккаунт Supabase Auth могут завести, не будучи менеджером. Членство хранится явно:

```sql
create table restaurant_managers (
    user_id       uuid primary key references auth.users (id) on delete cascade,
    restaurant_id uuid not null references restaurants (id) on delete cascade,
    created_at    timestamptz not null default now()
);
alter table restaurant_managers enable row level security;
```

Один пользователь — один ресторан (`user_id` — PK). Если когда-нибудь понадобится «менеджер нескольких ресторанов», PK меняется на пару — миграция простая, пока не нужна.

**Хелпер для политик:**

```sql
create function is_manager_of(p_restaurant_id uuid) returns boolean
language sql stable security definer set search_path = ''
as $$
    select exists (
        select 1 from public.restaurant_managers
        where user_id = (select auth.uid()) and restaurant_id = p_restaurant_id
    );
$$;
```

Почему `security definer`: сама `restaurant_managers` закрыта RLS; политика на другой таблице, читающая её под правами вызывающего, упёрлась бы в её же политику. `set search_path = ''` — обязательная гигиена для definer-функций (иначе подмена схемы). `(select auth.uid())` в скобках — Postgres вычисляет один раз на запрос, а не на каждую строку.

**Политики** (все `to authenticated`; для `anon` политик нет, значит доступа нет — проверяется тестом):

| Таблица | Операции | Условие |
|---|---|---|
| `restaurant_managers` | `select` | `user_id = (select auth.uid())` — менеджер видит только свою строку; писать из клиента нельзя никому |
| `restaurants` | `select`, `update` | `is_manager_of(id)`; `insert`/`delete` нет — ресторан заводит владелец проекта |
| `faq_entries`, `menu_categories`, `menu_items` | `select`, `insert`, `update`, `delete` | `is_manager_of(restaurant_id)`; на `insert` и `update` — `with check` с тем же условием (иначе можно перенести свою запись в чужой ресторан сменой `restaurant_id`) |

`delete` для блюд, категорий и FAQ разрешён (это справочники, а не журнал). `conversations`, `messages`, `booking_requests`, `guest_requests`, `processed_updates` — **без политик для `authenticated`**, как и раньше.

**Что бот.** Бот ходит под service role и RLS не замечает — политики его не ломают. Проверяется на приёмке (шаг 11), а не предполагается.

**Auth-конфиг.** `config.toml`: `[auth] enable_signup = false` и `[auth.email] enable_signup = false` (регистрации нет). Для удалённого dev-проекта то же — в дашборде (Authentication → Sign In / Providers → отключить «Allow new users to sign up»). Это не заменяет `restaurant_managers`: даже если регистрацию включат по ошибке, посторонний войдёт, но не увидит ничего.

**Как завести менеджера** (шаг в README проекта, без секретов в git):
1. Dashboard → Authentication → Users → «Add user» (email + пароль, «Auto Confirm User»).
2. SQL Editor: `insert into restaurant_managers (user_id, restaurant_id) values ('<uid>', '<id ресторана>');`

Seed это не делает: пользователь Auth в `seed.sql` — хрупкая вещь (хеш пароля, внутренние таблицы Auth), а пароль в git не коммитим.

**Данные без миграции (для сведения):** `restaurants.opening_hours` — jsonb `{"1": {"open":"13:00","close":"24:00"}, …}`: ключ — ISO-день недели `"1"…"7"`, нет ключа = выходной, `null` = без ограничений (формат бота, `bookingRules.ts`; админка пишет **тот же** формат). `manager_chat_id` — bigint, `null` = уведомления выключены.

### 2.Б Сервер

Своего сервера у админки нет: клиент ходит в Supabase напрямую с anon-ключом, права ограничивает RLS (§2.А). **Service-role ключ в браузер не попадает никогда** — ни в `VITE_*`-переменные, ни в код; в `admin/` его нет вообще.

Edge Functions и бот в этом спринте не меняются. Единственное исключение — если приёмка вскроет, что бот не учитывает какой-то случай из новых данных (например, `opening_hours` с `close < open`, который админка теперь может сохранить): такое лечится валидацией в админке, не правкой бота (§3, инвариант 4).

### 2.В Админка (`admin/`)

#### Слои (ADR-008) и структура

```
admin/src/
  routes/        TanStack Router: файловые маршруты, guard'ы, loaders. Только сборка экранов.
  features/      auth/, restaurant/, faq/, menu/ — компоненты и хуки экрана
  api/           RTK Query (единственное место, где есть supabase-js), store, supabaseClient.ts, database.types.ts
  domain/        чистая логика без React и Supabase: схемы валидации, openingHours, форматирование
  components/ui/ shadcn (генерируется CLI, руками почти не правим)
```

Правило: `routes → features → api → supabase`; `domain` не импортирует ничего из остальных слоёв; компоненты не импортируют `@supabase/supabase-js` (только типы из `database.types.ts` допустимы). Проверка — `admin/scripts/check-layers.sh` (по образцу бота), подключается как `pnpm check:layers:admin`. Расширение ADR-008 для админки — тот же ADR, статус не меняется.

#### Каркас

- **Менеджер пакетов и запуск:** `admin/` — пакет pnpm-воркспейса (`apps/*` уже в `pnpm-workspace.yaml`; проект `04-05-supabase-lesson` сам пакет, `admin/` вложен в него, поэтому воркспейс нужно расширить на `apps/*/admin` — см. вопрос 2). Скрипты: `dev`, `build`, `typecheck`, `lint`, `test`, `types:gen`.
- **Env:** `admin/.env.local` (в `.gitignore`): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. `.env.example` в git. Анон-ключ публичный по природе — защита это RLS.
- **Типы БД:** `pnpm types:gen` → `supabase gen types typescript --linked > admin/src/api/database.types.ts`; файл коммитится. Любая миграция, меняющая схему, требует перегенерации — в чеклист DoD.
- **TanStack Router:** файловые маршруты через плагин Vite; корневой контекст маршрутизатора получает `store`, чтобы `beforeLoad` мог проверять сессию. Маршруты:
  - `/login`
  - `/_authed` (layout с навигацией и guard'ом) → `/restaurant`, `/faq`, `/menu`, `/menu/$categoryId`; `/` → редирект на `/menu`.
  - Внутренние состояния экрана (выбранная категория, диалог редактирования) — в URL, где это разумно (`/menu/$categoryId`, `?edit=<id>`), чтобы работала кнопка «назад» и перезагрузка страницы.
- **shadcn/ui:** `init` (Tailwind), компоненты по мере надобности; ожидаемый набор — `button`, `input`, `textarea`, `label`, `form`, `select`, `switch`, `checkbox`, `table`, `dialog`, `alert-dialog`, `sheet`, `badge`, `skeleton`, `sonner` (toast), `dropdown-menu`, `separator`. Версии Tailwind/shadcn/TanStack Router на старте проверяются по актуальной документации (Context7), а не по памяти.
- **Формы:** `react-hook-form` + `zod` (как в рекомендациях shadcn). Схемы zod живут в `domain/` — это и валидация формы, и единый источник правил «что допустимо».
- **Redux Toolkit:** `store` с `baseApi` (RTK Query) и slice `auth`. RTK Query с `fakeBaseQuery()` и `queryFn`, в которых вызывается supabase-js; ошибки приводятся к сериализуемому `{ message, code? }` (в Redux не кладём экземпляры `Error`/`PostgrestError`). Теги кэша: `Restaurant`, `Faq`, `MenuCategory`, `MenuItem`.

#### Вход и защита

- **Сессия.** supabase-js хранит и обновляет токены сам. Источник правды для навигации — `supabase.auth.getSession()` в `beforeLoad` защищённого layout'а: нет сессии → `redirect({ to: '/login', search: { redirect: <откуда пришли> } })`. После входа — возврат на исходный адрес (`redirect` параметр **валидируется**: только относительный путь внутри админки, иначе `/` — защита от open-redirect).
- **Slice `auth`:** `status: 'loading' | 'signedIn' | 'signedOut'`, `email`. Подписка `onAuthStateChange` создаётся один раз при старте приложения и приводит slice в соответствие (выход в другой вкладке, протухший refresh-токен). При `SIGNED_OUT` — сброс кэша RTK Query (`api.util.resetApiState()`), чтобы данные прошлого менеджера не остались в памяти.
- **Член ли пользователь ресторана.** После входа запрос `getMe` (`select restaurant_id from restaurant_managers`). Нет строки — экран «Нет доступа к ресторану. Обратитесь к владельцу» + кнопка «Выйти»; остальные запросы не выполняются. Есть — `restaurantId` лежит в кэше `getMe` и используется всеми остальными запросами (в запросы на запись он подставляется явно, `with check` в БД это страхует).
- **Ошибки входа** — одно общее сообщение «Неверный email или пароль» (без различения «нет такого пользователя» / «неверный пароль»). Кнопка блокируется на время запроса. Rate limit — на стороне Supabase.
- **Выход:** `signOut()` → `/login`.

#### Экран «Ресторан» (`/restaurant`)

Одна форма, один `update` по строке ресторана. Поля:

| Поле | Ввод | Правило |
|---|---|---|
| `name` | текст | обязательное, 1–120 |
| `description`, `address`, `phone`, `email` | текст | пусто → `null`; `email` — формат email, если задан |
| `timezone` | выбор из `Intl.supportedValuesOf('timeZone')` с поиском | обязательное; **меняется редко, и смена сдвигает все будущие брони в абсолютном времени** — предупреждение под полем (брони хранятся в UTC, пересчёта нет) |
| `working_hours` | текст | свободный текст для карточки «О ресторане» (показывается гостю как есть) |
| `opening_hours` | редактор по 7 дням (ниже) | структурные часы, по ним бот ограничивает бронь |
| `manager_chat_id` | число | целое (может быть отрицательным — групповой чат); пусто → `null` = уведомления выключены. Подсказка, как узнать id (README); рядом пометка: менеджер должен сам написать боту `/start` |

Редактор `opening_hours`: на каждый день недели — переключатель «Работаем» + два поля времени «с» / «до». Правила (домен `openingHours.ts`, чистые функции с тестами):
- Формат хранения `HH:MM`; `close` может быть `24:00` (бот так понимает «до полуночи»).
- `open < close` строго. Переход через полночь («до 02:00») **не поддерживается** — бот считает окно в пределах суток; редактор объясняет это и не даёт сохранить `close <= open` (иначе брони молча перестанут приниматься — `workingWindow` бота трактует такое окно как пустое/битое).
- «Выходной» = ключа нет в объекте. Все семь дней выключены → сохраняется `{}` (ресторан закрыт всегда), и это **не то же самое**, что `null`. Для `null` («без ограничений») — отдельная явная опция «Не ограничивать бронь часами работы». Различие `{}` / `null` показывается в интерфейсе словами, не только состоянием переключателей.
- Копирование «применить ко всем дням» — одна кнопка, чтобы не вбивать семь раз.

Сохранение: кнопка недоступна, пока форма не изменена и не валидна; после успеха — toast «Сохранено». Ошибка сервера — toast и данные формы не сбрасываются.

#### Экран «FAQ» (`/faq`)

- Таблица: вопрос, ответ (обрезан), «опубликован» (переключатель прямо в строке), действия.
- Создание/правка — диалог. Поля: `question` (1–300), `answer` (1–2000), `is_published`. `sort_order` в форме нет: порядок меняется стрелками «выше/ниже» в таблице. Стрелки меняют `sort_order` у **двух соседних** записей (обмен значений) одним запросом-батчем; при равных `sort_order` (так бывает после ручных вставок) порядок внутри группы стабилизируется по `created_at, id`, а перед обменом значения нормализуются (0, 1, 2, …) — иначе обмен равных чисел ничего не меняет и кнопка «не работает».
- Удаление — через `alert-dialog` («Удалить вопрос? Гости перестанут его видеть»).
- Новая запись: `sort_order = max + 1` (в конец), `is_published = true` по умолчанию схемы.

#### Экран «Меню» (`/menu`, `/menu/$categoryId`)

Две колонки (на узком экране — последовательно): слева категории, справа блюда выбранной.

- **Категории:** список, создание/переименование (диалог, `name` 1–80), порядок стрелками (тот же механизм, что у FAQ — общий хук/функция в `domain/` + `api/`), удаление. Пункт «Без категории» показывает блюда с `category_id = null` (их бот находит только поиском — STATE §4; админка делает такие блюда видимыми менеджеру). **Удаление категории:** `menu_items.category_id` в схеме `on delete set null` — блюда не удаляются, а «осиротевают» и пропадают из меню гостя. Поэтому диалог подтверждения называет число блюд («В категории 7 блюд, они станут «Без категории» и пропадут из меню бота. Удалить?»), а если блюд нет — удаление без предупреждения про блюда.
- **Список блюд** (выбранная категория): название, цена с валютой, две колонки переключателей — «Опубликовано» (`is_published`) и «В наличии» (`is_available`), бейджи «Черновик» (не опубликовано) и «Нет КБЖУ» (хоть одно из четырёх значений `null` — менеджер видит, что гость получит «нет данных»). Переключатели — **оптимистичные**: RTK Query `onQueryStarted` + `updateQueryData`, при ошибке откат (`patchResult.undo()`) и toast. Это нужно, чтобы стоп-лист переключался мгновенно во время службы. Остальные операции (форма, удаление) — пессимистичные: ждут ответа.
- **Форма блюда** (диалог или `sheet`; создание и правка — один компонент). Поля и правила — в таблице. Валидация зеркалит `check`-ограничения БД, чтобы ошибка показывалась в поле, а не как «violates check constraint»:

| Поле | Ввод | Правило |
|---|---|---|
| `name` | текст | обязательное, 1–120 |
| `category_id` | выбор | категория или «Без категории» |
| `description`, `ingredients` | текст | пусто → `null` |
| `price` | число | обязательное, ≥ 0, не более 2 знаков после запятой (`numeric(10,2)`); запятая и точка принимаются; `0` допустим (бесплатное блюдо — это не «нет цены») |
| `currency` | выбор из кодов ISO | см. вопрос 3 |
| `portion_grams` | целое | > 0 или пусто → `null` |
| `kcal_per_portion`, `protein_per_portion`, `fat_per_portion`, `carbs_per_portion` | число, 1 знак | ≥ 0 или пусто → `null` |
| `allergens` | три состояния (ниже) | |
| `photo_url` | текст | пусто → `null`; если задан — `http(s)://` |
| `is_published` | переключатель | **по умолчанию выключен** (как в схеме): новое блюдо — черновик, пока менеджер не опубликует |
| `is_available` | переключатель | по умолчанию включён |

**Аллергены — три состояния, а не два.** В схеме `null` = «не указано», `{}` = «указано: аллергенов нет», `{...}` = список. Поле формы — выбор режима «Не указано / Аллергенов нет / Указать» и при «Указать» — теги (ввод + Enter, без дублей, trim, регистр не меняем). Нельзя схлопывать «не указано» и «нет аллергенов»: бот на первое скажет «нет данных», на второе — «аллергены не указаны как присутствующие», и для человека с аллергией это разные ответы.

**Пустое поле и ноль — разные вещи** (инвариант ядра): пустой ввод → `null`, введённый `0` → `0`. Для КБЖУ это важно (напиток может иметь 0 жиров).

- **Удаление блюда:** `alert-dialog`. Мягкого удаления нет — блюдо можно просто снять с публикации; текст диалога предлагает этот вариант.
- Лимиты бота (STATE §2: 10 блюд в категории на экране, больше — подсказка искать по названию) — в админке предупреждение у категории: «В категории больше 10 блюд: гость увидит первые 10 и подсказку искать по названию».

#### Общие состояния экранов

Каждый экран явно показывает: загрузку (skeleton), ошибку загрузки (сообщение + «Повторить»), пустое состояние («Пока нет вопросов — добавьте первый»). Протухшая сессия посреди работы (запрос вернул 401/JWT expired) → один тихий refresh, при неудаче — выход на `/login` с сохранением адреса.

### Что бот и админка делают с одними и теми же данными

Админка и бот читают одни таблицы без общего кода (разные рантаймы: Deno и браузер). Правила формата (`opening_hours`, `allergens`, `null` против `0`) дублируются осознанно и сверяются руками на приёмке (шаги 8–10), а не общей библиотекой: ради трёх правил делать shared-пакет между Deno и Vite — избыточно.

## 3. Инварианты, которые этот спринт обязан удержать

1. **RLS — единственная защита данных; интерфейс — удобство.** Скрытая кнопка не считается защитой: каждое ограничение (чужой ресторан, постороннего пользователя, анонима) проверяется запросом мимо интерфейса (тест §5).
2. **Service-role ключ не покидает сервер.** В `admin/` его нет: ни в коде, ни в `.env.example`, ни в `VITE_*`. Проверка при ревью — `grep -ri service_role admin/` пусто.
3. **Политики — только то, что нужно спринту.** `conversations`, `messages`, заявки остаются закрытыми для `authenticated` до S05/S06. Не добавлять «на всякий случай».
4. **Админка не может записать то, на чём ломается бот.** Невалидные `opening_hours` (`close <= open`, мусор в формате времени, ключи вне `"1"…"7"`), отрицательные цены/КБЖУ, `portion_grams = 0` — отсекаются валидацией до отправки, а ограничениями БД — на записи.
5. **`null` ≠ `0` ≠ пустая строка; `null` аллергенов ≠ `{}`** (ADR-004 и инвариант «не выдумывать» из S02). Тест на схему формы блюда.
6. **Новое блюдо — черновик.** Публикация — явное действие менеджера; блюдо без цены/состава не появляется в меню «само».
7. **Смена `restaurant_id` через API невозможна** (`with check`): менеджер не может перенести запись в чужой ресторан, а `restaurant_id` подставляет код, не форма.
8. **Слои ADR-008:** компоненты не знают про Supabase; `domain` без React/Supabase; `pnpm check:layers` (бот) и `pnpm check:layers:admin` зелёные.
9. **Бот не пострадал:** `deno test` и `pnpm check:layers` бота зелёные, на приёмке бот работает после включения политик.
10. **Выход чистит память:** после `signOut` кэш RTK Query пуст, данные прошлого менеджера на экране не остаются.

## 4. Открытые вопросы объёма

Вопрос без ответа блокирует связанную задачу — ответ даётся первой записью `QA.md` сессии.

1. **Как заводить менеджера: руками в Dashboard + SQL (рекомендация) или скрипт?** Руками: два шага из README, один раз на проект, ноль кода. Скрипт `scripts/create-manager.ts` (service role, из локального `.env`) — удобнее, но это код под единичную операцию. Блокирует: приёмку (нужен хотя бы один менеджер).
2. **Где живёт `admin/` в монорепозитории?** Рекомендация: `apps/04-05-supabase-lesson/admin/` как отдельный пакет — нужен `apps/*/admin` в `pnpm-workspace.yaml` (сейчас `apps/*`, и вложенный пакет не подхватится) и свои скрипты в корне (`dev:admin`, `build:admin`, … как у остальных проектов). Альтернатива — `apps/04-05-admin/` рядом: не трогает воркспейс, но разрывает проект на два каталога, а ADR-002 и CLAUDE.md говорят «каталог `admin/` в корне проекта». Блокирует: старт.
3. **Валюта блюда.** В схеме `menu_items.currency` по умолчанию `'RUB'`, а ресторан-сид — в EUR; колонки `restaurants.currency` нет. Рекомендация: в форме выбор из короткого списка (`EUR`, `RUB`, `USD`, `GBP`), по умолчанию — валюта большинства блюд ресторана (вычисляется по уже загруженным), иначе `RUB`; миграций не нужно. Альтернатива — колонка `restaurants.currency` с редактированием на экране «Ресторан»: чище, но это миграция, правка seed и `getRestaurantInfo`. Блокирует: форму блюда.
4. **Порядок элементов: стрелки или перетаскивание?** Рекомендация: стрелки «выше/ниже» (без библиотеки DnD, работает с клавиатуры и на телефоне). Перетаскивание — улучшение после MVP. Блокирует: FAQ и категории.
5. **Как тестировать RLS: интеграционные тесты на dev-БД (рекомендация) или pgTAP (`supabase test db`)?** Интеграционный тест: Vitest, два пользователя Auth + два ресторана создаются service-role'ом в `beforeAll` и удаляются в `afterAll`; проверяется anon, чужой менеджер, свой менеджер, подмена `restaurant_id`; без `SUPABASE_SERVICE_ROLE_KEY` в окружении тест пропускается (по образцу интеграционного теста бота). pgTAP — «чистый» SQL-уровень, но требует локального Docker-стека и нового инструмента. Блокирует: DoD.
6. **Периоды брони «Обед / Ужин» остаются константами бота.** Рекомендация: да, в S04 не трогаем (бот и так сверяет час с `opening_hours`, то есть админка уже управляет границами «снаружи»). Перевод периодов на данные — миграция + правка домена бота + экран; делаем, если появится второй ресторан с другими периодами. Блокирует: ничего, фиксирует границу объёма.
7. **Хранить ли `restaurantId` менеджера в `getMe` или в JWT-claim (custom access token hook)?** Рекомендация: запрос `getMe` — проще, одна лишняя выборка при старте. Claim быстрее, но требует хука Auth и усложняет отладку. Блокирует: `getMe`.

## 5. Что показываем на приёмке

Предусловие: в dev-проекте есть пользователь Auth + строка `restaurant_managers`; второй пользователь Auth **без** строки (для шага 3); `admin/.env.local` заполнен; бот работает.

**Вход и защита**
1. Открыть `/menu` без входа → редирект на `/login?redirect=/menu`. Войти верным паролем → попадаем на `/menu`. Неверный пароль → одно общее «Неверный email или пароль».
2. Перезагрузить страницу → остаёмся внутри (сессия жива). «Выйти» → `/login`, кнопка «назад» браузера не показывает данные (guard + пустой кэш).
3. Войти вторым пользователем (без строки в `restaurant_managers`) → «Нет доступа к ресторану», данных нет, есть «Выйти».
4. `/login?redirect=https://evil.example` → после входа попадаем на `/`, а не на внешний адрес.
5. **RLS мимо интерфейса:** с anon-ключом и без токена `select * from restaurants`, `menu_items`, `faq_entries` → пусто / отказ; `insert` в `faq_entries` → отказ. Токеном второго пользователя — то же. Проверяет автотест (шаг 12) и руками один запрос из консоли браузера.

**Ресторан**
6. Изменить `address` и `working_hours` → «Сохранено»; в Telegram «О ресторане» показывает новые значения сразу, без передеплоя.
7. Редактор часов: поставить для понедельника `18:00`–`17:00` → сохранить нельзя, понятное сообщение. Выключить воскресенье, сохранить → в БД ключа `"7"` нет; в боте воскресенье не предлагается на шаге даты брони. Включить «Не ограничивать» → в БД `opening_hours = null`, бот снова предлагает все дни. Выключить все дни → в БД `{}` (не `null`), бот не предлагает ни одной даты.
8. `manager_chat_id`: ввести свой id → отправить заявку из бота → менеджеру приходит уведомление. Очистить поле → в БД `null`, уведомление не уходит, заявка создаётся.

**FAQ и меню**
9. FAQ: создать вопрос → он в конце списка; в боте «Частые вопросы» показывает его. Снять «опубликован» → пропал из бота. Стрелками переставить два вопроса → порядок в боте изменился; повторить на записях с одинаковым `sort_order` (выставить руками в SQL) — стрелка работает.
10. Меню: создать блюдо с ценой `0` и КБЖУ `0`/пусто → карточка в боте: «0» и «нет данных» различаются. Аллергены «Не указано» против «Аллергенов нет» → бот отвечает по-разному. Новое блюдо до публикации в боте не видно; после включения «Опубликовано» — видно. Переключить «В наличии» → в боте «недоступно» сразу; отключить сеть и переключить → переключатель откатывается, toast с ошибкой.
11. Удалить категорию с блюдами → диалог называет число блюд; после удаления блюда в «Без категории» и не видны в меню бота, находятся поиском только если опубликованы. Бот при этом работает без ошибок (проверить меню, поиск, бронь).

**Автоматические проверки**
12. `pnpm --filter … test` (admin): схемы форм (null/0, аллергены, цены), `openingHours`, перестановка `sort_order`, откат оптимистичного переключателя; интеграционный RLS-тест на dev-БД. `typecheck`, `lint`, `build` — чисто. `pnpm check:layers:admin`, `pnpm check:layers` (бот), `deno test` (бот) — чисто. `grep -ri service_role admin/` — пусто.
