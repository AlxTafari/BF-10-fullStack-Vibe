# S06b — Админка: менеджер подключается к диалогу

После спринта менеджер нажимает в ленте чата «Подключиться к чату» — гостю приходит «К чату подключился менеджер», AI-помощник замолкает, и менеджер пишет гостю прямо из админки (в Telegram с подписью «👤 Менеджер ресторана»). Кнопка «Отключиться» возвращает разговор боту, гостю приходит уведомление; забытое подключение само истекает через 30 минут без активности менеджера.

Это базовая функция любого бота поддержки («оператор подключился»), ресторан здесь — пример предметной области.

## 1. Цель и границы

- **Входит:**
  - Ручной режим диалога (`conversations.handoff_until`): включается кнопкой «Подключиться к чату», продлевается каждым ответом менеджера, выключается кнопкой «Отключиться» или тайм-аутом. Писать гостю можно только в ручном режиме.
  - Edge Function `manager-chat`: подключение, ответ, отключение; доступ — по JWT менеджера и членству в ресторане.
  - Бот: в ручном режиме свободный текст гостя только записывается, агент и поиск блюда не вызываются; кнопки работают как раньше.
  - Админка: цветная кнопка «Подключиться к чату», поле ввода (доступно только после подключения), пузырь «Менеджер», плашка «Вы в чате · бот на паузе до HH:MM» с кнопкой «Отключиться», ошибка доставки у поля ввода.
  - Агент видит реплики менеджера в окне истории как реплики менеджера, а не свои.
- **Не входит:**
  - Уведомление менеджеру в Telegram о новом сообщении гостя в ручном режиме: в админке есть бейдж непрочитанных и `(N)` в заголовке вкладки (хвост).
  - Вложения, фото, форматирование (Markdown) в ответе менеджера — только текст.
  - Редактирование и удаление отправленного ответа.
  - Несколько менеджеров в одном диалоге, «кто подключён», передача диалога другому менеджеру: менеджер на ресторан один (как в S06).
  - Ответ менеджера по кнопке из карточки обращения: менеджер переходит из карточки в диалог («Открыть диалог», S06) и пишет там.
  - Статус «прочитано гостем»: Telegram боту его не отдаёт.
  - Повтор отправки по расписанию: не доставлено — менеджер видит ошибку сразу и решает сам.

## 2. Что делаем

### 2.А Схема / данные

Миграция `…_manager_replies.sql`.

```sql
alter table conversations add column handoff_until timestamptz;
```

- Ручной режим = `handoff_until > now()`. Тайм-аут ленивый: никакой фоновой задачи, истёкшая метка просто перестаёт действовать. `null` — режима нет.
- Пишется только RPC (ниже). Бот колонку читает, но не пишет.

**Реплика менеджера** — обычная строка `messages`: `direction = 'out'`, `kind = 'text'`, `meta = { "manager": true, "managerId": "<uuid>" }`. Отдельной колонки `sender` нет: `meta` с S09 уже несёт служебные пометки сообщения (AI-ответ, запасной ответ), админка и агент их читают. `managerId` — `auth.users.id` без внешнего ключа: журнал неизменяем и не должен ломаться при удалении пользователя.

Уведомления гостю «К чату подключился менеджер» и «Менеджер отключился от чата» — сообщения бота (`direction = 'out'`, `kind = 'text'`, `meta = null`).

**RPC** (обе `security definer`, `search_path = ''`, права только `authenticated`; чужой или несуществующий диалог — `not_found`, как `mark_conversation_read`):

- `begin_manager_handoff(p_conversation_id uuid)` → `(chat_id bigint, was_active boolean, handoff_until timestamptz)`. Подключение. В одной транзакции: проверка членства, `was_active` = режим уже шёл, `handoff_until = now() + interval '30 minutes'`, `state = '{}'` (незаконченный сценарий сбрасывается — вопрос 3).
- `extend_manager_handoff(p_conversation_id uuid)` → `(chat_id bigint, handoff_until timestamptz)`. Перед ответом: режим должен идти (`handoff_until > now()`), иначе `handoff_inactive`; продлевает `handoff_until = now() + 30 минут`. Проверка и продление — один `update … where handoff_until > now()`: истёкший режим ответ не «воскрешает».
- `end_manager_handoff(p_conversation_id uuid)` → `(chat_id bigint, was_active boolean)`. Отключение: `handoff_until = null`.

`list_conversations_page` пересоздаётся с `handoff_until` (бейдж «Менеджер» в списке). Realtime `conversations` уже опубликован — смена `handoff_until` приходит событием `UPDATE`.

### 2.Б Сервер

**Edge Function `manager-chat`** (`verify_jwt = true`, значение по умолчанию — секцию в `config.toml` не добавляем). Тело `{ action: "join" | "leave", conversation_id }` или `{ action: "reply", conversation_id, text }`.

1. Клиент Supabase с JWT из заголовка `Authorization` (anon key + токен менеджера) вызывает RPC — членство проверяет БД, а не код функции.
2. Отправка в Telegram и запись в `messages` — клиентом service role (у менеджера нет права `insert` на `messages`, и давать его не нужно).

`join`:
- `begin_manager_handoff` → если `was_active = false`, гостю «К чату подключился менеджер ресторана. Он ответит здесь.», запись в `messages`. Повторное подключение (режим уже шёл — вторая вкладка, двойной клик) только продлевает, гостю второй раз не пишет;
- ответ `{ joined: true, handoff_until, delivered }`: уведомление не дошло (403) — режим всё равно включён, админка показывает «Гость не получит сообщения: заблокировал бота».

`reply`:
- текст обрезается по краям; пустой или длиннее 4000 символов — `400 invalid_text` (лимит Telegram 4096, запас на подпись);
- `extend_manager_handoff`; режим не идёт (не подключался или истёк тайм-аут) — `409 handoff_inactive`, ничего не отправляется;
- ответ гостю: `👤 Менеджер ресторана\n<текст>` (обычный текст, без `parse_mode`);
- успешная отправка → запись в `messages` (только сам текст менеджера, без подписи — подпись это оформление Telegram);
- ответ функции: `{ delivered: true, handoff_until }`; Telegram 403 (гость заблокировал бота) → `{ delivered: false, reason: "blocked" }`; другая ошибка Telegram → `{ delivered: false, reason: "telegram_error" }`. Недоставленное в `messages` не пишется: в журнале только то, что гость получил;
- Telegram принял, запись в БД упала → `{ delivered: true, recorded: false }`, ошибка в лог функции. Гость сообщение получил, в ленте его не будет — принятый риск (один запрос, вероятность низкая).

`leave`:
- `end_manager_handoff` → если `was_active = true`, гостю «Менеджер отключился от чата. Снова отвечает AI-помощник.» (при выключенном AI ресторана — «…Можно продолжить через меню бота.»), запись в `messages`; ответ `{ left: true }`. Режим уже истёк — гостю ничего, `{ left: true }`.
- Тайм-аут гостю не сообщается: фоновой задачи нет, писать некому. Следующий текст гостя просто обработает бот.

Слои (ADR-008): `index.ts` (разбор запроса) → `services/managerChat.ts` (`joinChat`, `sendManagerReply`, `leaveChat`) → `repositories` (новый `handoffRepo.ts` для трёх RPC; запись сообщения — существующий `messagesRepo`). Тексты — `_shared/content.ts`. Проверка ввода — `domain/managerReply.ts` (чистые функции, юнит-тесты).

**Бот (`router.ts`).** Новая ветка в `handleMessage` после сценария и до агента:

```
команда (/start, /cancel)  → как раньше
живой сценарий             → как раньше (гость сам нажал «Забронировать» во время ручного режима)
ручной режим               → текст записан (kind = 'text'), ответа нет
AI / поиск                 → как раньше
```

- Проверка `isHandoffActive(conversation, now)` — `domain`, чистая функция.
- В ручном режиме текст идёт в `logIncoming` с `kind = 'text'` (не `search`): это разговор по существу, его видят превью, непрочитанные и окно агента.
- Антиспам не меняется: свободный текст вне сценария идёт в лимит и в ручном режиме.
- Кнопки (`handleCallbackQuery`) ручной режим не проверяют совсем.

**Агент.** В окне истории реплика с `meta.manager` уходит модели как реплика модели, но с префиксом `[Менеджер ресторана]: `, плюс строка в системном промпте: «реплики с этим префиксом написал живой менеджер; не повторяй и не опровергай его обещаний, если не уверен — предложи связаться с менеджером». Без этого после возврата диалога модель считает обещания менеджера своими.

### 2.В Экран

Лента чата (`features/chat`):

- **Режим не идёт:** под лентой вместо подписи «Менеджер отвечает гостю вне бота» — цветная (акцентная) кнопка «Подключиться к чату» и подсказка «Гостю придёт уведомление, AI-помощник замолчит». Поля ввода нет.
- **Режим идёт — поле ввода** под лентой: многострочное, Enter — отправить, Shift+Enter — перенос, счётчик при подходе к 4000. Во время отправки поле и кнопка заблокированы; успех — поле очищается, сообщение придёт в ленту по Realtime (как любое новое сообщение, оптимистичной вставки нет: один источник правды). Ошибка — текст остаётся в поле, под ним «Не доставлено: гость заблокировал бота» / «Не доставлено: ошибка Telegram, попробуйте ещё раз» / «Подключение истекло — подключитесь снова» (`handoff_inactive`, кнопка «Подключиться» появляется вместо поля, текст в поле сохраняется в состоянии компонента). `recorded: false` — «Доставлено, но не сохранилось в истории».
- **Пузырь менеджера** справа, как у бота, другим цветом, подпись «Менеджер». AI-пометки S09 к нему не относятся.
- **Плашка ручного режима** в шапке ленты, пока `handoff_until > now`: «Вы в чате · бот на паузе до HH:MM» (время в поясе ресторана) и кнопка «Отключиться». Истечение без событий: таймер на клиенте в момент `handoff_until` прячет плашку и поле ввода, возвращает кнопку «Подключиться».
- **Список диалогов:** бейдж «Менеджер» у строки в ручном режиме.
- API — RTK Query endpoints `joinChat`, `sendManagerReply`, `leaveChat` через `supabase.functions.invoke` (компоненты к Supabase не ходят, CLAUDE.md).

## 3. Инварианты, которые этот спринт обязан удержать

- ADR-008: обработчик функции не ходит в репозиторий; `domain` не знает Telegram и Supabase. `pnpm check:layers`.
- Доступ: менеджер пишет только в диалоги своего ресторана. Проверяет БД (RPC под JWT), не код функции. Кейсы аноним / посторонний / чужой менеджер — в `rls.integration.test.ts` (пометка STATE §4).
- В журнале `messages` — только то, что гость реально получил.
- Гость в Telegram не видит служебного: UUID, `meta`, имён полей (критерий §10.10 из S07, `testing/internals.ts`).
- AI не отвечает в ручном режиме ни на свободный текст, ни на текст вне шага сценария.
- Тайм-аут без фоновых задач: только сравнение `handoff_until` с `now()`.

## 4. Решения по объёму

Закрыты 2026-11-11 до старта (QA, «S06b: вопросы спеки»):

1. Подключение — явной кнопкой «Подключиться к чату» (защита от случайной отправки); писать можно только после неё. Отключение — кнопкой «Отключиться» или через 30 минут без активности менеджера (подключение и каждый ответ продлевают). Первый вариант «подключение первым сообщением» заменён 2026-11-11 при ревью спеки.
2. Гость в ручном режиме: уведомление при подключении и при отключении кнопкой, свободный текст получает только менеджер, кнопки меню работают.
3. Активный сценарий при подключении сбрасывается.
4. Статусы доставки: синхронный ответ функции, отдельной колонки статуса нет; недоставленное в журнал не пишется.
5. Блокировка бота гостем: Telegram 403 → «Не доставлено: гость заблокировал бота».
6. Спринт ведётся параллельно с незакрытым S09: в корневом `LOG.md` — отдельный раздел S06b; при закрытии каждый спринт архивируется своим файлом.

## 5. Что показываем на приёмке

1. Гость пишет боту вопрос, AI отвечает. В админке открыть диалог: поля ввода нет, есть кнопка «Подключиться к чату». Нажать — гостю приходит «К чату подключился менеджер…», в шапке плашка «бот на паузе до HH:MM», в списке бейдж «Менеджер», появилось поле ввода. Повторное нажатие в другой вкладке второго уведомления не шлёт.
1а. Написать «Здравствуйте, это менеджер» — гостю приходит сообщение с подписью «👤 Менеджер ресторана», в ленте админки пузырь «Менеджер».
2. Гость отвечает текстом — бот молчит, сообщение появляется в админке, растёт счётчик непрочитанных.
3. Гость нажимает кнопку «Меню» — бот показывает меню (кнопки работают).
4. Второй ответ менеджера — время «до HH:MM» сдвинулось.
5. «Отключиться» — гостю «Менеджер отключился от чата…», плашка в админке исчезла; следующий вопрос гостя снова обрабатывает AI, и ответ не противоречит сказанному менеджером.
6. Гость посреди брони (бот ждёт имя), менеджер подключается — сценарий сброшен, ответ гостя уходит менеджеру, а не в имя.
7. Тайм-аут: на dev поставить `handoff_until` в прошлое SQL-запросом — плашка и поле пропали, вернулась кнопка «Подключиться»; отправка из уже открытой вкладки — «Подключение истекло»; гостю снова отвечает AI.
8. Гость заблокировал бота, менеджер пишет — «Не доставлено: гость заблокировал бота», текст остался в поле, в ленте ничего нового.
9. Менеджер чужого ресторана вызывает функцию с чужим `conversation_id` — `not_found` (интеграционный тест).
