# Гостевой бот ресторана — роадмап

Действующий план. Стек: Supabase (Postgres + Edge Functions на Deno), Telegram Bot API, TypeScript — как в `03-supabase-lesson`; админка — Vite + React + TS, shadcn/ui, TanStack Router, Redux Toolkit + RTK Query, Supabase Realtime (WebSocket).

Источник замысла — [`../restaurant-guest-bot-mvp-plan.md`](../restaurant-guest-bot-mvp-plan.md) (входной, не редактируется).

## 1. Что строим

```
гость (Telegram) → Edge Function webhook → кнопки/команды + сервисы ядра → Supabase (меню, заявки, диалоги)
                                                                          ↓ Realtime (WebSocket)
                                                              админка менеджера (shadcn + TanStack Router)
```

Внутри: бот **без AI** (команды, inline-кнопки, пошаговые сценарии), информация о ресторане, меню, вопросы по блюдам, заявка на бронь, обращения, админка с живым обновлением заявок и чата.
Снаружи: AI-слой (S09, после ядра и админки), подбор блюда по пожеланиям, свободный диалог. Также (см. MVP-план §9): заказы/оплата, несколько каналов, live-chat гостю, касса, векторный поиск.

## 2. Что упрощено и почему

| Было | Стало | Почему | Сигнал возврата |
|---|---|---|---|
| AI в боте | Отложен, S09 | Сначала ядро и админка; сервисы ядра станут tools для LLM | Ядро и админка приняты |
| Интеграция с My-Rest | Отложена, S10 | Сначала сценарии на ручных данных | Бот и админка приняты |
| Ответ менеджера гостю из бота | Менеджер отвечает вне бота | MVP-план §3.2 | Появится запрос на ответ из админки. **Сигнал сработал 2026-10-17** (запрос на старте S06): ответы вынесены в S06b, S06 остаётся «чтение + непрочитанные» |
| Учёт столов и мест при брони | Нет: заявка `pending`, наличие места решает менеджер вручную | В модели нет столов и вместимости; автопроверка требует таблицу столов, длительность брони, рассадку и защиту от гонок | Менеджеры тонут в заявках на занятые слоты или бот должен сам подтверждать бронь |
| Realtime в админке | Только заявки, обращения, чат | Остальные экраны редко меняются | Нужна совместная правка меню |

Инварианты домена упрощением не трогаются.

### 3.2 Заметки для будущих спринтов

Решения, принятые раньше, чем дошла очередь до спринта; при написании спеки — учесть.

- **S08 (CI/CD), безопасность админки:** токены сессии Supabase лежат в `localStorage` → при деплое админки задать CSP (`script-src 'self'`, без `unsafe-inline` для скриптов) и проверить его на реальном хостинге. Тексты гостей в админке — только как текст (S05 §2.В, S06 §3.7).
- **S08, CI:** интеграционному RLS-тесту (`admin/tests/rls.integration.test.ts`) нужен service-role ключ — в CI он секрет репозитория, а не файл `.env`; тест создаёт и удаляет свои данные в dev-БД, поэтому гонять его на PR против общей dev-БД — решить (отдельный проект или локальный `supabase start`).
- **S05, S06:** каждая новая политика RLS добавляется вместе с кейсами в `rls.integration.test.ts` (аноним, посторонний, чужой менеджер).
- **Несколько менеджеров на ресторан:** перестановка FAQ/категорий сделана `upsert`'ом целых строк (запись, удалённая в другой вкладке, воскреснет) — при появлении второго менеджера заменить на RPC.

### 3.1 Отложенное за пределы плана

Бот для сотрудников, заказы, мультиканальность, автосинхронизация My-Rest, учёт столов и свободных мест при брони (отдельный спринт после S05).

## 4. Definition of Done спринта

- Схема/миграции применены, `typecheck` / `lint` / `build` чисто.
- Тесты по правилу проекта (как минимум — ядро с тихими ошибками: дедупликация заявок, курсор, статусы).
- Спека спринта отработана или расхождение зафиксировано в `../STATE.md`.
- **Ручная приёмка пользователем пройдена** — зелёные тесты её не заменяют.
- Ритуал закрытия выполнен (см. `../archive/README.md` и CLAUDE.md).
