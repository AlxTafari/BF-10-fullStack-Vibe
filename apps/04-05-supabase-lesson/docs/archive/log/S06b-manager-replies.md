# S06b — менеджер подключается к диалогу

Ведётся параллельно с незакрытым S09 (спека §4 п.6): при закрытии этот раздел уходит в `docs/archive/log/S06b-manager-replies.md`.

## 2026-11-11 — S06b: спека и реализация
**Цель:** ответ гостю из админки с подписью «Менеджер», ручной режим (AI на паузе), возврат боту.
**Решения:**
- Сигнал сработал повторно: бот ресторана — пример бота поддержки, «менеджер подключился» обязателен.
- Подключение — явной кнопкой «Подключиться к чату», писать можно только после неё; отключение — «Отключиться» или 30 мин без активности менеджера. Гостю уведомление при подключении и отключении. Первый вариант (подключение первым сообщением) заменён при ревью спеки: случайная отправка отбирала бы диалог у бота. Тайм-аут ленивый: `conversations.handoff_until`, без фоновой задачи.
- Гость в ручном режиме: свободный текст только менеджеру, кнопки работают. Активный сценарий при подключении сбрасывается: иначе ответ менеджеру бот съест как шаг «имя».
- Отправка — Edge Function `manager-chat` с JWT менеджера, синхронно: 403 Telegram (гость заблокировал бота) менеджер видит сразу. Не триггер + `pg_net`, как `notify-guest`: у `pg_net` нет ответа.
- Колонки статуса доставки нет: недоставленное в `messages` не пишется. Реплика менеджера — `meta.manager`, отдельной колонки `sender` нет.
- Реализация. Миграция `20261111120000_manager_handoff.sql`: `conversations.handoff_until`, RPC `begin_manager_handoff` (режим на 30 мин + сброс сценария, `was_active` против повторного уведомления), `extend_manager_handoff` (проверка и продление одним `update … where handoff_until > now()`: истёкший режим ответ не воскрешает), `end_manager_handoff` (отдаёт `restaurant_id` — текст уведомления зависит от `ai_enabled`); `list_conversations_page` с `handoff_until`.
- Edge Function `manager-chat` (`join` / `reply` / `leave`): RPC — клиентом с JWT менеджера, запись в `messages` — service role. Telegram 403 → `blocked` разбирается в обработчике, сервис про Telegram не знает (ADR-008). CORS: админка на другом домене; `*` безопасно, авторизация заголовком. `check:layers` проверяет и `manager-chat`.
- Бот: в ручном режиме свободный текст вне сценария записывается как `text` и остаётся без ответа; стикер/фото — «менеджер видит только текст». Сценарий, начатый гостем кнопкой во время режима, ведёт бот.
- Агент: реплика с `meta.manager` в истории идёт стороной модели с префиксом `[Restaurant manager]:`, в промпте правило не подтверждать и не опровергать обещания менеджера.
- Админка: «Подключиться к чату» (зелёная) вместо подписи «Менеджер отвечает вне бота»; поле ввода только в режиме (Enter — отправить, Shift+Enter — перенос, счётчик с 3500); плашка «Вы в чате · бот на паузе до HH:MM» + «Отключиться»; зелёный пузырь «Менеджер»; бейдж «менеджер» в списке. Метка из списка (Realtime), шапка — запасной источник. Истечение — таймер на метку (`useHandoffActive`, «сейчас» в состоянии: `Date.now()` в рендере ругает `react-hooks/purity`). Черновик переживает истечение режима.
- `database.types.ts` правлен руками: на dev миграции ещё нет, `types:gen` её не увидит. После выкатки перегенерировать и сверить.
**Осталось:**
- Интеграционные тесты (RPC в `chat.integration.test.ts`, сценарии ручного режима в `ai.integration.test.ts`) локально не прогонялись: Docker не запущен, а dev-БД без миграции. Прогонит job `integration` на PR.
- Саму функцию `manager-chat` вживую не вызывали: проверить на приёмке, что шлюз пропускает JWT менеджера (`verify_jwt`) и CORS с домена админки.
- Приёмка по спеке §5.
- 2026-11-11, выкатка: PR #4 смержен, CI зелёный, но deploy упал на бандлинге `manager-chat`: `Relative import path "@supabase/supabase-js" not prefixed with / or ./ or ../`. Причина: у новой функции нет секции в `config.toml` с `import_map = "./functions/deno.json"` (у `telegram-webhook` и `notify-guest` есть с S08). Локальный `deno check` и job'ы checks/integration этого не ловят: они читают общий `deno.json`. Добавлена секция `[functions.manager-chat]` с `verify_jwt = true` и `import_map`. Новая функция = новая секция в `config.toml`.
