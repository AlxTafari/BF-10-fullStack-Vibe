## 2026-11-08 — S07: каркас сценарных тестов, тексты, лимит кнопок

**Цель:** ответы на вопросы спеки §4 (все — по рекомендациям), затем код: сценарии §10, аудит обещаний, лимит кнопок, тесты админки последовательно.

**Решения:**
- `telegram-webhook/testing/`: `fakeTelegram.ts` хранит сообщения по чатам (правка/удаление как у Telegram, «not modified» и «not found» — те же ошибки), `guest.ts` — гость и `update_id` отрицательные (не пересекаются с реальными), `internals.ts` — проверка §10.10 на каждом тексте и подписи кнопки. Данные блюд тест берёт из БД, не из seed: меню в dev правится из админки.
- Первое нажатие на пустом чате — под несуществующим `message_id = 0` (как кнопка под удалённым сообщением); роутер уходит в fallback «отправить новое».
- 13 сценариев зелёные; поломка `BOOKING_SENT` → тест §10.5/6 падает; после прогона тестовых строк в БД нет.
- Тексты: «Бронь отменена.» (без «менеджер уведомлён»), подтверждение отмены без обещания уведомления, «…или связаться с менеджером через меню бота» вместо «написать нам», большая компания — «бронь через бота не оформить — оставьте запрос менеджеру».
- Лимит кнопок: `rate_limits.bucket` (`text`/`button`), PK `(external_user_id, bucket)`, `check_rate_limit(..., p_bucket default 'text')` — старый бот работает до деплоя. 30 нажатий / 60 с, проверка до `answerCallbackQuery`: `warn` — всплывашка, `drop` — пустой ответ, в `messages` ничего.
- Админка: `fileParallelism: false`. Находка: из трёх прогонов упал первый — Realtime-тест чата по таймауту 45 с (80 с прогон). Это холодный старт Realtime после простоя (как в LOG S06), а не пересечение файлов; последовательный запуск его не лечит.

**Осталось:** применить миграцию (`pnpm db:push`) и прогнать сценарий лимита кнопок; деплой `telegram-webhook` и `notify-guest`; решение по холодному Realtime; §2.В.2 (вливание Realtime в кэш); ручная приёмка по `TESTER.md`.

## 2026-11-08 — S07: миграция, гонка двойного тапа, прогрев Realtime, кэш админки

**Цель:** применить миграцию, деплой, закрыть код-часть спринта.

**Решения:**
- Миграция `button_rate_limit` применена к dev; `telegram-webhook` и `notify-guest` задеплоены.
- **Найдена гонка двойного тапа (S03):** `continueFlow` сохранял состояние и на шаге «Отправить». Отставший обработчик (прочитал диалог до чужой отправки) записывал отправленный черновик обратно, второй раз «выигрывал» его в `clearStateIfDraft` и отвечал гостю повторно. В живом прогоне окно узкое (1 падение из ~35), подтверждено детерминированным тестом «отставший обработчик». Исправление: на `submit` состояние не пишется — `submitFlow` работает с ним в памяти; при сбое вставки в БД остаётся сводка, повтор «Отправить» работает. Общая проблема «последняя запись побеждает» для обычных шагов сценария остаётся (двойной тап по одной кнопке её не задевает).
- Тест чата админки: прогрев Realtime пробами (до 60 с) до проверки — `SUBSCRIBED` приходит раньше, чем начинают идти `postgres_changes`. Три полных прогона подряд зелёные.
- §2.В.2: склейку `mergeBookingEvent`/`mergeGuestRequestEvent` проверяем на настоящем сторе без сети (`upsertQueryData`, клиент Supabase подменён `vi.mock`) — выносить ничего не пришлось. Не покрыто: событие во время загрузки списка и хук подписки — в `TESTER.md`.

**Осталось:** ручная приёмка (спека §5: тексты и лимит кнопок на живом боте, шаги S05 из `TESTER.md`).
