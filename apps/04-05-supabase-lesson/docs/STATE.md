## 2. Что построено

**Окружение.** Supabase-проект `myrest-guest-bot-dev` (dev), бот `@myrest_guest_bot`, webhook зарегистрирован, секреты выставлены. Данные — вымышленные (греческий ресторан Лавраки в Салониках, EUR).

**БД** (`supabase/migrations`, 9 штук): `restaurants`, `faq_entries`, `menu_categories`, `menu_items`, `conversations` (с `state jsonb` под S03), `messages` (индекс под курсорную пагинацию), `processed_updates`, `booking_requests` (с `replaces_id`), `guest_requests`. В `restaurants` добавлены `manager_chat_id`, `opening_hours` (jsonb, часы по дням недели). RLS включён везде. Политики для `authenticated`: справочники и членство (S04, ниже), чтение заявок (S05); чат (`conversations`, `messages`) для менеджера закрыт — доступ у бота через service role, откроется в S06. Seed идемпотентный: 1 ресторан, 6 FAQ, 4 категории, 10 блюд (в т.ч. без КБЖУ, в стоп-листе, неопубликованное). Перезалив — `pnpm db:seed:remote`.

**Edge Function `telegram-webhook`.** Проверка секрета, дедупликация по `update_id`, диалог и все сообщения (входящие, исходящие, нажатия кнопок) пишутся в БД. `/start` → приветствие и главное меню; «О ресторане» → карточка из БД; остальные кнопки — заглушки; свободный текст → подсказка про меню.

**Слои** (ADR-008): `domain` (форматирование «нет данных»), `repositories`, `services` (`getRestaurantInfo`, `openConversation`, `recordMessage`, `registerUpdate`), `telegram`, обработчики. Проверка слоёв — `pnpm check:layers`.

**S02: информация и меню.** «Частые вопросы» (список → ответ), «Меню» (категории → блюда → карточка: цена, состав, аллергены, порция, КБЖУ; «нет данных» вместо выдумок, ноль не путается с `null`; предупреждение про аллергию на каждой карточке; блюдо в стоп-листе помечено «недоступно»). Свободный текст — поиск блюда по названию (0 / 1 / несколько совпадений). Скрытые блюда отфильтрованы в SQL и недоступны по подделанному `callback_data`. Лимиты: поиск — 8, блюда категории — 10 (больше — подсказка искать по названию). Новые сервисы: `listFaq`, `getFaqAnswer`, `listMenuCategories`, `searchMenu`, `getDishDetails`. Домен: `formatPrice`, `formatDishCard`, `searchQuery`, `callbackData` — 19 тестов `deno test`. Миграций не было.

**S03: бронь, обращения, «Мои заявки».** Пошаговые сценарии (состояние в `conversations.state`, истекает через 30 минут): бронь — дата → «Обед/Ужин» → час → гости → имя → контакт → комментарий → сводка; обращение — тип → текст → контакт → сводка. Всё кнопками, кроме имени/контакта/числа гостей/текста; «← Назад» и «✖️ Отмена» на шагах, `/cancel`, кнопки меню сбрасывают сценарий. Даты, периоды и часы считаются по `opening_hours` и поясу ресторана (выходные скрыты, сегодня — не раньше «сейчас + 30 мин»), время хранится в UTC. Заявка создаётся только после «✅ Отправить», статус `pending`/`new`, тексты не обещают подтверждения. Идемпотентность: ключ `booking:/guest:<conversationId>:<draftId>`; сброс состояния атомарен (`clearStateIfDraft`) — при серии тапов гостю отвечает один обработчик, «Отправить» по уже отправленному молча игнорируется. Менеджеру — уведомление в `manager_chat_id` (сбой не теряет заявку, виден в `manager_notified_at`). «📋 Мои заявки»: список броней и обращений гостя, карточка со статусом, отмена (мгновенная, с уведомлением; отмена брони отменяет её ожидающее изменение), изменение = новая заявка с `replaces_id` (один ожидающий запрос на бронь держит частичный уникальный индекс). Новые сервисы: `createBookingRequest`, `createGuestRequest`, `notifyManager`, `startFlow`/`continueFlow`/`submitFlow`, `listMyRequests`, `getMyBooking`, `cancelMyBooking`. Миграции: `manager_chat_id` + `opening_hours` + `manager_notified_at`; `replaces_id` + индекс. Тестов: 81 `deno test` (домен: время/DST, часы, валидация, оба сценария, «Мои заявки») + интеграционный на dev-БД (дубль, гонка, чужой диалог, отмена, изменение).

**S04: админка (`admin/`).** Vite 8 + React 19 + TypeScript, shadcn/ui, Tailwind 4, TanStack Router, Redux Toolkit + RTK Query (`fakeBaseQuery` + `queryFn` с supabase-js, ошибки — сериализуемый `{message, code?}`). Каталоги: `api/` (единственное место с supabase-js), `domain/` (чистая логика), `features/`, `routes/`, `components/ui/`. Проверка слоёв — `pnpm check:layers:admin`.
- **Вход.** Supabase Auth, email + пароль; регистрации нет (`enable_signup = false`). Guard — `beforeLoad` в `_authed` (`hasSession()`), выход в другой вкладке ловит slice `auth` (одна подписка `onAuthStateChange`, на `SIGNED_OUT` — сброс кэша RTK). `getMe` — членство менеджера; без строки в `restaurant_managers` — «Нет доступа к ресторану». `safeRedirect` против open-redirect. Тихий refresh: `domain/refreshingFetch` подменяет `fetch` supabase-клиента — 401 на `/rest/v1/` → `refreshSession()` → один повтор, иначе локальный выход на `/login?redirect=…`.
- **RLS.** `restaurant_managers` (один пользователь — один ресторан), `is_manager_of()` (`security definer`, `search_path = ''`), политики на `restaurants` (select/update), `faq_entries`, `menu_categories`, `menu_items` (all, с `with check`). Для `anon` политик нет. Конспект — [`guides/supabase-rls-auth.md`](guides/supabase-rls-auth.md).
- **Валюта.** `restaurants.currency` вместо `menu_items.currency` (expand → деплой бота → contract; обе миграции накатаны). Бот правился только в `menuRepo`/`menu.ts`.
- **Экраны.** «Ресторан»: поля, `opening_hours` (7 дней, `null` «без ограничений» ≠ `{}` «закрыто всегда», `close <= open` не сохраняется, `24:00`), `manager_chat_id`, часовой пояс, валюта. FAQ: таблица, диалог, переключатель «опубликован», порядок перетаскиванием (`@dnd-kit`, клавиатура, нормализованный `sort_order`, оптимистично с откатом). «Меню» (`/menu/$categoryId`): категории (порядок, удаление с числом блюд), блюда (оптимистичные «Опубликовано»/«В наличии», бейджи «Черновик»/«Нет КБЖУ», предупреждение про лимит бота), форма блюда (пусто → `null`, `0` → `0`; аллергены в трёх состояниях `null`/`[]`/список). Общие состояния: skeleton / ошибка + «Повторить» / пусто.
- **Тесты.** 108 в `admin`: домен (часы, схемы форм и блюда, перестановка, refreshingFetch, ошибки) + 36 интеграционных RLS на dev-БД (`admin/tests/`: аноним, посторонний, менеджер чужого ресторана — запросами мимо интерфейса; свои данные, чистятся в `afterAll`). `deno test` бота — 81.

**S05: заявки и обращения в админке.** Менеджер видит брони и обращения своего ресторана, меняет их статусы, новые приходят по WebSocket без перезагрузки, гость получает решение по брони в Telegram.
- **БД** (две миграции). `20261015100000_requests_read_realtime`: `select`-политики на `booking_requests`/`guest_requests` (`is_manager_of`), публикация `supabase_realtime`, индекс `(restaurant_id, booking_at)`. `20261015110000_request_status_rpc`: колонка `guest_notified_at`, расширение `pg_net`, триггер `notify_guest_on_booking_decision`, RPC `set_booking_status` / `set_guest_request_status`.
- **Смена статуса — только RPC** (`security definer`, `search_path = ''`, права только `authenticated`): матрица переходов, `p_from` (ожидаемый статус, иначе `status_conflict`), запрет подтверждения прошедшей брони (`booking_in_past`), `original_not_active`, атомарные каскады (подтверждение изменения: исходная → `cancelled`, новая → `confirmed`; отмена исходной → ожидающее изменение `cancelled`), порядок блокировок «исходная → изменение» против взаимной блокировки. Прямой `update` менеджера политикой закрыт. Ошибки RPC — коды в `domain/rpcErrors`.
- **Уведомление гостя.** Триггер на `booking_requests` срабатывает только при флаге транзакции `app.notify_guest = '1'`, который ставит RPC вокруг основного `update` (отмена самим гостем и каскады не уведомляют). `net.http_post` → Edge Function `notify-guest` (`verify_jwt = false`, секрет в `x-notify-secret`; сервис `notifyGuestOfBookingDecision` пропускает устаревший статус, повторный вызов и **прошедшую бронь**; ошибка отправки не откатывает решение, остаётся `guest_notified_at = null`). URL и секрет триггера — в Vault (`notify_guest_url`, `notify_guest_secret`); секрет функции — `NOTIFY_GUEST_SECRET`. Только брони; по обращениям гость не уведомляется (ответ менеджера = чат, S06).
- **Админка.** `domain/` (матрица `bookingStatus`/`guestRequestStatus`, `rpcErrors`, `applyRowEvent`, `requestLists`, `contactLink`, `time`, `plural`), `api/requestsApi.ts` (запросы + RPC-мутации, `limit 100`), `api/requestsRealtime.ts` (канал `requests:<restaurantId>`, `setAuth` после refresh, пересчёт списков на `SUBSCRIBED`), экраны `/bookings`, `/requests` с карточкой в `sheet` (`/bookings/$bookingId`, `/requests/$requestId`), размер страницы 20/50/100 (`?size=`), звук (кнопка «🔔 Звук», по умолчанию выкл., только `INSERT`), бейджи и `(N)` в заголовке вкладки, индикатор связи. Комментарии и контакты гостя — только текстом.
- **Тесты.** Админка — 223 (домен + интеграционные на dev-БД: RLS, `realtime.integration` — Realtime+RLS и формат дат, `status-rpc.integration` — 41 тест: матрица, гонка, прошедшая бронь, каскады). Бот — 86 `deno test` (+ тексты и `isBookingPast` для `notify-guest`).

**Не закрыто осознанно:** чат в админке — S06; учёт столов и мест — отдельный спринт позже.

## 4. Хвосты, которые тянутся

- Автотесты бота: домен + интеграционный тест сервисов заявок (запускается с `--env-file`, без `SUPABASE_URL` пропускается). Сервисы S02, роутер и webhook — ручной приёмкой; остальные тесты на сервисы — до S07. Админка: домен и интеграционные тесты на dev-БД (RLS, Realtime, RPC статусов); UI-компоненты и вливание Realtime-событий в кэш RTK Query (`mergeBookingEvent`/`mergeGuestRequestEvent`, `useRequestsRealtime`) автотестами не покрыты.
- **Приёмка S05 неполная.** Не пройдены вручную: изменение брони (шаги 11–13), устойчивость Realtime — обрыв сети, истёкший токен, повторный вход (14–16), блокировка бота гостем (8а), доступ посторонних в браузере (17). Список, шаги и ожидаемое — в `TESTER.md` (локально, в `.gitignore`); пройти в S07.
- **Интеграционные тесты админки делят одну dev-БД и идут параллельно** — один полный прогон из четырёх дал одно падение (не воспроизведено, три следующих зелёных). Вероятная причина — пересечение файлов `rls`/`realtime`/`status-rpc` на общих данных; в S07/S08 развести (последовательный запуск или отдельная БД).
- Нет проверок слоёв (бот и админка) и тестов в CI — S08. RLS-тесту нужен service-role ключ в `.env`; в CI он станет секретом.
- Только dev-проект Supabase; отдельный проект под реальный ресторан не заводился.
- `deno.lock` не коммитится (генерируется при `deno check`).
- `deno lint` ругается на `npm:`-импорты (`no-import-prefix`) — как в коде S01; правило не настроено, в CI (S08) решить: отключить или перейти на `deno.json` imports.
- Часы работы — одно окно на день (без перерыва, без перехода через полночь), периоды «Обед 12–16 / Ужин 17–22» — константы в домене (`bookingRules.ts`), из админки не правятся (нужно перевести бота на данные). `manager_chat_id` теперь правится на экране «Ресторан»; узнать id — README.
- Учёт столов и занятости не ведётся: заявка `pending`, наличие места решает менеджер (роадмап §2).
- Блюда без категории (`category_id is null`) в боте находятся только поиском; в админке они видны в «Без категории». Фото блюд (`photo_url` — просто ссылка, загрузки в Storage нет) и поиск по алиасам не делались.
- Менеджер заводится руками (Dashboard + SQL, README); пароль менеджера прозвучал в сессии S04 — сменить.
- Токены сессии лежат в `localStorage` (стандарт supabase-js для SPA) — главный риск XSS. Меры: **CSP `script-src 'self'` при деплое админки (S08, см. [роадмап](roadmap/README.md) §3.2)**; не добавлять `dangerouslySetInnerHTML` и сторонние скрипты; текст гостей (S05 — заявки, S06 — чат) выводить только как текст (уже в инвариантах спек S05 §2.В и S06 §3.7).
- Перестановка FAQ/категорий — `upsert` целых строк: запись, удалённая в другой вкладке в момент перестановки, воскреснет. Один менеджер — принято; при нескольких заменить на RPC.
- `menu_items.currency` удалена; валюта одна на ресторан, цены при её смене не пересчитываются (предупреждение в форме).
- Политик на чат (`conversations`, `messages`) для менеджера нет — S06; RLS-тест расширяется вместе с ними (каждая новая политика — с кейсами аноним / посторонний / чужой менеджер).
- **Vault и секреты `notify-guest` заводятся руками в каждом проекте Supabase** (нет в миграциях намеренно): `notify_guest_url` (`https://<ref>.supabase.co/functions/v1/notify-guest`) и `notify_guest_secret` (= `NOTIFY_GUEST_SECRET` функции). Без них триггер лишь пишет `warning`, статус меняется, а гостю ничего не уходит (у заявки метка «гость не уведомлён»). Для нового проекта и для прод — в чек-лист S08.
- `pg_net` ставит запрос в очередь без ретраев: сбой `notify-guest` или Telegram → `guest_notified_at = null`, повторной отправки нет (менеджер видит метку). Кнопки «отправить ещё раз» нет.
- Прошедшей брони гость решения не получает (намеренно, окно давности не вводили); если окажется неудобно — пересмотреть.
- Просроченные `pending` не закрываются автоматически, только метка «время прошло» (В6).
- Звук — только в открытой вкладке, после клика по «🔔 Звук» (политика автовоспроизведения); push браузера не делали.
