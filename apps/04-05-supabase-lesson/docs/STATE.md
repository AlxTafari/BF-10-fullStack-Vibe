## 2. Что построено

**Окружение.** Supabase-проект `myrest-guest-bot-dev` (dev), бот `@myrest_guest_bot`, webhook зарегистрирован, секреты выставлены. Данные — вымышленные (греческий ресторан Лавраки в Салониках, EUR).

**БД** (базовые миграции S01–S03; полный список — `supabase/migrations`): `restaurants`, `faq_entries`, `menu_categories`, `menu_items`, `conversations` (с `state jsonb` под S03), `messages` (индекс под курсорную пагинацию), `processed_updates`, `booking_requests` (с `replaces_id`), `guest_requests`. В `restaurants` добавлены `manager_chat_id`, `opening_hours` (jsonb, часы по дням недели). RLS включён везде. Политики для `authenticated`: справочники и членство (S04, ниже), чтение заявок (S05); чат (`conversations`, `messages`) для менеджера закрыт — доступ у бота через service role, откроется в S06. Seed идемпотентный: 1 ресторан, 6 FAQ, 4 категории, 10 блюд (в т.ч. без КБЖУ, в стоп-листе, неопубликованное). Перезалив — `pnpm db:seed:remote`.

**Edge Function `telegram-webhook`.** Проверка секрета, дедупликация по `update_id`, диалог и все сообщения (входящие, исходящие, нажатия кнопок) пишутся в БД. `/start` → приветствие и главное меню; «О ресторане» → карточка из БД; остальные кнопки — заглушки; свободный текст → подсказка про меню.

**Слои** (ADR-008): `domain` (форматирование «нет данных»), `repositories`, `services` (`getRestaurantInfo`, `openConversation`, `recordMessage`, `registerUpdate`), `telegram`, обработчики. Проверка слоёв — `pnpm check:layers`.

**S02: информация и меню.** «Частые вопросы» (список → ответ), «Меню» (категории → блюда → карточка: цена, состав, аллергены, порция, КБЖУ; «нет данных» вместо выдумок, ноль не путается с `null`; предупреждение про аллергию на каждой карточке; блюдо в стоп-листе помечено «недоступно»). Свободный текст — поиск блюда по названию (0 / 1 / несколько совпадений). Скрытые блюда отфильтрованы в SQL и недоступны по подделанному `callback_data`. Лимиты: поиск — 8, блюда категории — 10 (больше — подсказка искать по названию). Новые сервисы: `listFaq`, `getFaqAnswer`, `listMenuCategories`, `searchMenu`, `getDishDetails`. Домен: `formatPrice`, `formatDishCard`, `searchQuery`, `callbackData` — 19 тестов `deno test`. Миграций не было.

**S03: бронь, обращения, «Мои заявки».** Пошаговые сценарии (состояние в `conversations.state`, истекает через 30 минут): бронь — дата → «Обед/Ужин» → час → гости → имя → контакт → комментарий → сводка; обращение — тип → текст → контакт → сводка. Всё кнопками, кроме имени/контакта/числа гостей/текста; «← Назад» и «✖️ Отмена» на шагах, `/cancel`, кнопки меню сбрасывают сценарий. Даты, периоды и часы считаются по `opening_hours` и поясу ресторана (выходные скрыты, сегодня — не раньше «сейчас + 30 мин»), время хранится в UTC. Заявка создаётся только после «✅ Отправить», статус `pending`/`new`, тексты не обещают подтверждения. Идемпотентность: ключ `booking:/guest:<conversationId>:<draftId>`; сброс состояния атомарен (`clearStateIfDraft`) — при серии тапов гостю отвечает один обработчик, «Отправить» по уже отправленному молча игнорируется. Менеджеру — уведомление в `manager_chat_id` (сбой не теряет заявку, виден в `manager_notified_at`). «📋 Мои заявки»: список броней и обращений гостя, карточка со статусом, отмена (мгновенная, с уведомлением; отмена брони отменяет её ожидающее изменение), изменение = новая заявка с `replaces_id` (один ожидающий запрос на бронь держит частичный уникальный индекс). Новые сервисы: `createBookingRequest`, `createGuestRequest`, `notifyManager`, `startFlow`/`continueFlow`/`submitFlow`, `listMyRequests`, `getMyBooking`, `cancelMyBooking`. Миграции: `manager_chat_id` + `opening_hours` + `manager_notified_at`; `replaces_id` + индекс. Тестов: 81 `deno test` (домен: время/DST, часы, валидация, оба сценария, «Мои заявки») + интеграционный на dev-БД (дубль, гонка, чужой диалог, отмена, изменение).

**S04: админка (`admin/`).** Vite 8 + React 19 + TypeScript, shadcn/ui, Tailwind 4, TanStack Router, Redux Toolkit + RTK Query (`fakeBaseQuery` + `queryFn` с supabase-js, ошибки — сериализуемый `{message, code?}`). Каталоги: `api/` (единственное место с supabase-js), `domain/` (чистая логика), `features/`, `routes/`, `components/ui/`. Проверка слоёв — `pnpm check:layers:admin`.
- **Вход.** Supabase Auth, email + пароль; регистрации нет (`enable_signup = false`). Guard — `beforeLoad` в `_authed` (`hasSession()`), выход в другой вкладке ловит slice `auth` (одна подписка `onAuthStateChange`, на `SIGNED_OUT` — сброс кэша RTK). `getMe` — членство менеджера; без строки в `restaurant_managers` — «Нет доступа к ресторану». `safeRedirect` против open-redirect. Тихий refresh: `domain/refreshingFetch` подменяет `fetch` supabase-клиента — 401 на `/rest/v1/` → `refreshSession()` → один повтор, иначе локальный выход на `/login?redirect=…`.
- **RLS.** `restaurant_managers` (один пользователь — один ресторан), `is_manager_of()` (`security definer`, `search_path = ''`), политики на `restaurants` (select/update), `faq_entries`, `menu_categories`, `menu_items` (all, с `with check`). Для `anon` политик нет. Конспект — [`guides/supabase-rls-auth.md`](guides/supabase-rls-auth.md).
- **Валюта.** `restaurants.currency` вместо `menu_items.currency` (expand → деплой бота → contract; обе миграции накатаны). Бот правился только в `menuRepo`/`menu.ts`.
- **Экраны.** «Ресторан»: поля, `opening_hours` (7 дней, `null` «без ограничений» ≠ `{}` «закрыто всегда», `close <= open` не сохраняется, `24:00`), `manager_chat_id`, часовой пояс, валюта. FAQ: таблица, диалог, переключатель «опубликован», порядок перетаскиванием (`@dnd-kit`, клавиатура, нормализованный `sort_order`, оптимистично с откатом). «Меню» (`/menu/$categoryId`): категории (порядок, удаление с числом блюд), блюда (оптимистичные «Опубликовано»/«В наличии», бейджи «Черновик»/«Нет КБЖУ», предупреждение про лимит бота), форма блюда (пусто → `null`, `0` → `0`; аллергены в трёх состояниях `null`/`[]`/список). Общие состояния: skeleton / ошибка + «Повторить» / пусто.
- **Тесты.** 108 в `admin`: домен (часы, схемы форм и блюда, перестановка, refreshingFetch, ошибки) + 36 интеграционных RLS на dev-БД (`admin/tests/`: аноним, посторонний, менеджер чужого ресторана — запросами мимо интерфейса; свои данные, чистятся в `afterAll`). `deno test` бота — 81.

**S05: заявки и обращения в админке.** Менеджер видит брони и обращения своего ресторана, меняет их статусы, новые приходят по WebSocket без перезагрузки, гость получает решение по брони в Telegram.
- **БД** (две миграции). `20261015100000_requests_read_realtime`: `select`-политики на `booking_requests`/`guest_requests` (`is_manager_of`), публикация `supabase_realtime`, индекс `(restaurant_id, booking_at)`. `20261015110000_request_status_rpc`: колонка `guest_notified_at`, расширение `pg_net`, триггер `notify_guest_on_booking_decision`, RPC `set_booking_status` / `set_guest_request_status`.
- **Смена статуса — только RPC** (`security definer`, `search_path = ''`, права только `authenticated`): матрица переходов, `p_from` (ожидаемый статус, иначе `status_conflict`), запрет подтверждения прошедшей брони (`booking_in_past`), `original_not_active`, атомарные каскады (подтверждение изменения: исходная → `cancelled`, новая → `confirmed`; отмена исходной → ожидающее изменение `cancelled`), порядок блокировок «исходная → изменение» против взаимной блокировки. Прямой `update` менеджера политикой закрыт. Ошибки RPC — коды в `domain/rpcErrors`.
- **Уведомление гостя.** Триггер на `booking_requests` срабатывает только при флаге транзакции `app.notify_guest = '1'`, который ставит RPC вокруг основного `update` (отмена самим гостем и каскады не уведомляют). `net.http_post` → Edge Function `notify-guest` (`verify_jwt = false`, секрет в `x-notify-secret`; сервис `notifyGuestOfBookingDecision` пропускает устаревший статус, повторный вызов и **прошедшую бронь**; ошибка отправки не откатывает решение, остаётся `guest_notified_at = null`). URL и секрет триггера — в Vault (`notify_guest_url`, `notify_guest_secret`); секрет функции — `NOTIFY_GUEST_SECRET`. Только брони; по обращениям гость не уведомляется (ответ менеджера = чат, S06).
- **Админка.** `domain/` (матрица `bookingStatus`/`guestRequestStatus`, `rpcErrors`, `applyRowEvent`, `requestLists`, `contactLink`, `time`, `plural`), `api/requestsApi.ts` (запросы + RPC-мутации, `limit 100`), `api/requestsRealtime.ts` (канал `requests:<restaurantId>`, `setAuth` после refresh, пересчёт списков на `SUBSCRIBED`), экраны `/bookings`, `/requests` с карточкой в `sheet` (`/bookings/$bookingId`, `/requests/$requestId`), размер страницы 20/50/100 (`?size=`), звук (кнопка «🔔 Звук», по умолчанию выкл., только `INSERT`), бейджи и `(N)` в заголовке вкладки, индикатор связи. Комментарии и контакты гостя — только текстом.
- **Тесты.** Админка — 223 (домен + интеграционные на dev-БД: RLS, `realtime.integration` — Realtime+RLS и формат дат, `status-rpc.integration` — 41 тест: матрица, гонка, прошедшая бронь, каскады). Бот — 86 `deno test` (+ тексты и `isBookingPast` для `notify-guest`).

**S06: чат гостей в админке.** Менеджер видит диалоги и переписку, новые сообщения приходят по WebSocket, непрочитанные общие на ресторан.
- **БД** (`20261018100000_admin_chat`): `messages.kind` (`text`/`button`), `conversations.last_message_at/preview/direction`, `manager_last_read_at`; триггер `messages_after_insert` (`greatest` по `last_message_at`, превью — только пока нет более позднего *текстового* сообщения); `select`-политики для менеджера, публикация Realtime; RPC `get_messages_page` (курсор `(created_at, id)`), `list_conversations_page`, `count_unread_conversations` (потолок 100), `mark_conversation_read` (запись отметки только через RPC, отметка растёт).
- **Админка.** `domain/`: `cursor` (`compareTimestamptz` — единственное место нормализации времени: дробь до 6 знаков, смещение в UTC), `messages`, `conversations` (`applyConversationEvent` → `{ list, needsRefresh }`), `chatTime`. `api/chatApi` (кэш с `merge`/`serializeQueryArgs`, курсор) и `chatRealtime` (подписка на `conversations` — на уровне `_authed`, на `messages` — маршрутная). Экран «Чаты»: список, лента с подгрузкой вверх, бейдж непрочитанных, связка с заявками.
- **Решения.** `unread_count` на клиенте не угадывается: событие не отличает текст гостя от нажатия кнопки, поэтому при входящем api-слой перечитывает список; событие `UPDATE` без смены `last_message_at` игнорируется (на этом держатся `last_nav` S06d и `setConversationState` бота). Realtime приходит с задержкой — интеграционные тесты ждут ≥ 10 с.

**S06c: ретеншн и антиспам.** Миграция `20261019100000_retention_antispam`: `kind='search'`, `rate_limits`, RPC `check_rate_limit` (атомарный upsert, одно предупреждение на окно), `purge_old_data()` (пачки по 5000, `pg_cron` 03:17 UTC; кнопки и поиск — 7 дней, текст — 90, `processed_updates` — 7, `rate_limits` — 1; диалоги с заявками не удаляются; превью стирается вместе с текстом). Бот: `domain/antispam`, ворота в `router.ts` после `buildContext` (первое сообщение гостя всегда проходит), лимит 3 сообщения / 30 с, текст ≤ 500 символов. **Лимит считает только свободный текст вне сценария** (команды, кнопки и шаги брони не считаются — найдено на приёмке). Предупреждение «Слишком много сообщений» удаляет сам бот через 30 с (`sendTemporary`, `EdgeRuntime.waitUntil`). Проверка — `pnpm db:check:retention`.

**S06d: анти-дубли в чате бота.** Миграция `20261019110000_last_nav`: `conversations.last_nav jsonb` (`{screen, message_id, at, faq_answer_id?}`), RPC `set_last_nav` и `set_faq_answer` (compare-and-swap, `service_role`). Telegram-клиент: `TelegramApiError`, `sendMessage` → `message_id`, `editMessageText`, `deleteMessage`, `clearKeyboard`. `domain/navigation.ts`: `decideNav` (окно дубля 120 с, строго `<`), `parseLastNav`. `logging.ts`: `replyNav` (правка / антидубль / CAS-гонка двойного тапа), `replyFaqAnswer` (клавиатура остаётся только у последнего ответа FAQ), `sendTemporary`. Экраны: `menu`, `info`, `cats`/`cat:<id>`/`dish:<id>` («Меню блюд» правится на месте), `flow:<draftId>` (сценарии: кнопки правят сообщение, после текстового ответа шаг рисуется заново внизу и прежнее удаляется, итог брони — новым сообщением внизу, менеджер уведомляется **до** ответа гостю). FAQ, поиск и «Мои заявки» не чистятся; в группах бот работает как раньше (`ctx.isPrivate`). Тесты бота — 131 (`navigation`, `logging` с подменёнными клиентами, `client`, `antispam`) + интеграционные `navigation.integration`, `antispam.integration`.

**S07: тесты сценариев и hardening.**
- **Сценарные тесты бота** (`telegram-webhook/scenarios.integration.test.ts`, 15 сценариев): настоящий `routeUpdate` + dev-БД, Telegram подменён через `deps.tg` (боевой код ради тестов не менялся). `testing/fakeTelegram.ts` хранит чат как Telegram (правка, удаление, ошибки «not modified» / «not found», `failNext` для 403); `testing/guest.ts` — гость и `update_id` отрицательные, `cleanup()` удаляет свои заявки, диалог, `rate_limits`, `processed_updates`; `testing/internals.ts` — критерий §10.10 (UUID, `null`/`undefined`, имена полей БД, `manager_chat_id`, неопубликованные блюда) на каждом тексте и подписи кнопки гостю. Покрыты все критерии плана §10 (кроме №8 — он в тестах RPC админки), плюс «Мои заявки», сбой уведомления менеджера, `/cancel`, двойной тап (параллельно и детерминированно), лимит кнопок. Данные блюд — из БД, не из seed. Тесты сервисов S02 отдельно не писались — их закрывают сценарии.
- **Гонка двойного тапа «Отправить» исправлена** (`services/flow.ts`, `continueFlow`): на шаге `submit` состояние не сохраняется — иначе отставший обработчик возвращал отправленный черновик и отвечал гостю второй раз.
- **Лимит нажатий кнопок** (миграция `20261108100000_button_rate_limit`): `rate_limits.bucket` (`text`/`button`), PK `(external_user_id, bucket)`, `check_rate_limit(..., p_bucket default 'text')`. 30 нажатий / 60 с (`BUTTON_RATE_MAX`, `domain/antispam.ts`); проверка в роутере до `answerCallbackQuery`: `warn` — всплывашка, `drop` — пустой ответ, в `messages` не пишется. Fail open.
- **Тексты без лишних обещаний:** «Бронь отменена.» (без «менеджер уведомлён»), подтверждение отмены без обещания уведомления, отмена рестораном — «…или связаться с менеджером через меню бота», компания больше лимита — «бронь через бота не оформить — оставьте запрос менеджеру».
- **Админка:** интеграционные тесты последовательно (`fileParallelism: false`); прогрев Realtime пробами в тесте чата; `src/api/requestsApi.merge.test.ts` — склейка `mergeBookingEvent`/`mergeGuestRequestEvent` на настоящем сторе без сети (перенос между списками, дубль, `DELETE` чужой строки, фильтр, карточка не создаётся и не откатывается).
- Тесты: бот — 157 (домен + интеграционные + сценарии), админка — 311.

- **Маршрутизация** (`telegram-webhook/handlers/ai.ts`, `voice.ts`): кнопка / команда / проверка шага — без LLM; не подошло шагу → агент с контекстом шага; при включённом AI текст на карточке брони/обращения — сразу агенту (поправка полей, пожелание, вопрос). - **Карточка заявки** (бронь и обращение): «Что-нибудь ещё?» вместо шага комментария, «✏️ Исправить» с меню полей (шаг `edit`, снимок `editFrom` для «Назад»), пометка ✏️ у изменённых пунктов; имя с телефоном одним сообщением, кнопка «Использовать Telegram».

Экран «Статистика AI»: день / неделя / месяц в поясе ресторана — ходы, токены, оценка стоимости по таблице цен с датами действия (`admin/src/domain`), запасные ответы по причинам, время ответа, распознавание голосовых отдельной группой; ссылки на Billing и Usage AI Studio (API баланса нет).
- **Качество.** `pnpm eval:ai [фильтр]` — эталонные фразы на настоящем Gemini (`supabase/scripts/`, ожидаемые и запрещённые tools, проверка черновика), последний прогон 20/20 на `flash-lite`. `check:layers`: `llm/` не импортирует приложение, `domain` и `telegram-webhook` не импортируют `llm/`.

## 4. Хвосты, которые тянутся

- Автотесты: бот — домен, интеграционные на dev-БД и сценарии через роутер (S07; без `SUPABASE_URL` пропускаются). Сам `index.ts` webhook (проверка секрета, разбор JSON) — только ручной приёмкой. Админка: UI-компоненты и хук `useRequestsRealtime` (событие во время загрузки списка) автотестами не покрыты.
- **Приёмка S05 неполная.** Не пройдены вручную: изменение брони (шаги 11–13), устойчивость Realtime — обрыв сети, истёкший токен, повторный вход (14–16), блокировка бота гостем (8а), доступ посторонних в браузере (17). Список, шаги и ожидаемое — в `TESTER.md` (локально, в `.gitignore`). На приёмках S07 и S08 не отмечены — пройти отдельным днём (решение S08, вопрос 7).
- **Приёмка S08 без п.3 и п.5.** Не проверено: прямой push в `main` с поломкой `BOOKING_SENT` → `integration` красный, `deploy` skipped → revert (п.3); push только в `apps/01-currency-bot/` → `guest-bot.yml` не запускается (п.5). Ветка `s08-acceptance` на GitHub не удалена.
- Локально интеграционные тесты делят одну dev-БД (в CI — своя БД на прогон). `realtime.integration.test.ts` без прогрева; в CI прошёл, при случайных падениях — добавить. ECR в CI иногда отвечает `Rate exceeded` при `supabase start` — CLI повторяет сам, иначе перезапуск.
- **Prod = dev-проект.** Миграции в `myrest-guest-bot-dev` катит только CI: миграция с ноутбука мимо `main` сломает следующий `db push` (голый `supabase db push` возможен, запрет по договорённости); функции с ноутбука перезапишет следующий push в `main`. Отдельный проект под реальный ресторан — по `prod-checklist.md` (приложение).
- Админка на GitHub Pages: нет защиты от встраивания во фрейм (`frame-ancestors` в `<meta>` не работает), глубокие ссылки со статусом 404. Нужны заголовки — переезд на хостинг со своими заголовками (Cloudflare Pages, как в спеке).
- Экрана сброса пароля в админке нет; «Send password recovery» из Dashboard отвечает `requested path is invalid` (Auth Redirect URLs). Пароль менеджера меняется через SQL Editor.
- `@claude` в Contributors на главной репозитория — из кэша GitHub после force-push (гипотеза), в истории `main` подписей нет; чинится поддержкой GitHub.
- Часы работы — одно окно на день (без перерыва, без перехода через полночь), периоды «Обед 12–16 / Ужин 17–22» — константы в домене (`bookingRules.ts`), из админки не правятся (нужно перевести бота на данные). `manager_chat_id` теперь правится на экране «Ресторан»; узнать id — README.
- Учёт столов и занятости не ведётся: заявка `pending`, наличие места решает менеджер (роадмап §2).
- Блюда без категории (`category_id is null`) в боте находятся только поиском; в админке они видны в «Без категории». Фото блюд (`photo_url` — просто ссылка, загрузки в Storage нет) и поиск по алиасам не делались.
- Менеджер заводится руками (Dashboard + SQL, README). Пароль менеджера задан заново в S08.
- Токены сессии лежат в `localStorage` (стандарт supabase-js для SPA) — главный риск XSS. Меры: **CSP `script-src 'self'` тегом `<meta>` (S08, проверено на Pages: inline-скрипт не выполняется)**; не добавлять `dangerouslySetInnerHTML` и сторонние скрипты; текст гостей (S05 — заявки, S06 — чат) выводить только как текст (уже в инвариантах спек S05 §2.В и S06 §3.7).
- Перестановка FAQ/категорий — `upsert` целых строк: запись, удалённая в другой вкладке в момент перестановки, воскреснет. Один менеджер — принято; при нескольких заменить на RPC.
- `menu_items.currency` удалена; валюта одна на ресторан, цены при её смене не пересчитываются (предупреждение в форме).
- Политики на чат (S06) покрыты RPC/RLS-проверками спринта; при любой новой политике — кейсы аноним / посторонний / чужой менеджер в `rls.integration.test.ts`.
- **Предупреждение антиспама удаляется фоновой задачей `waitUntil`:** если воркер убит раньше (деплой, сбой), оно останется в чате. Страховка при желании — `pg_cron` раз в минуту + функция очистки.
- **Открытый вопрос S06d №3:** можно ли править `editMessageText` сообщение старше суток — не проверено на живом боте (fallback на новое сообщение есть). Окно дубля 120 с — стартовое значение, правится константой `DUPLICATE_WINDOW_SECONDS`.
- Демо-диалог S06 (`db:seed:chat-demo`) после первой очистки теряет нажатия кнопок старше 7 дней.
- Не измерено на живом боте: поведение двойного тапа и гонки CAS (покрыто тестами с подменой и интеграционными на RPC).
- Состояние сценария — «последняя запись побеждает»: два одновременных РАЗНЫХ действия на обычном шаге (не «Отправить») могут перезаписать друг друга. Двойной тап по одной кнопке это не задевает; при жалобах — CAS по `draftId` + шагу.
- [BUG-003](bugs/backend/BUG-003-nedostupen-na-shage-gostej.md) — «вариант недоступен» на шаге гостей (найден в S08, гипотеза). [BUG-001](bugs/backend/BUG-001-antidubli-nedorabotany.md) (S06d, найден на приёмке S07) — повторные сообщения удаляются не во всех случаях (сценарий не записан). BUG-002 исправлен в S09.
- Уведомления гостю о решении по брони (`notify-guest`) — без кнопок; «через меню бота» гость ищет сам. Предложено: кнопки «📅 Забронировать» / «💬 Связаться с менеджером» / «📋 Мои заявки» под уведомлением.
- **Условие запуска на реальных гостях (S09, §4.10 спеки):** платный тариф Gemini **и** модель, у которой в прайсе платного уровня «Used to improve our products: No». Dev-проект уже на платном тарифе, `gemini-3.5-flash-lite` и `gemini-3.6-flash` — «No» (сверено 2026-11-11). Смена `GEMINI_MODEL` — только на модель с «No»; новый проект — то же условие.
- Качество ответов модели автотестами не проверяется (агент в тестах — на фейковом LLM): после смены модели или промпта — `pnpm eval:ai` вручную (нужны `GEMINI_API_KEY`/`GEMINI_MODEL` в `.env`).
- Цены моделей — константа в `admin/src/domain` с датами действия: новая модель или смена цены — коммит, модель без цены — предупреждение на экране «Статистика AI», в стоимость не входит.
- Распознавание голоса ошибается (`flash-lite` записал «три» вместо «четыре»): гость поправляет на карточке. Режим «размышлений» и `thinkingLevel: low` (меньше задержки и расхода) не пробовали — проверять на эталонах.
- Голосовые хранит только Telegram: срок хранения файла по `file_id` не гарантирован, старое голосовое может перестать играть в админке. Старый Safari может не играть OGG — есть «Скачать». Расшифровку, сделанную другим менеджером, видно после перезагрузки ленты (Realtime только на INSERT).
- Webhook синхронный на всё время хода агента (до 45 с): повторная доставка при таймауте отсекается `registerUpdate`, поведение Telegram при долгом ответе отдельно не замерялось.
- Справочник аллергенов в трёх местах (БД, бот, админка) — общего модуля нет, сверку держит RLS-тест. Новый аллерген — менять все три.
- «Скордалия» (`allergens = null`) есть в seed, но seed идёт только в `db reset`; на других БД такое блюдо заводится через админку.
- S06b: колонки статуса доставки нет — недоставленная реплика менеджера в журнал не попадает; `manager-chat` с CORS `*` (авторизация JWT). Новая Edge Function = новая секция в `config.toml` с `import_map`, иначе deploy падает на бандлинге (локальный `deno check` и CI-проверки это не ловят).
- `types:gen` админки пишет в файл через `>`: при сбое CLI `database.types.ts` обнулится — генерировать во временный файл и сравнивать.
- **Vault и секреты `notify-guest` заводятся руками в каждом проекте Supabase** (нет в миграциях намеренно): `notify_guest_url` (`https://<ref>.supabase.co/functions/v1/notify-guest`) и `notify_guest_secret` (= `NOTIFY_GUEST_SECRET` функции). Без них триггер лишь пишет `warning`, статус меняется, а гостю ничего не уходит (у заявки метка «гость не уведомлён»). Для нового проекта — `prod-checklist.md`.
- `pg_net` ставит запрос в очередь без ретраев: сбой `notify-guest` или Telegram → `guest_notified_at = null`, повторной отправки нет (менеджер видит метку). Кнопки «отправить ещё раз» нет.
- Прошедшей брони гость решения не получает (намеренно, окно давности не вводили); если окажется неудобно — пересмотреть.
- Просроченные `pending` не закрываются автоматически, только метка «время прошло» (В6).
- Звук — только в открытой вкладке, после клика по «🔔 Звук» (политика автовоспроизведения); push браузера не делали.
