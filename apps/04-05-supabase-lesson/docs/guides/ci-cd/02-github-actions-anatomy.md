# 02. Анатомия GitHub Actions на примере `guest-bot.yml`

Конспект к S08, сессия 1. Файл — [`.github/workflows/guest-bot.yml`](../../../../../.github/workflows/guest-bot.yml).
Номера строк — на момент сессии 1 (только job `checks`); после следующих сессий могут сдвинуться.

---

## 1. Где живёт workflow и кто его читает

GitHub ищет workflow **только** в `.github/workflows/` в корне репозитория. Поэтому файл лежит не в
`apps/04-05-supabase-lesson/`, а в корне монорепо, рядом с `ci.yml` конвертера валют.

Каждый файл там — отдельный независимый workflow. Они не знают друг о друге и запускаются по своим `on`.

## 2. `on` — когда запускаться (строки 9–23)

```yaml
on:
  push:
    branches: [main]
    paths: [...]
  pull_request:
    branches: [main]
    paths: [...]
  workflow_dispatch:
```

Три события:

- **`push` в `main`.** Срабатывает на прямой push **и на merge PR**. С точки зрения git merge — это новый коммит
  в `main`, то есть тот же push. Отдельного события «merge» для этого не нужно.
- **`pull_request` в `main`.** Срабатывает при открытии PR и на каждый новый коммит в его ветку. Важная деталь:
  GitHub проверяет **не голую ветку, а результат её слияния с текущим `main`** (временный merge-коммит). То есть
  PR проверяется так, как будто его уже влили.
- **`workflow_dispatch`.** Кнопка «Run workflow» во вкладке Actions. Нужна, чтобы перезапустить руками, не делая
  пустой коммит.

Push в ветку без PR не запускает ничего: ни `push` (там только `main`), ни `pull_request` (PR нет). Ветку можно
спокойно пушить «в черновик».

### `paths` — фильтр по файлам

```yaml
paths:
  - "apps/04-05-supabase-lesson/**"
  - ".github/workflows/guest-bot.yml"
```

Workflow запустится, только если коммит (или PR) меняет хотя бы один файл под этими шаблонами. Это монорепо:
правка конвертера валют не должна гонять тесты гостевого бота. Поэтому и старый `ci.yml` получил свой `paths`
по `apps/01-currency-bot/**`.

Вторая строка — сам файл workflow. Без неё правка YAML (например, новый шаг) workflow не запустила бы, и
проверить правку было бы нечем. Частая ловушка.

## 3. `concurrency` — что делать с наложением прогонов (строки 27–29)

```yaml
concurrency:
  group: guest-bot-checks-${{ github.ref }}
  cancel-in-progress: true
```

Прогоны с одинаковой `group` не идут одновременно. `github.ref` — ветка (`refs/heads/main`) или PR
(`refs/pull/12/merge`), поэтому у каждой ветки и каждого PR своя группа.

`cancel-in-progress: true`: пушнул, через минуту пушнул ещё раз — первый прогон отменяется. Его результат уже
устарел, а минуты и время ожидания тратятся зря.

Для деплоя (сессия 3) будет **другая** группа и `cancel-in-progress: false`. Отменить проверки безопасно,
отменить `supabase db push` посреди миграции — нет.

`${{ ... }}` — выражение GitHub Actions. Подставляется до запуска шага. Внутри доступны контексты: `github`
(событие, ветка, коммит), `secrets`, `vars`, `env`, `needs` и другие.

## 4. `permissions` — права токена (строки 32–33)

В каждый job GitHub автоматически выдаёт токен `GITHUB_TOKEN`. Им actions ходят в API GitHub (скачать код,
оставить комментарий, создать релиз). `contents: read` — только чтение кода. Проверкам больше не нужно. Если
какой-нибудь action окажется скомпрометирован, он не сможет пушить в репозиторий.

Принцип — **минимальные права**: шире выдаётся конкретному job'у, когда понадобится.

## 5. `jobs` — что делать (строки 35+)

```yaml
jobs:
  checks:
    name: Checks (types, lint, layers, unit tests, build)
    runs-on: ubuntu-latest
    timeout-minutes: 15
    defaults:
      run:
        working-directory: apps/04-05-supabase-lesson
    steps: [...]
```

- **`checks`** — id job'а. По нему на job ссылаются другие (`needs: [checks]`). `name` — подпись в интерфейсе.
- **`runs-on: ubuntu-latest`** — на чём выполнять. Каждый job получает новую виртуалку. Файлы между job'ами
  не переносятся: что `checks` собрал, `deploy` не увидит (для этого есть artifacts).
- **`timeout-minutes`** — потолок. По умолчанию 360 минут: зависший шаг молча съел бы шесть часов.
- **`defaults.run.working-directory`** — из какой папки выполнять `run`-шаги. Репозиторий скачивается в корень,
  а наши скрипты (`pnpm check:layers`) объявлены в `package.json` приложения. Шаги Deno переопределяют папку
  на `supabase/functions`: там лежит `deno.json`.

С сессии 2 job'ов два: `checks` и `integration` идут параллельно, каждый на своей виртуалке (разбор
`integration` — заметка 03). В сессии 3 добавится `deploy` с `needs: [checks, integration]`.

## 6. `steps` — шаги

Два вида шагов:

```yaml
- uses: actions/setup-node@v7     # готовый action
  with:
    node-version: 24
    cache: pnpm

- name: "Bot: deno lint"           # своя команда
  working-directory: apps/04-05-supabase-lesson/supabase/functions
  run: deno lint
```

- **`uses`** — подключить чужой action. `with` — его параметры (у каждого action свои, описаны в его
  `action.yml`). Версия после `@` — тег. `@v7` означает «последний релиз седьмой мажорной версии»: патчи
  приходят сами, ломающие изменения — нет.
- **`run`** — выполнить команду в shell (bash на Ubuntu). Если команда вернула не 0, шаг красный, следующие
  шаги не выполняются, job красный.

### Наши шаги по порядку

1. **`actions/checkout`** — скачать репозиторий. Без него на виртуалке пусто.
2. **`pnpm/action-setup`** — поставить pnpm. Версия 11 — та же, что локально: `pnpm-workspace.yaml` использует
   `allowBuilds`, которого в старых версиях нет.
3. **`actions/setup-node` с `cache: pnpm`** — Node 24 и кэш хранилища pnpm. Ключ кэша — хэш
   `pnpm-lock.yaml`. Lock не менялся — пакеты берутся из кэша за секунды, а не качаются заново.
4. **`denoland/setup-deno`** — Deno 2.9.7, как локально. Формат `deno.lock` зависит от версии Deno. Другая
   версия могла бы прочитать lock иначе.
5. **`pnpm install --frozen-lockfile`** — поставить зависимости **строго по lock-файлу**. Если `package.json`
   и `pnpm-lock.yaml` разошлись, ошибка. Без флага pnpm молча обновил бы lock, и CI проверял бы не те версии,
   что у тебя.
6. **Бот:** слои → `deno check --frozen .` → `deno lint` → `deno test --allow-env --frozen`. `--frozen` у Deno —
   то же самое для `supabase/functions/deno.lock`. Интеграционные тесты без `SUPABASE_URL` пропускаются сами
   (так они написаны в S03–S07), здесь идёт только домен.
7. **Админка:** слои → `typecheck` → `lint` → `build`. Тестов админки здесь нет: интеграционным нужна БД, а
   юнит-тесты не дублируем (S08, вопрос 8) — всё пойдёт в `integration`.

Каждая проверка — **отдельный шаг**, а не одна длинная команда через `&&`. Тогда в интерфейсе сразу видно,
*что именно* упало, без чтения всего лога.

## 7. Где смотреть результат

- **Вкладка Actions** репозитория → workflow «Guest bot» слева → прогон → job → шаг. Лог каждого шага
  разворачивается отдельно. Упавший шаг раскрыт сразу.
- **Значок у коммита** в истории на GitHub: жёлтый кружок — идёт, зелёная галочка — прошло, красный крестик —
  упало.
- **Страница PR** — блок проверок внизу, рядом с кнопкой merge. Пока проверки красные, кнопка остаётся
  активной (branch protection выключена), но крестик видно.
- **Перезапуск:** в прогоне кнопка «Re-run jobs» (все или только упавшие). Или «Run workflow» на странице
  workflow (`workflow_dispatch`).
- **Письмо:** GitHub по умолчанию пишет автору коммита, если прогон упал.

## 8. Branch protection — что это и почему выключено

Правило в Settings → Branches (или Rules → Rulesets) для `main`. Типичный набор:

- «Require a pull request before merging» — в `main` нельзя push напрямую, только через PR;
- «Require status checks to pass» — merge заблокирован, пока выбранные job'ы не зелёные;
- «Require branches to be up to date» — ветка PR должна содержать свежий `main`.

У нас всё это выключено: прямой push в `main` разрешён наравне с PR (S08). От красного кода в prod защищает
`needs:` у деплоя (заметка 01, §4). Включить защиту можно в любой момент, workflow для этого менять не нужно:
нужные job'ы уже публикуют статусы, их остаётся отметить в правиле.

## 9. Как проверять workflow, не пуша вслепую

Цикл «поправил YAML → push → ждёшь две минуты → опечатка» медленный. Что помогает:

- **Команды шагов — сначала в терминале.** Всё, что в `run`, — обычные команды. В сессии 1 каждый шаг `checks`
  сначала прошёл локально.
- **`actionlint`** (`brew install actionlint`) — линтер для workflow: ловит опечатки в ключах, неверные
  выражения `${{ }}`, несуществующие входы actions.
- **Ветка + PR** — проверить правку workflow, не трогая `main`. Workflow из ветки PR запускается именно в той
  версии, что в ветке.
- **Ветка + `workflow_dispatch`** — без PR: `gh workflow run guest-bot.yml --ref <ветка>`. Запустится версия
  workflow из ветки (сам файл с `workflow_dispatch` должен уже быть в `main`). Так в сессии 2 отлаживался
  `integration`: два прогона в ветке, в `main` — уже зелёный.
