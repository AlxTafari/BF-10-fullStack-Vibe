# 03. База данных в CI: Supabase внутри раннера

Конспект к S08, сессия 2. Job `integration` в [`.github/workflows/guest-bot.yml`](../../../../../.github/workflows/guest-bot.yml)
(строки 103–188 на момент сессии 2). Цифры ниже взяты из настоящих прогонов в ветке `s08-integration`.

---

## 1. Зачем тестам своя БД

Интеграционные тесты (RLS, RPC статусов, Realtime, сценарии бота) ходят в настоящий Postgres. Варианты:

| | Общая dev-БД | Supabase в раннере |
|---|---|---|
| Секреты в GitHub | service-role ключ dev-проекта | не нужны: ключи локального стека — общие демо-ключи |
| Прогоны мешают друг другу | да: два PR одновременно пишут в одни таблицы | нет: у каждого job'а своя виртуалка и своя БД |
| Мешают ручной работе | тестовые рестораны и заявки в dev-админке | нет |
| Проверка миграций | только новая, поверх уже накатанных | **все с нуля**, по порядку |
| Время | быстрее (БД уже есть) | плюс ~1 минута на `supabase start` |

Выбрано второе (спека S08, §2.Б.2). Минута на старт окупается тем, что «зелёный» значит «работает на
пустом месте», а не «работает на моей dev-БД».

## 2. Что такое `supabase start` в раннере

Раннер `ubuntu-latest` — виртуалка с уже установленным Docker. `supabase start` делает то же, что у тебя
локально:

1. Скачивает образы контейнеров (Postgres, Auth, PostgREST, Realtime, Kong, Edge Runtime).
2. Создаёт пустую БД и применяет **все** файлы `supabase/migrations/` по порядку имён.
3. Выполняет `supabase/seed.sql` (`[db.seed]` в `config.toml`).
4. Запускает остальные контейнеры и поднимает API на `http://127.0.0.1:54321`.

Из лога прогона (сокращено):

```
Applying migration 20261012100000_schema.sql...
...
Applying migration 20261108100000_button_rate_limit.sql...
Seeding data from supabase/seed.sql...
Started supabase local development setup.
```

После job'а виртуалка уничтожается вместе с контейнерами. Чистить за собой (`supabase stop`) не нужно.

### `-x` — какие контейнеры не нужны

```yaml
run: supabase start -x studio,mailpit,storage-api,imgproxy,postgres-meta,logflare,vector,supavisor
```

Список допустимых имён печатает `supabase start --help`. Отключено то, что тестам не нужно: веб-интерфейс
(`studio`) и его API (`postgres-meta`), почта (`mailpit`), файлы (`storage-api`, `imgproxy` — в проекте нигде
нет `storage.from`), логи (`logflare`, `vector`), пулер соединений (`supavisor`). Меньше контейнеров — быстрее
старт и меньше точек отказа.

Остаются: `postgres`, `gotrue` (Auth — тесты админки входят менеджером), `postgrest` (REST API, через него
ходит supabase-js), `realtime` (тесты WebSocket), `kong` (шлюз, единая точка `:54321`), `edge-runtime` (функции).

### Версия CLI

```yaml
- uses: supabase/setup-cli@v3
  with:
    version: 2.117.0
```

Почему не `pnpm exec supabase` из `node_modules`: npm-пакет `supabase` при установке скачивает бинарник
скриптом `postinstall`. pnpm 10+ такие скрипты по умолчанию не выполняет: в `allowBuilds` (`pnpm-workspace.yaml`)
разрешён только `esbuild`. Поэтому CLI ставит отдельный action, а версия прописана руками — та же, что в
`pnpm-lock.yaml`. Обновил CLI локально — обнови и здесь.

## 3. `.env` из `supabase status`

Тесты бота и админки берут адрес и ключи из `apps/04-05-supabase-lesson/.env`: бот через
`deno test --env-file=../../.env`, админка через `loadEnv` в `admin/vite.config.ts`. Ради CI тесты не
менялись: workflow просто создаёт этот файл.

```bash
supabase status -o env \
  --override-name api.url=SUPABASE_URL \
  --override-name auth.anon_key=SUPABASE_ANON_KEY \
  --override-name auth.service_role_key=SUPABASE_SERVICE_ROLE_KEY > .env
```

- `-o env` печатает переменные в формате `ИМЯ="значение"`, готовом для `.env`.
- Свои имена у CLI другие (`API_URL`, `ANON_KEY`, `SERVICE_ROLE_KEY`). `--override-name` переименовывает их
  прямо при выводе, без `sed`.
- Остальные переменные вывода (`DB_URL`, `JWT_SECRET`, …) тоже попадают в файл. Тестам они не мешают.

Следом идёт проверка, что все три имени в файле есть и не пустые. Сам файл в лог не печатается. Ключи
локального стека — общие демо-ключи (CLI сам пишет: «API keys and JWT secrets are shared defaults»), утечки тут
нет. Но привычка «секретные файлы не выводим» должна быть одинаковой везде, иначе однажды так же выведешь
настоящий `.env` в job'е деплоя.

## 4. Проверка, что функции находят импорты

В сессии 1 импорты бота переехали в общий `supabase/functions/deno.json`, а в `config.toml` функциям прописан
`import_map = "./functions/deno.json"`. `deno check` в `checks` это видит, но функции в Supabase исполняет не
наш Deno, а **edge runtime** — у него своя логика поиска конфигурации. Проверить можно только запуском.

`supabase start` поднимает контейнер `edge-runtime`, и он сразу обслуживает все функции из
`supabase/functions/` с настройками из `config.toml`. Шаг workflow отправляет каждой функции POST без секрета:

```
telegram-webhook: HTTP 401, body: forbidden
notify-guest: HTTP 401, body: forbidden
```

Почему это доказательство:

- Секретов функций в раннере нет (`TELEGRAM_WEBHOOK_SECRET`, `NOTIFY_GUEST_SECRET`), поэтому наш код отвечает
  `401 forbidden`. Чтобы ответить, функция должна была загрузиться, то есть разрешить **все** импорты.
- Если импорт не найден, функция не стартует, ответ — 5xx.
- 401 умеет отдавать и шлюз Kong (проверка JWT), но с JSON вида `{"msg": ...}`. Поэтому шаг сверяет не только
  код, но и тело `forbidden`. У обеих функций `verify_jwt = false`, так что до Kong-проверки дело не доходит.

Окончательная проверка — первый деплой в prod (сессия 3): облачный рантайм может отличаться от локального.

## 5. Что нашёл первый прогон

Первый прогон: функции загрузились, все 157 тестов бота зелёные, а **все четыре интеграционных файла админки
упали** на подготовке данных:

```
Error: sign in manager-a: Email logins are disabled
```

Причина — в `supabase/config.toml`:

```toml
[auth]
enable_signup = false        # регистрация закрыта — это и было нужно

[auth.email]
enable_signup = false        # а это выключило провайдер email целиком
```

Комментарий в шаблоне конфига обещает «disallow new user signups via email», но CLI превращает этот флаг в
переменную `GOTRUE_EXTERNAL_EMAIL_ENABLED`, то есть выключает email-вход вообще. Регистрацию закрывает общий
`[auth] enable_signup`, его достаточно. Исправление — `[auth.email] enable_signup = true`.

Почему раньше не всплывало: облачный dev-проект `config.toml` не читает (его настройки — в Dashboard), а
локальный стек до S08 почти не запускали. Это ровно тот класс ошибок, ради которого БД поднимается с нуля:
**конфиг, который никогда не применялся**.

Что **не** подтвердилось из рисков спеки:

- Тесты не полагаются на данные dev-БД вне `seed.sql`: менеджеров и рестораны тесты создают сами, бот берёт
  ресторан из seed.
- Realtime после холодного старта успел: `realtime.integration.test.ts` прошёл без прогрева.
- Отсутствие секретов `notify_guest_*` в Vault тесты статусов не ломает.

## 6. Время и что может пойти не так

Второй прогон, всё зелёное:

| Шаг | Время |
|---|---|
| `checks` целиком (параллельно) | 44 с |
| `integration` целиком | 2 мин 03 с |
| ↳ `supabase start` (скачивание образов + миграции) | ~62 с |
| ↳ тесты бота (157) | 8 с |
| ↳ тесты админки (311) | 22 с |

Частые причины падения `integration`:

- **Реестр образов.** В первом прогоне был `error from registry: Rate exceeded` — CLI сам повторил через 4 с.
  Если повторы не спасут, прогон упадёт на `Start Supabase` без связи с кодом: просто перезапустить
  (Re-run failed jobs).
- **Миграция, которая работала только поверх dev.** Упадёт `Start Supabase` с именем файла миграции.
- **Тест, полагающийся на данные dev-БД.** Упадёт тест; данных нет в `seed.sql`.
- **Конфиг локального стека** (`config.toml`), как в §5.

На любом падении шаг `Supabase logs on failure` (`if: failure()`) печатает `supabase status` и последние 300
строк лога каждого контейнера, каждый в сворачиваемой группе. Без этого разбираться пришлось бы вслепую:
виртуалка исчезает вместе с контейнерами.
