## 1. Что происходит после push в `main`

```
push в main
  ├─ checks       (типы, линтер, слои, юнит-тесты, сборка)   ~45 с  ┐ параллельно
  └─ integration  (Supabase в раннере, все тесты)            ~2,5 мин┘
        │ оба зелёные
        ▼
     deploy        environment: production                    ~25 с
        1. Check prod variables
        2. Prod: migrations   supabase link + проверка пулера + db push
        3. Prod: functions    supabase functions deploy --use-api
        4. Smoke test functions
        │ зелёный
        ▼
     deploy-admin  environment: github-pages                  ~50 с
        1. Check admin variables
        2. Admin: build for prod   (+ проверка CSP, + 404.html)
        3. upload-pages-artifact
        4. deploy-pages
        5. Smoke test admin
```

Весь путь от push до новой админки — около 4 минут. Падение любого шага останавливает всё, что после него.

## 2. Почему именно такой порядок: схема → функции → админка

**Схема раньше кода.** Если функция, которая пишет в новую колонку, выйдет раньше колонки, первый же гость
получит ошибку. Поэтому сначала `db push`, потом `functions deploy`.

**Админка после функций и схемы.** Админка ходит в те же таблицы и RPC. Новая админка со старой схемой —
та же проблема, что у функций. Поэтому `deploy-admin` стоит в `needs: deploy`, а не параллельно.

**Между шагами prod живёт в смешанном состоянии.** Миграции применились, а функции ещё старые — несколько
секунд (на прогоне `bffe0da` шаг функций занял 4 с). Если шаг функций упадёт, это состояние останется до
следующего деплоя. Значит, **каждая миграция обязана работать со старым кодом**. Это правило называется
expand → contract.

## 3. Expand → contract: как менять схему, не ломая работающий код

Ломающее изменение схемы (переименовать, удалить, сделать обязательным) делится на два деплоя:

1. **Expand (расширить).** Добавить новое, не трогая старое. Старый код продолжает работать, новый код
   пользуется новым.
2. **Contract (сузить).** Когда во всём prod уже новый код, отдельной миграцией убрать старое.

Примеры из проекта:

| Изменение | Expand | Contract |
|---|---|---|
| Валюта с блюда на ресторан (S04) | `20261014110000_restaurant_currency.sql`: колонка у ресторана | `20261014120000_drop_item_currency.sql`: удалить колонку у блюда |
| Лимит нажатий кнопок (S07) | `20261108100000_button_rate_limit.sql`: новый параметр `p_bucket text default 'text'` | — (умолчание остаётся) |

Второй пример — expand внутри одной миграции. Уже задеплоенный бот зовёт `check_rate_limit` без `p_bucket` и
продолжает работать, а новый бот передаёт параметр. Комментарий об этом есть прямо в миграции.

Чего нельзя делать одной миграцией вместе с кодом:

- переименовать колонку (старый код ищет старое имя);
- удалить колонку или функцию, которую читает текущий код;
- добавить `not null` без `default` (старый код не передаёт значение);
- поменять сигнатуру RPC без умолчаний.

## 4. Почему миграции катит только CI

До S08 миграции в удалённый проект катились с ноутбука (`pnpm db:push`). Теперь это делает только CI, а
скрипт `db:push` печатает подсказку и выходит с ошибкой.

Причина — история миграций. Supabase хранит в удалённой БД список применённых версий
(`supabase_migrations.schema_migrations`). `db push` сравнивает его с файлами `supabase/migrations/`. Сценарий
поломки:

1. В ветке `feature` пишешь миграцию `20261120…_x.sql` и катишь её с ноутбука.
2. Ветку не мержишь (передумал, переделал под другим именем).
3. Следующий деплой из `main`: в удалённой истории есть версия, которой нет в файлах. `db push` падает с
   `Remote migration versions not found in local migrations directory`.

С CI в удалённую БД попадает только то, что дошло до `main`. Новая миграция проверяется:

- **в PR** — job `integration` накатывает все миграции с нуля на чистую БД раннера ([03](03-database-in-ci.md));
- **локально** — `pnpm start` + `pnpm db:reset`.

Голый `supabase db push` из терминала по-прежнему сработает: CLI на ноутбуке ходит через токен `supabase login`,
пароль БД ему не нужен. Запрет держится на договорённости, а скрипт — напоминание.

Функции с ноутбука катить можно (`pnpm deploy:rest`): истории у функций нет, следующий push в `main` просто
перезапишет их кодом из `main`.

Сверка после деплоя (шаг Д2 первого запуска показал 13/13):

```bash
pnpm --filter 04-05-lesson exec supabase migration list --linked
```

## 5. `concurrency`: два деплоя не идут одновременно

Два уровня:

```yaml
# весь workflow
concurrency:
  group: guest-bot-checks-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

# job deploy
concurrency:
  group: guest-bot-prod
  cancel-in-progress: false
```

- **На PR** новый коммит отменяет старый прогон: проверять устаревший код незачем.
- **В `main` не отменяем никогда.** Отмена прогона целиком убила бы `deploy` посреди `db push`. Сначала было
  `cancel-in-progress: true` для всех событий — второй push в `main` отменил бы первый вместе с деплоем.
  Исправлено до первого деплоя.
- Второй push в `main` **ждёт**, пока первый прогон закончится. Третий заменяет ждущий второй: в prod уедет
  самый свежий код, промежуточный пропускается.
- У `deploy` и `deploy-admin` свои группы (`guest-bot-prod`, `guest-bot-pages`) без отмены: даже ручной
  запуск не пойдёт параллельно с автоматическим.

Миграция, прерванная на середине, хуже упавшей. Postgres откатит незавершённую транзакцию, но если миграция
не в одной транзакции (например, `create index concurrently`), БД останется в промежуточном состоянии.

## 6. Smoke-проверки: что ловят и чего нет

| Проверка | Как | Что ловит |
|---|---|---|
| Функции | `POST` без секрета → ждём **401** и тело `forbidden` | функция загрузилась, импорты нашлись, первая строка кода выполнилась |
| Админка `/` | **200**, в HTML есть `Content-Security-Policy` и `id="root"` | сайт опубликован, сборка с CSP под этот проект |
| Админка `/bookings/smoke` | **404** с той же разметкой | `404.html` на месте, глубокие ссылки открываются ([06](06-spa-hosting-and-csp.md)) |

Ждём 401, а не 200, потому что без секрета функция и должна отказать. 401 доказывает, что дошли до нашего
кода. 5xx значит, что функция не стартовала. Pages раздаёт новый деплой не мгновенно, поэтому у админки до 6
попыток с паузой 10 с (на зелёном прогоне хватило первой).

Чего smoke **не** ловит: сломанную бизнес-логику, ошибку в сценарии брони, сломанный Realtime, нарушение CSP
в браузере. Это ловят тесты в `integration` до деплоя и ручная проверка после (шаг Е чек-листа). Smoke
отвечает на один вопрос: «выкладка не превратила prod в 500».

## 7. Откат

### Код (функции и админка): откат = новый деплой старого кода

```bash
git revert <плохой коммит>
git push
```

Revert — новый коммит, отменяющий изменения. Он проходит весь конвейер (~4 мин) и выкладывает функции и
админку в прежнем виде. История в `main` остаётся честной: видно и ошибку, и откат.

**Ручной запуск (`workflow_dispatch`) для отката не подходит.** У `deploy` условие
`github.ref == 'refs/heads/main'`, а запуск с ветки `main` берёт её последний коммит, то есть тот же плохой.
Спека S08 предполагала откат функций запуском со старого коммита, но с текущим условием это не работает.

**Аварийно, если ждать 4 минуты нельзя:** функции можно выкатить с ноутбука из старого коммита (из корня
репозитория):

```bash
git switch --detach <хороший коммит>
pnpm deploy:rest
git switch main
```

Это временная мера: следующий push в `main` перезапишет функции. Revert в `main` всё равно нужен.

### Схема: только вперёд

Автоматического отката миграций нет и не будет (спека S08, §1 «вне рамок»). Причины:

- данные: откат `add column` теряет то, что успели записать; откат `drop column` невозможен — данных уже нет;
- `down`-миграции почти никто не тестирует, они ломаются в самый неподходящий момент.

Плохая миграция исправляется **новой миграцией** с новой версией. Файл уже применённой миграции не правится
никогда: в prod она уже записана в историю, и правка в файле там не выполнится.

Expand → contract делает откат кода безопасным: после revert старый код работает с новой схемой, потому что
миграция его не сломала (§3). Поэтому правило §3 — не формальность, а то, что делает revert рабочим.

## 9. Шпаргалка

- Новая миграция → совместима со старым кодом? Нет → разбить на expand и contract.
- Проверить миграцию → PR (`integration`) или `pnpm start && pnpm db:reset`. Не `db push`.
- Плохой деплой кода → `git revert` + push.
- Плохая миграция → новая миграция вперёд, старый файл не трогать.
- Деплой упал на середине → смотреть, какой шаг. До `db push` prod не тронут; после — новая схема со старым
  кодом, и это безопасно, если соблюдён expand → contract.
