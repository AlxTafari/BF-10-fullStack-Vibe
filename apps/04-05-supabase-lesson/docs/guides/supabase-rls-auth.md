# Supabase: Auth и RLS — как это работает

Конспект к спринту S04. Объясняет, на чём держится безопасность админки. Не спека и не ADR — учебная заметка.

---

## 1. Проблема: браузер ходит в БД напрямую

У админки нет своего сервера. Браузер использует `supabase-js` и обращается к Postgres через PostgREST (HTTP API поверх БД). Значит:

- **anon-ключ лежит в бандле** — его видит любой, кто открыл DevTools. Он публичный по природе.
- Любой может взять этот ключ и отправить `select * from restaurants` мимо вашего интерфейса.

Скрытая кнопка или проверка в React — это удобство, а не защита. Защита должна жить **в самой БД**. Это и есть RLS.

---

## 2. Auth: «кто ты»

Supabase Auth — отдельный сервис (схема `auth` в той же БД). Он отвечает на один вопрос: **кто делает запрос**.

### Поток входа (email + пароль)

1. Клиент: `supabase.auth.signInWithPassword({ email, password })`.
2. Auth проверяет пароль (хеш хранится в `auth.users`).
3. Возвращает **session**: `access_token` (JWT, живёт ~1 час) и `refresh_token`.
4. `supabase-js` сохраняет их (localStorage) и **сам** подставляет `Authorization: Bearer <access_token>` в каждый запрос.
5. Когда access-токен протухает, библиотека обновляет его по refresh-токену.

### Что внутри JWT

Подписанный JSON. Нам важны поля:

| Поле | Значение |
|---|---|
| `sub` | uid пользователя (`auth.users.id`) |
| `role` | `authenticated` (вошёл) или `anon` (токена нет — работает anon-ключ) |
| `exp` | когда истекает |

Подпись проверяет PostgREST. Подделать `sub` нельзя — подпись не сойдётся.

### Три роли Postgres, которые надо различать

| Роль | Кто | RLS |
|---|---|---|
| `anon` | запрос без входа (только anon-ключ) | действует |
| `authenticated` | запрос с токеном вошедшего | действует |
| `service_role` | серверный ключ (наш бот) | **обходит RLS** |

Поэтому service-role ключ **никогда не попадает в браузер**: с ним RLS бессилен.

### Auth ≠ «менеджер ресторана»

`auth.users` — просто «кто-то с аккаунтом». Если регистрация открыта, аккаунт заведёт кто угодно. Поэтому в спеке есть таблица `restaurant_managers` (`user_id → restaurant_id`): членство хранится **явно**. Вошёл ≠ имеет права. И `enable_signup = false` — дополнительный слой, а не замена.

## 3. RLS: «что тебе можно»

Row Level Security — механизм Postgres: для таблицы задаются **политики**, и БД сама фильтрует строки/операции под каждого пользователя.

```sql
alter table faq_entries enable row level security;
```

### Главные правила

1. **RLS включён, политик нет → доступа нет** (default deny). Для `anon` и `authenticated` таблица выглядит пустой, запись отклоняется. Сейчас так во всех таблицах проекта; бот работает, потому что `service_role` RLS обходит.
2. **Политики складываются по ИЛИ** (permissive): достаточно одной подходящей.
3. Политика привязана к роли (`to authenticated`) и операции (`select / insert / update / delete`).

### Два выражения в политике

- **`using (...)`** — какие *существующие* строки видны/доступны (для `select`, `update`, `delete`). Строка не прошла — её как будто нет.
- **`with check (...)`** — что можно *записать* (для `insert`, `update`). Не прошло — ошибка.

Зачем `with check` на `update`: без него менеджер мог бы выполнить `update faq_entries set restaurant_id = '<чужой>'` — `using` строку пропустил (она его), а новое значение никто не проверил. С `with check` результат тоже обязан удовлетворять условию.

### Функции Auth в политиках

- `auth.uid()` — uid из JWT текущего запроса (`sub`). Для `anon` это `null`.
- Пишем `(select auth.uid())`, а не `auth.uid()`: подзапрос вычисляется **один раз на запрос**, а не на каждую строку — заметно быстрее на больших таблицах.

## 4. Хелпер `is_manager_of` и зачем `security definer`

Политика на `menu_items` должна ответить: «текущий пользователь — менеджер ресторана этой строки?» Для этого нужно заглянуть в `restaurant_managers`.

**Проблема.** `restaurant_managers` сама под RLS. Если проверять членство прямо в политике (`exists (select … from restaurant_managers …)`), подзапрос выполняется **с правами вызывающего** и упирается в политику самой `restaurant_managers`. Получаются запутанные зависимости, а в худшем случае — рекурсия политик.

**Решение.** Вынести проверку в функцию с `security definer`: она исполняется с правами **владельца функции** (обходит RLS внутри себя), а наружу отдаёт только `true/false`.

```sql
create function is_manager_of(p_restaurant_id uuid) returns boolean
language sql stable security definer set search_path = ''
as $$
    select exists (
        select 1 from public.restaurant_managers
        where user_id = (select auth.uid()) and restaurant_id = p_restaurant_id
    );
$$;
```

Разбор:

- `security definer` — права владельца, RLS внутри не мешает.
- `set search_path = ''` — **обязательная гигиена** для definer-функций. Иначе злоумышленник мог бы создать у себя схему/функцию с подменённым именем, и привилегированная функция вызвала бы его код. Поэтому внутри везде полные имена: `public.restaurant_managers`.
- `stable` — функция не меняет данные, результат постоянен в рамках запроса; планировщик может оптимизировать.
- Наружу утекает только булево значение, не строки таблицы. Чужого членства через неё не узнать (`auth.uid()` берётся из JWT, а не из аргумента).

Дальше политики короткие:

```sql
create policy "managers manage faq"
on faq_entries for all to authenticated
using (is_manager_of(restaurant_id))
with check (is_manager_of(restaurant_id));
```

## 5. Карта политик S04

| Таблица | Кому / что |
|---|---|
| `restaurant_managers` | `select` только своей строки; писать из клиента нельзя никому |
| `restaurants` | `select`, `update` — менеджеру своего ресторана; `insert/delete` нет |
| `faq_entries`, `menu_categories`, `menu_items` | полный CRUD менеджеру своего ресторана |
| `conversations`, `messages`, `booking_requests`, `guest_requests`, `processed_updates` | **без политик** для `authenticated` до S05/S06 (принцип наименьших прав) |
| `anon` | политик нет нигде → доступа нет |

## 6. Чего RLS не делает (частые ошибки)

- **Не защищает от service-role ключа.** Утёк ключ — утекла вся БД.
- **Не заменяет валидацию.** Он решает «можно ли», а не «корректны ли данные» — для этого `check`-ограничения и zod.
- **View и функции с `security definer`** могут обойти RLS — каждую такую вещь надо проектировать как публичный API.
- **Забыли `enable row level security`** на новой таблице → она открыта всем, у кого есть доступ к API. Каждая новая таблица: сначала `enable`, потом политики.
- **Тест «в интерфейсе не видно» — не тест.** Проверять надо запросом с anon-ключом и токеном постороннего пользователя (интеграционный тест из §5 спеки).

## 7. Как это проверить руками

В SQL Editor Dashboard можно сыграть роль:

```sql
-- как anon
set local role anon;
select * from restaurants;          -- пусто

-- как конкретный вошедший пользователь
set local role authenticated;
set local request.jwt.claims = '{"sub": "<uid>", "role": "authenticated"}';
select * from faq_entries;          -- только его ресторан
```

А из браузера — в консоли с anon-ключом без токена `supabase.from('restaurants').select()` должен вернуть пустой массив, а `insert` — ошибку.

---

## 8. Шпаргалка

- **Auth** отвечает «кто»: выдаёт JWT, `auth.uid()` читает его в SQL.
- **RLS** отвечает «что можно»: политики на таблицах, default deny.
- **`restaurant_managers`** связывает «кто» с «чей ресторан».
- **`is_manager_of`** — `security definer`-хелпер, чтобы политики не упирались в RLS соседней таблицы.
- **`using`** фильтрует существующее, **`with check`** контролирует записываемое.
- **anon-ключ** публичный, **service-role** — только на сервере.
