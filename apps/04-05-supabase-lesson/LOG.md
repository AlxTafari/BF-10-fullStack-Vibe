## 2026-10-13 — S03: реализация (код готов, не прогнан на живой БД)
**Цель:** сделать бронь и обращения по спеке S03.
**Решения:**
- Домен: `zonedTime` (Intl, без зависимостей; несуществующее время → null, двойное → более раннее), `bookingRules` (даты/периоды/часы поверх `opening_hours`), `fieldValidation`, `bookingFlow` / `guestRequestFlow` (`advance` — чистая функция), `requestSummaries`. 65 тестов `deno test`.
- Кнопки сценария `flow:<draftId>:<действие>`, `draftId` не совпал → «Эта заявка уже неактуальна». Время/дата/период — только кнопками; «нет данных» для комментария — `null`.
- Сервисы `createBookingRequest` / `createGuestRequest` сначала ищут заявку по `idempotency_key`, и только потом валидируют: повтор через минуты не должен упасть на «слишком скоро». Параллельный двойной тап ловит `upsert … ignoreDuplicates`.
- `notifyManager` принимает функцию `send`, а не Telegram-клиент (ADR-008: сервисы не знают про Telegram). Сбой отправки логируется, заявка остаётся, `manager_notified_at = null`.
- ADR-006 / STATE §3 (апдейт помечается до обработки): оставляем как есть — сбой обработки подтверждения гость исправляет повторным «Отправить», дубль исключён ключом. Зафиксировать в STATE при закрытии.
- Уведомление менеджеру отправляется в `finally` после ответа гостю: сбой ответа гостю не лишает менеджера уведомления.
**Осталось:** `pnpm db:push`, перезалив seed, деплой функции, `manager_chat_id`, интеграционный тест на dev-БД, ручная приёмка по §5 спеки.

## 2026-10-13 — S03: учёт столов вынесен
**Решения:** столов и вместимости в модели нет, бот не проверяет занятость: заявка `pending`, место проверяет менеджер. Автопроверка мест — отдельный спринт после S05 (записано в роадмапе §2 и §3.1). Лимит заявок на час не вводим.

## 2026-10-13 — S03: кнопка «← Назад» в сценариях
**Цель:** гость смотрит часы обеда и хочет перейти к ужину, не сбрасывая заявку.
**Решения:** действие `back` в `advance` обоих сценариев: возвращает на предыдущий шаг и стирает данные этого шага и следующих (дату при возврате из периода сохраняем). Кнопка есть на всех шагах, кроме первых (дата, тип обращения) и экрана «слишком много гостей». Спеку не переписываем — расхождение (доп. кнопка) в STATE при закрытии.
**Осталось:** приёмка §5.

## 2026-10-13 — S03: приёмка отклонена — спам «заявка неактуальна» при многократном тапе
**Цель:** серия тапов по «Отправить» не должна давать гостю несколько сообщений; «неактуальна» после успешной отправки внушает, что заявка не ушла.
**Решения:**
- Состояние сбрасывается атомарно: `UPDATE … WHERE state->>'draftId' = <draft>` (`clearStateIfDraft`). Ответ гостю шлёт только обработчик, у которого сброс прошёл (`claimed`); уведомление менеджеру — только тот, кто создал заявку (`created`). Остальные тапы молчат.
- Кнопка «Отправить» старой сводки, чей черновик уже отправлен (`isDraftSubmitted` — поиск по `idempotency_key`), игнорируется без ответа. «Неактуальна» остаётся для брошенных/чужих сводок и прочих кнопок.
- Отступление от §5.3 спеки («гость видит ту же подтверждение»): подтверждение одно, повторы молчат.
- Тест: 3 параллельных `submitFlow` → 1 заявка, 1 `created`, 1 `claimed`.
**Осталось:** повторная приёмка §5.3, закрытие спринта по ритуалу.
