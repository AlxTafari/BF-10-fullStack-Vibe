## 2026-10-14 — старт S05: разбор открытых вопросов
**Цель:** закрыть вопросы §4 спеки S05 до миграции и кода.
**Решения:**
- В2: смена статуса только через RPC `security definer` (матрица, `p_from`, каскады не выражаются политикой).
- В3: подтверждать бронь в прошлом нельзя (`booking_in_past`).
- В4: запрос списка всегда с `limit 100`; в UI выбор размера страницы 20 / 50 / 100, по умолчанию 20 (срез на клиенте из загруженных 100). Пометка «Показаны последние 100» остаётся.
- В5: звук делаем — кнопка «🔔 Звук» в шапке, по умолчанию выключена (клик разблокирует аудио), играет только на `INSERT`. Системные уведомления браузера — нет.
- В6: просроченные `pending` не закрываем автоматически, помечаем «время прошло».
- В1: гостя уведомляем в Telegram. Вариант A: триггер + `pg_net` → Edge Function `notify-guest`; RPC ставит флаг транзакции, чтобы отмена самим гостем не уведомляла; колонка `guest_notified_at`. Только по броням (решения ресторана: confirmed / declined / cancelled); по обращениям нет — текстовый ответ менеджера это чат, S06.
- Спека S05 обновлена: `notify-guest`, `guest_notified_at`, триггер с флагом `app.notify_guest`, размер страницы, звук, инвариант 13, шаги приёмки 8а–8в.
- Миграция 1/2 `20261015100000_requests_read_realtime.sql` накатана на dev: `select`-политики на заявки, публикация `supabase_realtime`, индекс `(restaurant_id, booking_at)`. Миграция разбита на две (вторая — RPC, триггер, `guest_notified_at`), в спеке было «одна».
- **В7 закрыт** (`admin/tests/realtime.integration.test.ts`, 3 прогона подряд зелёные): менеджер получает INSERT и UPDATE своего ресторана; менеджер чужого ресторана, посторонний и аноним — ничего (RLS применяется к `postgres_changes`); `updated_at` и `booking_at` в payload строка-в-строку совпадают с PostgREST (`+00:00`, микросекунды) — нормализация в `time.ts`/`applyRowEvent` не нужна, сравнивать можно через `Date.parse`.
- **Находка:** `DELETE`-события RLS не фильтруются (удалённую строку нельзя прочитать): их получают все подписчики таблицы, но только с первичным ключом. Утечки данных нет, но событие приходит и чужого ресторана (каскадное удаление). `applyRowEvent` DELETE игнорирует или удаляет по `id`, если строка есть в кэше; фильтр `restaurant_id=eq.` в подписке эти события не отсекает.
- RLS-тест S04 обновлён: заявки теперь читаются менеджером (только свои), прямой `update`/`insert`/`delete` не работает; закрытыми остались `conversations`, `messages`, `processed_updates`. 111 тестов зелёные.
