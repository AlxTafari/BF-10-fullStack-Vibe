# Странная деревня — телеграм-бот (урок 3, Supabase)

## 1. Игра

Текстовый телеграм-бот с лором заброшенной деревни. Игрок заводит персонажа (только имя, без выбора роли), попадает в стартовую локацию — деревню, откуда может пойти к костру с терминалом.

**Основной функционал:**
- Онбординг: `/start` → имя → автоматическое назначение (без выбора игроком).
- Сцены: **деревня** (стартовая локация) и **костёр** (терминал). Переключение — `/сесть_у_костра`, `/встать`.
- В деревне любое произвольное сообщение → случайный отрывок описания локации (`VILLAGE_FRAGMENTS`) + призыв выбрать действие в меню. `/осмотреться` — то же самое без призыва.
- У костра любое сообщение → терминал отвечает отказом, затем рассказывает историю из общего пула (`tellTerminalStory`).
- `/новость` — передать весть терминалу (только из сцены «костёр»), лимит 5/день, есть анонимный вариант (2/день, без сохранения авторства).
- `/хроника` — листалка по всем вестям (пользовательские + истории терминала, пользовательские в приоритете), с реакциями (👍😂😱🤥) и датой по внутриигровому летоисчислению (`domain/calendar.ts`, сдвиг +209 лет).
- `/жители` — список активных за 30 дней, с числом вестей.
- `/что_здесь_происходит` — лорный текст (About).
- Контекстное меню (`mainMenuForScene`) — разный набор кнопок для деревни и костра.

**Статус игрового слоя:** механика лагерей (`camps`) в коде осталась, но временно не используется игроком — все новые персонажи получают дефолтный лагерь «Нейтралитет» без выбора, `/сменить_лагерь` отключена заглушкой. Разбор проблем игрового слоя и план развития (конфликт лагерей, счёт, подслушивание чужого лагеря, роль «смотрящего») — в `docs/GAME_DESIGN_REVIEW.md`. Исходный план и лор — `docs/plan.md`, `docs/lore-of-the-village.md`, `docs/draft.md` (локальные заметки, в git не попадают — см. `.gitignore`).

## 2. Технические цели: БД и Supabase

Учебная задача — отработать связи в реляционной БД и получить сквозной опыт с Supabase (Postgres + Edge Functions на Deno).

### Схема и связи

- **camps** (`id, name`) → **users** (`id, tg_id, name, camp_id, role, last_message_at, scene`) — one-to-many: у лагеря много жителей, у жителя один `camp_id`.
- **users** → **news** (`id, author_id, camp_id, text, created_at, posted_by`) — one-to-many: у жителя много вестей.
  - `author_id` — показывается как автор (null для анонимных и для филлера терминала).
  - `posted_by` — реальный автор, нужен только для подсчёта дневного лимита анонимных постов, наружу не отдаётся.
  - `camp_id` денормализован от автора на момент создания — не переписывается задним числом при смене лагеря.
- **users** ↔ **news** через **news_reactions** (`user_id, news_id, reaction_type, created_at`, `unique(user_id, news_id)`) — many-to-many: жители реагируют на много вестей, весть получает реакции от многих жителей. Апсерт при повторной реакции с другим типом.
- **users** → **messages** (`id, user_id, direction, text, created_at`) — one-to-many, сырой лог каждого входящего/исходящего сообщения (отдельное ТЗ, не связано с игровой лентой).

Все таблицы — `enable row level security`; доступ идёт через service role в Edge Functions (обходит RLS), политики — задел на будущее для прямого доступа с клиента.

### Edge Functions

- **telegram-webhook** — основной хендлер бота. Принимает апдейты от Telegram (проверка `X-Telegram-Bot-Api-Secret-Token`), роутит команды/callback-запросы, пишет каждое сообщение в `messages`.
- **list-clients** — ДЗ урока: все `users`, `order by last_message_at desc`.
- **list-messages** — ДЗ урока: все `messages`, `order by created_at desc`.

### Слои внутри функций (`_shared`)

- `domain/` — чистая бизнес-логика без зависимостей от Supabase/Telegram SDK: атрибуция вестей (`attribution.ts`), сборка ленты хроники (`chronicleFeed.ts`), случайный выбор (`randomPick.ts`), внутриигровой календарь (`calendar.ts`).
- `repositories/` — доступ к таблицам через Supabase-клиент (`campsRepo`, `usersRepo`, `newsRepo`, `messagesRepo`, `reactionsRepo`).
- `telegram/` — клиент Telegram Bot API (отправка сообщений, кнопок) и типы.
- `handlers/` (в `telegram-webhook`) — тонкие обработчики команд/сцен, вызывают domain + repositories.

## 3. Общие решения

- **Архитектура** — лёгкая чистая архитектура без переусложнения: domain / infra (repositories, telegram-клиент) / handlers. Никаких DI-контейнеров и абстракций под единственную реализацию — где логичнее одна функция, там одна функция.
- **Анонимность вестей** — `author_id = null`, связь с реальным автором нигде не хранится за пределами `posted_by` (нужен только для лимита, не для деанонимизации).
- **Денормализация `camp_id` в news** — осознанный компромисс ради целостности истории при смене лагеря, а не забытая нормализация.
- **Игровой слой не выпиливается вместе с фичами** — при временном отключении механик (смена лагеря, выбор лагеря при онбординге) код остаётся в проекте нетронутым для будущего возврата, отключается только вызов из обычного потока.
- **Тесты** — покрывают домен (`domain/`): атрибуция, выбор истории, сборка ленты, календарь.
- **Секреты** — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` задаются вручную; `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` Supabase прокидывает в Edge Functions автоматически. Локальная разработка — `supabase start` / `supabase functions serve` / `supabase db push`.
